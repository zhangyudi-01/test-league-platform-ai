## 一、数据流

```plaintext
中国竞彩网 webapi.sporttery.cn
  ├─ 受注赛程    → sporttery_football_match / sporttery_basketball_match（+球队、联赛档案）
  ├─ 混合过关赔率 → 足球 5 张玩法赔率表 / 篮球 4 张玩法赔率表
  ├─ 足球历史赔率 → 足球 5 张玩法历史表，并回写已有最新赔率表
  └─ 赛果       → 回写 match 表（比分字段）
                  └─ 赛程新增/修改及赛果回写 → audit_sporttery_*_match（Envers 修订快照）

```

本 change 合并三个相关需求，便于统一建设 Sporttery 采集链路；需求边界仍按 Story 分别跟踪和验收：

| 禅道需求 | 采集范围 | 关联任务 |
| --- | --- | --- |
| S619 竞彩赛事与球队信息采集 | 足球、篮球赛事（联赛）和球队来源信息 | T3670、T3671、T3672、T3673、T3674、T3721 |
| S620 竞彩赛程赛果信息采集 | 足球、篮球受注赛程和赛果 | T3722 |
| S621 竞彩赔率信息采集 | 足球、篮球各玩法赔率 | T3723 |

采集顺序（每轮）：**赛程 → 最新赔率 → 足球历史赔率 → 赛果 → 状态推进**。历史赔率需在赛果推进已开奖之前执行，避免候选比赛被排除；外部调度按入口独立触发。

## 字段缺失处理规则

| 字段类型 | 缺失处理 | 告警要求 |
| --- | --- | --- |
| 关键 ID：`matchId`、`leagueId`、`homeTeamId`、`awayTeamId` | 任一缺失即跳过该场的球队、联赛、赛程写入和状态推进；不影响同批其他比赛 | `WARN` 记录 `sport`、可获得的官方 ID 和具体 `missingFields` |
| 球队/联赛档案属性：简称、全称、联赛颜色 | 缺失或空白不阻断批次；新记录对应列保存 `NULL`。已有记录仅在来源值非空时更新，来源值缺失时保留旧值 | 每个缺失字段记录 `sport`、实体类型、对应官方 ID、来源比赛 ID 和具体上游字段名 |
| 其他可空赛程来源字段：场次、业务日期、比赛时间、销售状态、备注 | 新记录按映射结果保存，缺少业务日期或比赛时间时保存 `NULL`；已有记录遇到来源 `NULL` 时保留库内非空值，非空新值照常更新。缺少 `sellStatus` 时不推导停售或推进状态 | 缺少场次、日期、时间或销售状态时记录字段级 `WARN`；`remark` 为空属于正常可空信息，不单独告警 |
| 本地预处理字段：`if_change`、`s_match_id` | 采集不读取、不写入、不清空、不覆盖 | 不适用 |

缺 ID 校验同时约束赛程落库和状态推进；字段告警只跳过当前记录，不改变请求级响应，也不阻断同批其他有效记录。映射得到的 `null` 包括上游字段为 `null`、空字符串或空白字符串。更新语义为“来源有新值则更新、来源字段缺失则保留已有值”；首次插入没有旧值时，缺失的可空字段保持 `NULL`。场次编号仅在 `matchNumStr`、`matchNum` 均缺失时告警；业务日期以 `businessDate` 优先、`matchDate` 回退，两者均无有效值时告警。`matchDate` 同时是 `match_time` 的日期来源，因此自身缺失或无效时仍单独告警。告警分别列出具体上游字段名。

*   **处理逻辑**：按响应分页逐页请求并按 `matchId` 去重；仅使用有效的 `finalScore`，按“客队比分-主队比分”解析，左值写 `away_score`、右值写 `home_score`。只回写已有篮球赛程；比分为空、为 `-` 或格式不是“非负整数-非负整数”时跳过比分回写并保留已有值，不创建孤立赛果。本轮不读取 `oneScore`～`fourScore`，不采集四节或加时比分。
    

所有上游请求使用固定 `User-Agent` `Mozilla/5.0 (compatible; LeaguePlatform/1.0)` 并携带 `Referer: https://www.sporttery.cn/\`。采集服务对每次上游请求只发起一次 HTTP 请求；网络异常、超时、HTTP 错误或业务响应失败均直接转换为失败结果，由外部调度器按采集入口统一重跑。连接、读取超时沿用现有公共 HTTP 客户端配置。

### 2.7 足球历史赔率接口

*   **调用方式**：`GET https://webapi.sporttery.cn/gateway/uniform/football/getFixedBonusV1.qry?clientCode=3001&matchId=2041646\`。
    
*   **参数**：固定 `clientCode=3001`；`matchId` 取本地赛程官方 ID，一次请求一场比赛；没有日期范围参数。
    
*   **返回示例**：2026/10/15 实测，完整赔率列表保存于 `samples/football-odds-record.json`；下例为其中 HHAD 首条，未虚构 HAD 数据（该样本 hadList 为空）。
    

```json
{
  "errorCode": "0",
  "success": true,
  "value": {
    "oddsHistory": {

      "hadList": [],

      "hhadList": [
        {"a":"3.00","updateDate":"2026-09-22","df":"0","d":"4.15","af":"0","h":"1.80","updateTime":"09:19:24","hf":"0","goalLine":"-2"}
      ]
    }
  }
}

```

*   **玩法区分**：`hadList/hhadList/crsList/ttgList/hafuList` 分别为胜平负、让球胜平负、比分、总进球、半全场历史；一次响应可以返回多次赔率变化，不是只有最终赔率。
    
*   **发布时间**：`updateDate + updateTime` 按北京时间组成 `release_time`，不使用采集时间替代；无效时间或错误结构的条目跳过并记录失败。空列表或没有有效正数赔率属于正常无数据，不写记录、不填 0。
    
*   **字段差异**：比分“胜其他／平其他／负其他”来自 `s-1sh/s-1sd/s-1sa`，转换后保存 `win_else/equal_else/lose_else`。后缀 `f` 是变化标记，不是赔率。其余玩法复用最新赔率的选项对应关系。
    
*   **落库**：写入足球五张 `*_odds_record`，每张按 `match_id + release_time` 幂等保存全部有效历史。只能保存官网当前返回的历史，不承诺永久全历史或本地没有 ID 的比赛。
    

## 三、data-collection 对外提供的调度接口

以下 7 个 `POST` 接口由外部调度任务调用，每个接口只触发一项采集，不接收请求体、日期或分页参数。响应统一为 `CommonResult`：成功时 `code=0`、`message=OK`，失败时通过错误码和 `message` 表示；成功与失败时 `data` 均为 `null`，不返回采集数量或阶段摘要。采集数量和异常详情通过日志记录。上游请求失败时不由服务内部自动重试；历史赔率入口在单场失败后继续其他比赛，整轮返回失败；外部调度器根据失败结果决定是否重跑。

*   **调用方式**：`POST /sporttery/football/odds/record`。
    
*   **请求参数**：无请求体、无查询参数。
    
*   **上游接口**：足球 `getFixedBonusV1.qry?clientCode=3001&matchId=...`。
    
*   **返回示例**：
    

```json

```

*   **候选比赛**：沿用旧 JcZqOddsRecord，以北京时间当天零点为基准，选择 `match_time >= 当天零点 - 配置天数` 且 `sell_status != 3` 的本地足球比赛，按比赛时间和 ID 排序，不限制未来比赛。默认回溯 15 天；这不是“补抓所有已完赛比赛”的入口，已开奖和本地不存在的比赛不在本轮范围内。
    
*   **历史保存**：按五玩法保存官网实际返回的历史，无数据不建记录；联合主键确保重复调度不增加重复版本，缺失选项为 NULL，重复版本中的缺失值不抹掉已有有效值。
    
*   **最新回写**：按真实发布时间最大值选择每个玩法最新记录，回写已存在的五张最新表；HHAD 同时更新 `handicap`。保持旧代码的“只 UPDATE”行为，不创建缺失的最新行，不改 `int_single/match_status/collect_time`。早于库中已存最大历史时间的响应不回写最新表。
    
*   **事务及失败**：HTTP 请求在事务外；每场比赛的历史保存和最新回写使用独立事务，写入失败整场回滚，其他比赛继续。任一比赛或历史条目异常时整轮按现有 `ResultEnum.SERVICE_EXCEPTION` 返回 `code=31、message=服务异常、data=null`；空历史列表正常返回成功。失败由外部调度重跑，无内部重试。
    
*   **旧代码边界**：只迁移足球历史赔率与最新表回写，不建设旧项目的文件上传和短信推送登记；篮球历史赔率不在此次范围。

## 五、表设计

本设计共包含 22 张表：15 张来源表、5 张足球历史赔率表和 2 张赛程审计表。篮球赛程业务表及审计表保留 `part_end` 并新增 `away_score`、`home_score`。两张赛程表均包含预处理关联字段 `s_match_id`、支持反查的普通索引及可空 `if_change`；不建立数据库唯一约束，同一运动内一对一关联由 S622 应用层维护。对应审计表保存两列的可空快照。两列均由预处理维护，采集不解析、不赋值、不清空、不覆盖。其余来源表保留 DBA 定稿结构。本章维护最新完整建表 SQL；为篮球比分拆分另提供一次性扩展/回填迁移 SQL，保留 `part_end`，新增 `away_score`、`home_score` 并从历史 `part_end` 回填；核验后仍保留原字段。完整 SQL 文件为 `apps/league-platform/coredb-entity/src/main/resources/db/sporttery-schema.sql`，迁移 SQL 为 `apps/league-platform/coredb-entity/src/main/resources/db/sporttery-basketball-score-split-migration.sql`。共享 `revinfo` 复用已有表，不计入新增表数，不重建、不清空。各 SQL 由人员手动执行，应用不自动建表。

球队、联赛、比赛及九张赔率表中的数值 ID，在上游 DTO、Java 实体、Repository 主键和写入参数中统一使用 `Long`，不在 Java 映射过程中窄化为 `Integer`。数据库列类型仍严格保持 DBA SQL 中定义的 `BIGINT` 或 `INT`；`INT` 列可由 Java `Long` 表示，但实际写入仍受数据库 `INT` 取值范围限制。

DBA 第十三轮设计已移除 9 张玩法赔率表对比赛表的数据库外键。比赛表 `match_id` 为 `BIGINT`，赔率表 `match_id` 为 `INT`，两者通过相同的官方比赛 ID 进行业务关联；赔率记录写入时仍须确保 ID 在数据库 `INT` 的取值范围内。Java 使用 `Long` 不会扩大数据库 `INT` 列的存储范围。

### 5.10 竞彩足球、篮球赛程审计表

赛程表映射预处理维护的 `s_match_id` 和 `if_change`，采集任何情况下不解析、不赋值、不覆盖或清空两列。新增赛程两列保持 NULL，刷新及回写保留原值。两类实体通过 DynamicInsert/DynamicUpdate 避免未改变的关联列进入采集业务 SQL。审计表保存两列快照，`s_match_id` 不设置唯一索引，允许同一比赛保留多个修订。足球、篮球主表及审计表的最新完整定义均包含可空 `if_change`。

| 业务表 | 审计表 | 记录内容 |
| --- | --- | --- |
| sporttery\_football\_match | audit\_sporttery\_football\_match | 足球赛程全部字段、销售状态、主客对调、半场/全场比分及创建/更新时间快照 |
| sporttery\_basketball\_match | audit\_sporttery\_basketball\_match | 篮球赛程全部字段、销售状态、四节比分、主客队全场得分及创建/更新时间快照 |

*   **实现方式**：参考现有 Nami 足球、篮球赛程的 `@Audited`，沿用项目 Hibernate Envers。审计表不另写采集接口，不新增独立实体或 Repository。
    
*   **修订字段**：`rev INT` 为共享 `revinfo.rev`，`revtype TINYINT` 为 0 新增、1 修改、2 删除。联合主键 `(match_id, rev)`，同一事务内同一比赛多次修改合并为一条；审计发生时间通过 `revinfo.revtstmp`（毫秒时间戳）查询。
    
*   **写入逻辑**：足球、篮球赛程 Repository 的赛程保存、状态推进、赛果回写改为事务内 JPA 实体保存；已有记录先加悲观写锁，合并状态时只进不退，缺失比分不清空已有值。原生 SQL 和 JPQL 批量 UPDATE 会绕过 Envers，不能用于这些赛程写入。球队、联赛与赔率仍按原子 Upsert 写入。
    
*   **并发及事务**：业务数据与审计在同一事务提交或回滚；首次并发插入可能发生主键冲突或死锁，事务回滚后由外部调度重跑。完全相同数据重复采集不生成新修订，也不单独刷新赛程 `update_time`；该时间表示最后一次实体实际修改，不是每次抓取时间。
    
*   **审计范围**：记录启用后的 JPA 新增、修改、删除；不新增删除入口，直接执行数据库 SQL 不会被 Envers 捕获。已有比赛从后续首次实际变更开始留痕，不自动生成旧数据基线，不补造历史。
    
*   **新增配置**：无。沿用已有 `org.hibernate.envers.audit_table_prefix=audit_`、空后缀和 `store_data_at_delete=true`，复用共享 `revinfo`。
    
*   **建表与字段**：业务字段的类型、长度与各自原表保持一致；审计快照允许 NULL，创建/更新时间保留原值，不设置默认当前时间或自动刷新。遵循现有审计表模式，不新增外键。下方为两张审计表的最新完整定义，共享 `revinfo` 沿用现有结构。

### 5.11 篮球全场比分拆分迁移

篮球赛果列表接口仍为 `getUniformMatchResultV2.qry`。其 `finalScore` 为“客队得分-主队得分”。运行时直接解析上游 `finalScore`，将客队:主队格式保存到保留字段 `part_end`，并分别写入新增整数列 `away_score`、`home_score`；新列不是从运行时 `part_end` 再拆分。只有存量迁移会从历史冒号格式 `part_end` 回填两个新列。本次不调用比分直播 `getMatchScoreV1.qry` 或固定奖金详情接口，不采集四节/加时比分；已有 `part1`～`part4` 字段在表结构和 Java 实体中保留以兼容历史数据，但本次采集不读取、不更新这些字段。

*   **全量建表**：`sporttery-schema.sql` 和独立审计建表 SQL 保留 `part_end` 并新增 `away_score INT`、`home_score INT`；篮球四节字段 `part1`～`part4` 在完整表和 Java 实体中保留，以兼容历史数据；采集链路不再处理这些字段。新建环境同时保留 `part_end` 和新增主客得分列。
    
*   **存量升级**：人工备份业务表与审计表后执行 `sporttery-basketball-score-split-migration.sql`。脚本先新增主客得分列，再将符合 `^[0-9]+:[0-9]+$` 的旧 `part_end` 按客队在前、主队在后回填到业务表和审计快照；不符合冒号格式的旧值保留在 `part_end` 待核查。
    
*   **兼容与回滚**：`part_end` 为兼容保留字段，不删除；回滚时仅删除新增的 `away_score`、`home_score`，继续保留 `part_end`。
    
*   **审计影响**：新比分字段纳入 Envers 业务实体和审计表。迁移回填通过数据库 SQL 执行，不会生成 Envers 修订，也不回填新的历史审计事件；审计表中既有 `part_end` 快照按同一规则迁移。
