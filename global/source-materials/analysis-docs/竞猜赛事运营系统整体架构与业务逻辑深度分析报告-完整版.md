# 第一部分 · 项目概述与核心业务

## 1.1 系统定位

本系统是**体育彩票"北京单场"（北单）竞猜游戏的中后台运营平台**，处于"赛事数据源"与"北单游戏系统（体彩中心）"之间的核心运营枢纽位置。它在"赛事服务大平台"体系中的定位：

```
┌──────────────────┐   ┌──────────────────────────┐   ┌──────────────┐
│ 外部数据源         │   │     赛事服务大平台          │   │  北单游戏系统  │
│ 纳米/贝泰/同行/竞彩 │──▶│  数据采集→预处理→识别→运营  │──▶│  (体彩中心)   │
│ + 人工录入         │   │  【本系统：竞猜赛事运营系统】 │   │  sftp 文件交互 │
└──────────────────┘   └──────────────────────────┘   └──────────────┘
```

系统与北单游戏系统的交互是**文件级（sftp）而非接口级**：通过 8 类 V2 文件（A1 奖期创建 / A2 导入赛果 / A3 追加比赛 / A4 导入赛事 / A5 导入球队 / B1–B3 对应修改类）以"json → 加密签名 → zip → 上传 sftp 指定目录（按日期文件夹）"的方式完成赛程下发与赛果回传。实库 `bd_submit_batch` 显示 A1–A5 全部在用（A2 导入赛果 777 次占比最高），线上提交为主、线下下载为辅。

同时系统通过 **openapi v1 对外输出数据服务**（`/v1/bdlottery/match/list` 北单赛程彩果、`/v1/football/*` 比赛列表/直播/欧赔亚盘/积分榜/分析等 9 个只读接口，HMAC-SHA256 鉴权 + 用户/接口维度限流）——已从纯内控平台升级为"内控运营 + 数据开放"双能力平台。

## 1.3 核心业务域

覆盖 **12 个运动项目 + 3 个团体项目**（字典 `league_sport_id` 1–17），三类竞猜游戏（字典 game_type / game_id）：

| 游戏 | gameType | 子游戏（game_id） | 说明 |
| --- | --- | --- | --- |
| 足球单场 | 1200 | 200 胜平负 / 210 上下盘单双 / 230 总进球 / 240 半全场 / 250 单场比分 | 仅足球，任开 1 个子游戏即拥有"单场场次编号" |
| 下半场比分 | 1260 | 260 | 仅足球 |
| 胜负过关 | 1270 | 270 | 全运动，最大场次编号 ≥3 才可提交 |

## 1.4 解决的核心业务痛点

1. **多源数据不一致**：纳米（足球/篮球/冰球/橄榄球）、贝泰（足球）、同行（足球）、**中国竞彩（第 13 轮新增足球/篮球，`source_type=4`）**、人工录入五类数据源的字段、状态码、比分口径、主客顺序均不相同——通过标准化数据模型（s_match）+ 多源 ID 映射（`r_basic_data`/`r_team_data` 及竞彩独立映射表 `r_sporttery_basic_data`/`r_sporttery_team_data`）+ 字段级取数规则解决；
2. **多人交叉复核的风控要求**：草稿"审核+复核"、赛果"≥2 人审核一致才可确认"、赛果批次"≥3 人完成审核才可提交"——全流程内建制衡且均有表级落地；
3. **比赛异常闭环处置**：事件发现 → 告警核实 → 异常确认 → 变更处理（记录在案/调整停售/开奖延后/退票/争议赛果/按实际结果开奖）→ 变更单/公告导出 → 完成确认，全链路可回溯、可作废、可取消完成；
4. **人与系统的职责切分**：预处理阶段系统自动更新有白名单限制，入稿后/开售后的关键变更一律转人工任务；
5. **合规留痕**：操作日志（toto_operation_record 实库 17 万条）+ 实体审计（Envers audit_* 全域覆盖）+ 文件快照（bd_submit_batch.detail 存完整 json 内容）三层留痕。

## 2.2 北单赛程管理（业务主干）

**层级结构**：`奖期(bd_game_draw) 1 → N 批次(bd_batch) 1 → N 用户草稿(bd_batch_matchup_draft) → 草稿比对 → 正式版(bd_batch_matchup) → 开奖时间 → 赛果批次(bd_batch_matchup_draw)`

**① 奖期 bd_game_draw**：5 位奖期号（= 停售时间年+月）、开售/停售/开奖时间、`game1200/game1260/game1270` 三布尔列。有批次开售后不可编辑；无批次才可物理删除。实库 75→87 个奖期。

**② 批次 bd_batch**：单表双态（`batch_type` 0 赛程 / 1 开奖）；三状态字段 `batch_sale_status`（官网采集回写）/ `submit_status`（文件提交）/ `batch_draw_status`（开奖采集回写）。实库 1058→1165 批次。

**③ 个人草稿 bd_batch_matchup_draft**（每用户每批次一份，按 create_account 隔离）——OpenAPI 补充的关键实现细节：
- **会话式实时编辑**：`real-time/*` 系列接口（add/delete/manual-sort-no/matchup-no/recreate-sort-no/sales/sales-260/batch-matchup-drafts）在保存前操作"当前会话中的草稿"，`real-time/cancel` 清空会话；最终 `POST /batch-matchup-drafts` 才固化入库——前端高频编辑与库表解耦；
- **草稿流程节点**（MatchupDraftUpdateDTO.draftProcessNodes）：0 初始化 → 1 草稿已比对 → 2 草稿已配置让球 → 3 草稿已生成正式版 → 4 草稿配置开奖时间 → 5 草稿开奖时间比对——**草稿页六滑签的页内状态机**；
- **独立只读校验接口**（先弹窗确认再完整校验的 PRD 要求落地）：
  - `validate-main-source-match-availability`：主数据源比赛是否已删除/置换（只读，有异常仍返回 200+data 明细）；
  - `validate-sale-end-time-match`：停售时间与下半场停售时间不一致校验（需求 549，只读旁路）；
  - `verify/consistent`：用户草稿 vs 正式版一致性（开奖时间草稿的前置校验）；
  - `batch-matchup/validate-match-in-other-game-draw`：比赛是否已在其他奖期生成正式版；
- 添加比赛/让球/审核复核/场次编号/开售游戏/转移/导入胜负比赛/创建比赛/赛程变更等完整功能（详见追溯矩阵）；
- 停售时间默认规则可配置：`GET /batch-matchup-drafts/default-sale-end-rule-config`（实库字典 06:00–10:15 区间取 06:00）；
- **操作锁**：比对期间草稿保存/让球保存/开奖时间草稿均锁定——bd_batch_diff_record 联合主键 + `batch-diff/in-progress` 查询进行中比对 + `batch-diff/cancel/session` 会话级取消。

**④ 让球配置**：单场 |5| 整数、胜负 |99.5| 且 \*.5 结尾，分差 0.5 提醒，赔率联动展示。

**⑤ 草稿比对**：`bd_batch_matchup_diff` 逐字段差异；保存覆盖参与人；**生成正式版** → 18 位编号 → 回写 s_match → 覆盖草稿；`matchup-formal/previous-matchup-no` 查前置批次场次号（连贯性校验数据源）。

**⑥ 开奖时间草稿/比对**：节点切分 + 精细默认时间规则；`batch-matchup-drafts/change/draw-time` 查询比赛的异常开奖变更时间（变更管理联动）。

**⑦ 文件提交**：比赛（A1/A3/B1/B3）、赛事（A4）、球队（A5）三通道 + `valid_download/valid_*` 校验 + `download/download_*` 线下下载。

## 2.3 比赛监控（北单赛程监控 & 竞彩赛程监控）

### 2.3.1 北单赛程监控（第 13 轮菜单重命名自原“比赛监控”）
- 监控列表：行背景色按开售后异常事件着色；足球"比赛中"融合贝泰直播（`GET /s-match/live`）；
- 填写监控记录（POST /monitor）：无变动/新增异常/新增预警——创建事件+告警/预警；
- 赛果审核（event-match-check 系列）：贝泰/纳米双源，主客可互换；**`POST /event-match-check/batch` 支持批次维度批量创建/修改审核信息**；**第 12 轮（PBL-611）新增 `event_match_check.data_source_type`（1 纳米 / 3 贝泰）记录审核人所选数据源并落库回显**；
- 赛果确认三步接口：`match-result/check`（可确认校验）→ `match-result/diff`（多人比对）→ `match-result/confirm`（确认落库）；
- 赛果回退：`POST /match-result-rolled-back`（matchIdList）；
- 比赛进程：贝泰 27 种事件 + 纳米事件流；
- 赛果确认记录：`GET /s-match/result-confirm-record`。

### 2.3.2 竞彩赛程监控（第 13 轮新增 PBL-634）
- **定位与展示**：在【比赛监控】下新增【竞彩赛程监控】菜单（权限 `#152` 查询、`#153` 备注），按足球（运动项目=1）/篮球（运动项目=2）切换展示中国体彩网（竞彩网）抓取的比赛、单关/过关赔率与开售状态、半场/全场比分与彩果；
- **关联北单展示**：若竞彩比赛已关联我方标准比赛（`sporttery_*_match.s_match_id = s_match.match_id`），则展示关联的**北单比赛编号（`matchup_unique_no`）**及对应玩法的北单场次号；
- **变动事件与告警监控**：当竞彩发生开赛时间变化、队伍变化、比赛取消/推迟/中断/腰斩等异常时，生成 `sporttery_match_event` 与 `sporttery_task` 记录；页面支持【变动事件】弹窗查看历史变动轨迹（`GET /data-backend/sporttery/match-monitor/events`）；
- **独立备注体系**：使用 `sporttery_match_remark` 表（唯一键 `sport_id + remark_type + match_id + create_account`）维护竞彩比赛监控备注（`POST /data-backend/sporttery/match-monitor/remark`、`GET .../remarks`）。

## 2.4 异常管理 / 2.5 变更管理

- 告警核实（check_type=1）→ 异常确认（`event-match-check/event/confirm`，按异常类型联动更新 s_match）；
- **告警异常详情修改（第 13 轮新增 PBL-638）**：告警管理页支持编辑并保存任务的异常原因详述（`task.attribution_desc`），接口 `POST /data-backend/monitor/attribution-desc`（对应权限 `#147 ycgl:gjgl:update`）；
- 变更六操作（abnormal/record 新建处理、voided 作废、completed 完成确认、`task/cancel` 取消完成）；
- `abnormal/draw_time` 详情查询（开奖延后操作的时间展示）；
- 导出：`report/change_matchup/{id}` 变更单、`event_notice_export` 变更公告（前置校验 valid_change_notice / valid_change_inform）。

## 2.6 开奖管理

- 赛果批次：bd-batch/draw 系列（新建/编辑/删除/批次详情/序号调整）；
- 批次详情：`batch-matchup-draw` 系列（会话式 real-time add/delete/draw + `matchup` 范围添加 + `batch-matchup-draw-time` 计划添加 + `review-status` 审核开关）；
- 开奖计划：`batch-matchup/draw_time_plan`（原计划）+ `operation_draw_time`（变更后计划）；
- 提交赛果文件 A2/B2（≥3 人审核 + 全部赛果已确认 + 无未完成人工变更）。

- 匹配三链路（dimension/relations/{competition|season|team}）+ relations/{nami|beitai}/* 查询 + realtime/{nami|beitai}/matchup 预览；
- **第 13 轮新增竞彩赛事管理（PBL-632）与竞彩球队管理（PBL-633）**：

# 第三部分 · 业务流程与模块流转

## 3.1 主链路：赛程生命周期（正向流）

```
新建奖期 ─▶ 新建批次 ─▶ 各用户草稿(real-time会话式编辑→保存固化) ─▶ 草稿比对(分布式锁+差异记录)
   │                                                            │
   │                                            ┌── 保存草稿(覆盖参与人) ──┘
   │                                            └── 生成正式版(18位编号/回写s_match) ─▶ 正式详情
   │                                                                            │
   │                                             开奖时间草稿(verify/consistent校验) ─▶ 比对 ─▶ 保存至正式版
   │                                                                            │
   └─ 提交赛事文件(A4)/球队文件(A5)/比赛文件(A1|A3) ─▶ sftp ─▶ 北单系统导入
   └─ 下载文件(valid_download校验→download) 线下通道
   │                                                                            │
                     bjlot_match(官网采集/bd/match) ──▶ 批次开售状态回读 ──▶ 复合状态"已开售"
```

关键流转规则：
- 比赛复合状态沿 `未入稿(1000) → 已入稿(1001) → 赛程已提交(1002) → 已开售(1003) → (完场后)赛果已提交(1205) → 已开奖(1206)` 单向推进；
- **生成正式版是"草稿域→数据中心域"唯一回写点**；文件提交成功是"运营域→北单域"唯一出口；
- 开售前一切可逆；**开售后草稿侧全部锁定**，风险处置切换到监控/变更链路。

## 3.2 赛果与开奖链路

```
比赛完场(数据源事件)
 ─▶ 比赛监控列表 ─▶ 监控记录(人工造事件)
 ─▶ 赛果审核(event-match-check/batch 批量, 记录data_source_type 1纳米/3贝泰, ≥2人一致)

 ─▶ bjlot 官网开奖采集 ─▶ "已开奖"(终态)
```

## 5.2 请求链路（OpenAPI 证实的三层架构）

```
前端 ──▶ data-bff ──(代理透传)──▶ data-backend ──▶ MySQL(test2_newgoal)
   │         │(25自营: 草稿/开奖real-time会话、report、upload、download、otp)
   │         └─▶ league-bff-service ──▶ league-backend-service(V1老系统: 账号/角色)
   └─▶ notification(SSE长连接)
外部业务方 ──▶ openapi v1(HMAC+限流) ──▶ 只读数据服务
调度器 ──▶ data-collection(采集: 纳米/贝泰/同行/SportRadar/北单官网/★中国竞彩)
       ──▶ data-computation(标准化/检测/事件/★竞彩关联与变动事件) ──▶ 原始表/s_match/s_event/sporttery_*
```

**关键架构结论**：
1. **BFF 聚合层**：前端统一走 data-bff，其中 `/data-backend/*` 代理接口直接透传——PRD 操作日志中的 `/data-backend/*` 路径实为 BFF 代理路径；
2. **V1/V2 并存**：league-backend-service / league-bff-service 是老系统（北单 2.0），仍在承担账号/角色管理（data-bff 的 manager_account 系列走 league-bff 代理）；权限模块"继承北单 v2 系统"（rdc 表注释）得到接口层面证实；
3. **草稿/开奖的会话式实时编辑**是 data-bff 自营的核心增值逻辑（非简单代理）；
4. **错误码规范统一**：所有接口 yaml 注释 errorCode 0=成功 / 2=业务校验 / 3x=系统异常，跨服务一致。

# 第六部分 · 风险与设计瑕疵提示（含第 13 轮实库核验新发现）

1. **★ 第 13 轮竞彩表主键类型不一致（BIGINT vs INT）**：`sporttery_football_match.match_id` 与 `sporttery_basketball_match.match_id` 均为 `BIGINT`，但 9 张最新赔率表（`sporttery_football_*_odds`、`sporttery_basketball_*_odds`）和 5 张历史赔率表（`sporttery_football_*_odds_record`）的 `match_id` 以及 `sporttery_match_remark.match_id` 均定义为 `INT`（最大值约 21.4 亿）。当前竞彩官方 `matchId` 约 7~8 位整数（如 `2031220`）暂未溢出，但类型定义不一致存在长期隐患；
2. **★ 第 13 轮竞彩篮球存量数据比分拆分迁移 SQL 尚未执行**：`sporttery_basketball_match` 实库共 10,727 行，其中 10,668 行已有 `part_end`（格式 `"客队:主队"`），但新增列 `home_score` 与 `away_score` 在实库中**全部为 NULL**（说明《第十三轮冲刺竞彩抓取数据库设计和变更.md》第 2 节中的存量数据拆分 `UPDATE` 脚本尚未在 `test2_newgoal` 执行）；同时 `sporttery_football_match` 与 `sporttery_basketball_match` 的 `s_match_id` 目前全表均为 NULL（因 `r_sporttery_team_data` 尚未配置球队映射）；
3. **★ 第 13 轮权限 `#147` 尚未在实库执行插入**：设计文档定义的 7 条新权限（`#147~#153`）中，实库 `toto_permission` 仅插入了 `#148~#153`（共 6 条，总有效权限 149 条），而 **`#147`（异常管理 → 告警管理 → 修改，`ycgl:gjgl:update`，绑定 `POST /data-backend/monitor/attribution-desc`）尚未入库**，测试 PBL-638 时需关注接口鉴权是否因缺少 `#147` 权限记录而拦截；
4. **★ `r_sporttery_basic_data` 缺少数据库级唯一约束**：对比 `r_sporttery_team_data` 建有唯一索引 `uk_std_team (sporttery_team_id, sport_id, manual_team_id)`，`r_sporttery_basic_data` 仅以自增 `relation_id` 为主键，未对 `(sporttery_competition_id, sport_id)` 建唯一键，并发初始化或重复写入完全依赖应用层与乐观锁 `version` 防重；
5. **★ 竞彩采集脏数据与表名拼写瑕疵**：实库 `sporttery_football_team` 存在一条 `team_id=0`、名称全为空字符串的记录（来自上游接口未开售/占位数据）；`sporttery_football_ttg_odds_record`（总进球历史赔率）与 `sporttery_basketball_mnl_odds`（篮球胜负最新赔率）在实库中当前为 **0 行**，联调测试时需关注对应玩法的采集与展示；新增贝泰国家表 `beitai_footbal_country` 表名漏写字母 `l`；
6. **md 设计文档滞后于实库与 OpenAPI**（以 SQL dump + 实库 + OpenAPI 为准）：匹配字段同行→贝泰、s_event.reason_desc 扩容、s_match 新增 4 字段、角色新增两个；
7. **md 文档自身错误**：s_country/nami_football_season 字段表贴错、toto_account 描述错位；
8. bd_batch_matchup_draft 无业务唯一键——但 OpenAPI 显示 real-time 会话式编辑 + 最终单次 POST 固化，实际降低了并发窗口，风险缓释；
9. nami_basketball_stage_newgoal 字段名与语义不符；
10. 全库无物理外键——数据源删除→悬挂引用依赖 `*_deleted` + 17 识别规则兜底（实库 4 万条删除类任务为高频主负载；1382 条"赛季球队未关联"任务 status=4 失败需排查）；
11. bd_game_draw 三游戏布尔列扩展性弱；
12. 库内 ~48 张备份临时表无治理规范；
13. **V1/V2 双系统并存**：账号/角色在 league-backend-service（V1），业务在 data-backend（V2），BFF 层编织——跨系统一致性（如账号删除后 V2 权限残留）是长期维护风险；
14. openapi v1 的 `/v1/bdlottery/match/list` 硬依赖 bjlot_match 最新 2 个奖期的 update_time 增量语义，官网采集中断将直接影响对外数据服务时效。
