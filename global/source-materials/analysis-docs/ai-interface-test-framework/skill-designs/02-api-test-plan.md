# Skill 设计：api-test-plan

## 目标

生成一个 operation 的接口测试方案，**接口测试点直接写在方案的测试内容表格中**。接口执行证据形成后，同一 Skill 再按模块 Facet 收敛接口测试之后仍需做的功能测试。

## 两种调用模式

### 接口测试方案

**输入**：已澄清的接口分析、当前需求/OpenAPI、相关数据关系与 SQL 逻辑、测试范围，以及测试工程的 `测试代码知识图谱.md`、`测试脚本开发规范.md`、`代码编写规则.md`。存在历史复用回顾或用户指定参考时，按当前接口追读相关旧场景，用当前依据判断承接、变化或排除；没有历史参考不因此阻塞。按目标服务和用例类型读取相关章节，不把三份规范全文复制到方案。

**输出**：当前 operation 的测试方案。测试内容表格必须保持以下四列和顺序：

| **序号** | **测试项** | **测试点** | **备注** |
| --- | --- | --- | --- |
| 1 | `<规则分组>` | 【<可区分场景>】<前置数据/请求条件> → <明确响应或数据库预期> | <可选来源或补充边界> |

表格外仅在存在非标准路径或阻塞时，追加简短的“自动化适配说明”，按表格序号引用测试点，不新增表格列。该说明把两项判断分开写：

- **API 可观察性**：可由请求/响应或数据库副作用验证；或不可由接口边界观察，需由页面/交互等功能测试验证。
- **框架实现状态**：现有框架可直接实现；需要合规扩展；或尚待自动化设计确认。

“当前框架没有现成 helper”不等于“API 不可测”。框架缺口必须保留为适配/扩展事项，不能成为删除业务测试点或把它改列为功能测试的理由。只有行为本身无法从 API 请求、响应或可验证副作用观察，才归入功能测试。

**编写规则**：

- `测试项`用于把同一业务规则或判定风险归组；保持参考方案的显示方式，组内后续行可留空。
- `测试点`需能独立准备、触发和判定。按需要写出关键前置数据、请求参数/操作和精确预期；复杂预期可列字段/状态/顺序，不使用“符合要求”“正常返回”等不可判定措辞。
- 一个测试点只验证一个主要风险；不同输入导致不同错误/状态/副作用时分行。共享条件可精简重复，但不能依赖读者猜测。
- `备注`只放需求/接口/已确认问题来源、特殊测试边界或后续 SQL 核对提示；不得把必要前置条件或预期藏在此列。
- 只有契约明确或用户确认的边界才写成确定预期。若口径未知，返回澄清问题，不用“观察行为”伪装成可判定结果；探索性验证须有明确目的并标注。
- 覆盖成功、错误、空值/空集合、边界、跨字段、排序分页、状态转换和数据库副作用中与本接口有关的部分；不机械套用无关类别，也不漏掉需求明确的可观察行为。
- 不新增 TP-ID、优先级等表格列。后续通过最终序号、测试项和测试点简称追溯到自动化实施方案。

### 接口后功能残余收敛

**输入**：模块需求行为面、各相关 API 的测试点和真实运行状态、已通过断言及证据、页面/交互需求。

**输出**：同样使用四列表格的功能残余测试方案：

- 接口确实无法验证的视觉、控件交互、自动刷新、页面状态保持等行为保留为功能测试。
- API 已验证的业务规则不重复写成完整功能测试；只按风险增加少量页面呈现一致性或关键路径抽查。
- 接口未执行、失败、仅收集成功或阻塞的行为仍算未覆盖，不得据此删除功能测试。
- 所有相关 API 状态明确后才能给模块完整结论；范围未齐时只能输出明确标记的阶段性结果。

## 执行步骤

1. 校验输入分析中的问题是否已回答，确认当前 operation 和测试范围。
2. 按需求/契约逐项映射可观察行为；同时查阅测试工程资料，核对现有 Excel、纯 Python、client/generator、fixture 和 DB 验证能力。分别判断“API 能否观察此行为”和“现有框架能否直接实现”，不得混为一个判断。
3. 按业务风险组织测试项，写成四列表格；检查每个测试点是否自包含、结果是否可判定、是否有重复或遗漏。
4. 保留测试点到需求/接口来源的引用；把需要独立 SQL 验证的数据逻辑标出，但不在此生成最终 SQL 文件。
5. 仅在“功能残余收敛”模式读取运行证据，逐 Facet 判定已覆盖、未覆盖、UI 必测或抽查；记录证据，不按接口数量粗略删点。

## 文件约定

- 单接口模式：更新当前 API 的 `api-test-plan.md` 或项目已有测试方案文件，不另建测试点文件。
- 功能残余模式：更新模块级功能测试方案中的测试内容，不另建测试点 Skill 或复制完整 API 测试方案。
- 保持项目既有方案章节和版式；表格结构严格遵守上述四列。

## 完成门禁

- 每项需求行为都有明确去向：接口测试点、UI/功能点、分层验证或有依据地排除。
- 表格恰为 `序号 | 测试项 | 测试点 | 备注`，不通过备注承载核心预期。
- 每条测试点有触发条件/请求和确定结果；SQL/数据库结果不与需求口径冲突。
- 框架可行性不替代需求覆盖：API 可观察但当前框架未直接支持的测试点仍保留，并通过表格外适配说明交给自动化设计。
- 功能残余仅依真实执行证据收敛，未执行/失败的 API 不算覆盖。

本 Skill 不生成 SQL 文件、Workbook、数据初始化或 pytest 脚本。

## 实现契约

### 建议元数据

```yaml
name: api-test-plan
description: Create a single-operation API test plan whose test points are embedded in the required four-column test-content table, or reconcile evidence-backed API coverage into remaining functional tests. Preserve business coverage when automation support is missing.
```

用户指定一个 operation 且要设计接口覆盖时进入“接口方案”模式；用户提供了真实接口执行结果并要求收敛功能残余时进入“残余收敛”模式。不要因看到接口已写脚本就默认进入残余模式，必须检查执行状态和断言证据。

### 输入定位与停止条件

接口方案模式按顺序确认：

1. 用户指定的 API-ID/operation 与唯一权威接口分析文件；分析交接状态必须为可进入方案，或阻塞问题已有答复。
2. 当前需求、OpenAPI 和已确认问题；数据库/SQL 只用于解释该接口可观察的数据判据。
3. `测试代码知识图谱.md`：读取对应服务的客户端、Generator、Fixture、DB/Excel 能力；`测试脚本开发规范.md` 与 `代码编写规则.md` 读取模式选择、数据准备、断言和清理相关章节。
4. 读取一个与当前服务/接口模式匹配的真实方案样例，优先使用用户指定的四列表格样例。不要为了“完整”同时装载无关服务资料或重复读取整套规范。

以下情况停止定稿：来源版本冲突会改变预期；测试点所需业务口径未确认；API-ID 无法与 operation 唯一对应。可以交付明确标记为草稿的部分和需要用户决定的问题，不编造预期。

### 输出模板与追溯

保持项目方案现有封面/章节格式。新建方案可采用以下结构；已有方案只补缺失章节，不整体重排：

```markdown
# <operation>接口测试方案
## 一、测试类型
## 二、测试内容
### <测试项/模块名>
#### 预期目标
#### 测试内容
| 序号 | 测试项 | 测试点 | 备注 |
## 自动化适配说明（仅在存在非标准路径/阻塞时）
## 接口不可覆盖的功能点提示（仅在确有必要时）
```

每个测试点记录满足以下信息：

```text
【场景名】关键前置数据/状态；请求方法、参数或操作 → 可判定的响应字段/错误码/数据库副作用
```

来源编号放在备注（例如 `RSU`、需求条款或已确认问题），不加新列。若一个点使用多组等价值，注明代表值及等价范围；当预期、状态码或副作用不同，拆成不同序号。测试项按规则聚类，不能把多个独立业务结果塞进一个含糊测试点。

自动化适配说明只列非默认路径，每项用一行简记“测试点序号—API 可观察性—框架实现状态—后续处理”，例如：`序号 12：API 可观察；现有框架需扩展参数化 DB 校验；由自动化实施方案评估最小实现`。不要把“API 不可观察”作为框架支持状态；它是测试分层结论。只列有适配需要的点，不逐行重复“现有框架可实现”。

不要逐行重复声明“现有框架可支持”。此表不取代测试点，也不能把“需要扩展”改成“功能测试”。

### 残余模式门禁

按需求 Facet 关联 API 测试点；每个接口覆盖结论记录至少一个执行证据（报告/结果）和对应断言。只有实际通过、且断言测到同一行为面的 Facet 才标为已覆盖。失败、跳过、仅 `collect-only` 或计划中的测试均未覆盖。模块接口未全部完成时，仅输出标明 API 范围和未决接口的阶段性残余方案。

### 最终自检

- 方案只有一个 operation 范围；其需求行为均映射到接口表格、功能侧、分层检查或有来源依据的排除项。
- 表格标题严格为 `序号 | 测试项 | 测试点 | 备注`；序号无重复/无意外断号；测试项分组可读。
- 每个测试点的前置、请求/操作和预期可从该行确定；备注没有承担核心判据。
- 工程可行性与业务覆盖分开记录；适配说明仅列缺口，不扩充成第二份测试点表。
- 残余模式的每个“已覆盖”结论都有真实执行及同 Facet 断言证据。

### 交付后停止

完成接口方案或功能残余方案后，报告文档路径、范围、未决项和就绪状态，然后停止等待用户审核/修订指令；不自动调用 `api-test-automation-design`，也不自动把接口覆盖推断为功能残余已收敛。
