# Skill 设计：api-interface-analysis

## 目标

对一个 operation 建立可信的接口行为基线，找出真正需要用户决策的问题。此 Skill 结束时，后续测试方案可以直接使用已确认口径；不在这里生成接口测试点、SQL 预期或自动化代码。

## 适用范围

- 用户指定一个 API/operation，要求深度分析接口需求、契约和数据行为。
- 需要根据分析提出澄清问题，或把用户答复合入已有分析。
- 允许分析 BFF 与下游接口的调用关系，但交付范围仍限定在一个 operation。

不用于整模块接口清单盘点、功能测试点生成、测试方案/用例编写、造数或脚本实现。

## 输入

- 当前模块需求、相关变更及已确认答复。
- 指定 operation 的 OpenAPI/接口设计。
- 相关数据库设计、DDL、查询 SQL 和必要的字段/约束资料。
- 已有 `preanalysis/`、`reference-analysis/`、模块接口总览及同类接口分析（若存在）。
- 实现代码或运行现象（仅用于确认当前行为和识别差异）。

先复用已有分析定位范围；有历史复用回顾或用户指定历史资料时，按当前 operation 追读与行为、数据路径或边界相关的原文件/函数，并在分析中记录实际来源、定位及适用边界。只深入相关资料，不把所有历史文件无差别搬入输出；没有历史资料不因此阻塞。对作为规则依据的源文件应读到足以确认完整语义；若输出被截断，继续读取未覆盖部分。

`测试代码知识图谱.md`、`测试脚本开发规范.md` 和 `代码编写规则.md` 不作为业务契约的常规输入。只有当认证方式、测试数据获取、响应观察能力等会影响“此行为是否能由接口观察”时，才按需查看相关章节；不得因现有测试框架暂缺某个 helper 而改变或删减需求口径。

## 证据优先级

1. 当前需求和用户明确确认的行为。
2. 当前 operation 的接口设计/OpenAPI。
3. 数据库结构、业务查询 SQL 和已确认数据约束。
4. 历史参考与相似模块经验（识别沿用、变化和风险；只有当前需求、接口契约或用户确认支持的行为才作为当前预期）。
5. 实现代码、日志和运行结果（用于记录实现差异，不把现状自动当作预期）。

来源冲突应并列记录并说明影响；不得自行挑选一个来源覆盖其他来源。只有产品/用户能决定的问题才提问；能从现有材料确定的细节先自行查明。

## 执行步骤

1. 确认 operation、调用方、路径/方法、认证上下文及分析边界。
2. 从需求与已确认答复抽取本接口负责的可观察行为；识别不属于接口的页面行为，但不在此生成残余测试点。
3. 梳理请求字段、必填/校验、成功/错误响应、null/空集合、跨字段条件、排序分页和副作用；只记录来源支持的结论。
4. 追踪相关表和关键 SQL，说明参数如何进入查询/写入、数据关系和可能的空缺边界；不编造测试数据，也不在此新写最终 oracle SQL。
5. 对照 OpenAPI、需求、数据库和实现，形成“已确认口径 / 来源差异 / 待用户确认”三类结论。
6. 仅当存在阻断测试设计的业务决策时，提出精简问题；列出具体歧义、影响范围和需要用户决定的选项，不用泛问代替分析。
7. 用户答复后更新同一接口分析文档，保留已确认口径及问题状态；不另起相互矛盾的副本。

## 输出

每个 operation 的分析与专属问题单统一位于 `<module>/interfaces/<API-ID>-<slug>/`。已有旧分析按当前指定的 operation 迁移并保留内容，不复制权威文件。分析最小内容包括：

- 接口范围与来源清单。
- 请求、成功响应、错误响应和可观察行为。
- 业务数据路径/关键表、过滤/排序/写入关系。
- 已确认规则与边界。
- 来源差异、实现观察及风险（明确标记为观察，不是需求）。
- 待确认问题及答复状态。
- 指向后续测试方案的简短交接摘要。

每个接口维护 `clarification-questions.md`，没有待确认问题时明确注明；模块级问题沿用原 Q-ID，不重复登记。必要时补充接口级 Context Card 和 Data Closure；不强制创建新 manifest 或重复全模块分析。

## 完成门禁

- 一个 operation 的输入与边界清楚，相关需求/契约/数据路径没有关键未读来源。
- 所有作为结论的关键行为都有依据；事实、用户决策、SQL 推导和实现现状可区分。
- 待确认问题是测试预期无法自行决定的真实问题；没有未答问题时明确标记可进入方案设计。
- 未输出测试点、查询 oracle、用例、代码或臆测的实现预期。
- 工程规范未被当作需求事实；如发现测试环境能力限制，只登记为后续实现风险。

若关键业务问题仍待答，输出阻塞项并停止下游定稿；允许保留有明确范围标记的分析草稿。

## 实现契约

### 建议元数据

```yaml
name: api-interface-analysis
description: Analyze and clarify one specified HTTP API operation using its requirements, API contract, and relevant data model; update the interface analysis and open only decision-level questions. Do not generate test points, test plans, or automation code.
```

触发条件是用户明确选择一个 operation 并要求理解接口行为/澄清问题。用户只要求测试点、自动化方案或代码时，不重复运行本 Skill；引用已有且有效的分析即可。若用户给出多个 endpoints 但未指定本轮目标，不把它们悄悄合并成一次深度分析，应先完成已明确的目标或询问范围。

完成分析文档和问题清单后立即停止，不自动生成接口测试方案。若存在待用户决定的问题，等待答复；若已就绪，报告可进入测试方案阶段并等待用户明确审核/继续指令。

### 输入发现顺序

1. 优先使用用户传入的路径、operation/path/name 和本轮答复。
2. 从模块现有接口总览或接口分析索引确认 API-ID 与 operation 的唯一映射。
3. 从现有 `preanalysis/`、`reference-analysis/` 和 endpoint 文件中定位相关需求段、确认答复及复用边界。
4. 读取该 operation 的 OpenAPI/接口设计、相关 DDL/数据库设计/SQL；只读取必要实现证据来识别偏差。
5. 若存在多个可能的 operation、需求版本不明或来源冲突会改变预期，暂停定稿并记录问题；不按文件名猜测当前版本。

测试工程的三个规范不是每次都加载的业务输入。若需判断某项行为是 API 可观察还是纯 UI 行为，只读取知识图谱/规范中的相关能力段；记录“能力观察”，不能把它升级为需求口径。

### 分析文档最小结构

接口分析优先采用以下结构；已有文档能够清晰承载这些内容时可沿用，不适用的章节可省略或合并：

```markdown
# <模块/API 名称>接口分析
> operation：<HTTP method + path + operationId>
> 分析状态：<ready/blocked>

## 1. 接口定位与结论摘要
## 2. 分析范围与依据
## 3. 请求与接口契约
## 4. 业务规则与数据处理流程
## 5. 响应字段与结果分支
## 6. 职责边界与副作用
## 7. 来源差异、假设与待确认问题
## 8. 测试方案交接
```

来源部分应能定位到文件和相关章节/operation；不要求逐行摘要所有输入。接口专属问题正文维护在同目录问题单中，使用 `Q-001` 等稳定编号，记录歧义、依据、影响、需决定内容和状态；无待确认问题时明确注明。分析文档仅摘要影响并链接问题单。答复后更新同一问题和分析，不另建答案副本。

### 文件定位、完成标记与验证

- 接口分析写入 `<module>/interfaces/<API-ID>-<slug>/interface-analysis.md`，问题单及必要的接口级卡片放在同一目录。旧 endpoint 存在时仅迁移当前指定接口，更新原索引及链接；保留一个权威副本。
- 文末明确 `测试方案就绪：是/否`；为“否”时列出阻塞问题，为“是”时说明关键口径已确认。此短交接字段不替代问题正文。
- 输出前核对：operation/path 未串接口；请求/错误/成功/空值语义有来源；DB 路径符合表关系；实现差异明确标注为观察；Q 只保留需用户裁决的问题；没有生成 ATP、Excel、SQL oracle 或代码。
- 若输入完整但存在业务未决，交付分析和问题清单即可，不把 Skill 状态伪装为完成；用户答复后复跑受影响部分并更新同一文件。
