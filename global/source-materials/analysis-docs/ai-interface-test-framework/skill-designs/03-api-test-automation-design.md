# Skill 设计：api-test-automation-design

## 目标

在接口测试点审核后、任何编码或业务数据写入前，产出两项可审核设计：

1. 独立 SQL 核对材料（适用时）。
2. 说明数据、Excel 和脚本如何在现有测试工程落地的自动化实施方案。

该 Skill 把“预期怎么算”与“工程上怎么实现”一次设计清楚，但不写入测试代码/Workbook、不创建业务数据，也不把实施计划当成执行结果。

## 输入

- 单接口分析、问题清单及已确认答复；阶段性推进时标明尚未澄清问题。
- 已审核的接口测试方案和四列表格测试点，或用户明确同意阶段性推进的已审核部分。
- 数据库设计/DDL、相关既有 SQL、字段与约束。
- 测试工程 `AGENTS.md`、代码规则、脚本规范、知识图谱及自动化覆盖范围。
- 数据、执行和清理行为相似的有效实现；存在历史复用回顾或用户指定参考时，用其定位相关候选并核验实际源文件，不为凑数量读取无关样例。
- 当前仓库状态及用户已有修改。

只读必要规范和相似样例，引用其实际路径；不把规范全文或所有相似模块复制到产物。

测试点的自动化适配说明是设计输入，不是删点授权。对 API 可观察但当前框架未直接支持的测试点，应评估纯 Python、现有 Generator/DB 能力或最小合规扩展；不可行时明确阻塞和代价，等待用户决定，不能静默改成未覆盖或删除。

## 执行步骤

### 1. 固定设计边界

核对唯一 API、已审核范围、测试点序号及测试内容表格。用户明确同意阶段性推进时，可先设计预期明确、与未决问题无关的已审核测试点；受影响或未审核场景保留原问题链接、影响范围和恢复条件，不自行补业务口径，也不视作已覆盖。

### 2. 先形成独立 SQL oracle

根据已确认需求、接口契约、表结构和测试点推导 SQL，不把待测 Service/Mapper SQL 直接复制成预期。

- **查询接口**：按请求参数独立计算可比较的响应数据，明确字段、过滤、空结果及排序规则。
- **写接口**：按需要查询请求前状态、请求后持久化结果、幂等或副作用；HTTP 响应中无法由 DB 独立证明的字段仍按接口契约断言。
- **不适用场景**：若该 API 没有合理的数据库 oracle，或 SQL 无法增加独立判定价值，在自动化方案中说明原因，不为形式而编造 SQL。

SQL 应只读、参数明确、符合目标数据库方言，不使用 `SELECT *`，不依赖固定环境数据。时区、排序、版本、测试数据唯一键等会改变结果的前提必须明示。若可安全使用只读测试库，可执行查询验证；不能连接或执行时明确报告未验证，不暗示通过。绝不在本设计阶段执行 INSERT/UPDATE/DELETE。

### 3. 用 SQL 和测试点设计自动化实施方案

方案只写实现所需的决策，不复述整份需求。至少明确：

- 实施范围、正式脚本/Workbook/初始化材料的目标路径及计划修改/不修改文件。
- 每组测试点的范围（用四列表格最终序号、测试项、简短测试点引用）、数据闭包和分组理由。
- 采用现有业务造数函数、共享初始化 Workbook/fixture、或少量单用例增量的选择及其数据所有权/清理责任。
- Excel Sheet/用例行计划，以及每类用例直连的处理函数/generator。
- pytest 入口、动态预期如何从独立 SQL 移植为正式测试代码中的参数化查询、响应与 DB 断言边界。
- 每条用例如何独立执行，fixture 与 generator 分别创建/清理什么；DB 写入测试的串行和重复运行要求。
- 按场景组的实施顺序、Excel/语法/收集/集成/残留验证门禁及失败归类。

数据设计优先用最小闭包支撑多个同类测试点，同时每条用例独立执行。固定基线与单用例差异必须区分；记录精确清理键、外键逆序和失败路径清理方式。任何共享数据必须确认隔离，不依赖未登记环境样本。

### 4. 评审后交接

待用户/负责人审核 SQL 和自动化实施方案后，标记可实施。方案未审、关键数据源未确认或清理责任不明时，不进入实现阶段；允许先提交明确标记的阻塞项。

## 输出

在当前 operation 目录沿用既有文件，不复制重复版本：

- `api-query-oracle.sql`：独立、只读的核对 SQL；如不适用，在方案中说明，不创建空文件。
- `api-test-automation-plan.md`：紧凑的实施规格。建议含“依据与范围、SQL/预期策略、场景组映射、数据准备与清理、Excel/脚本结构、实施顺序与验收”六部分。

场景组映射至少支持从测试点序号追到数据策略、Workbook 行、处理函数、pytest 断言和清理责任。方案复杂度按接口实际复杂度决定，不追求和某个历史长方案同样篇幅。

## 硬边界

- 独立 SQL 和自动化方案按顺序由本 Skill 完成；不新增 SQL 专用 Skill。
- 不创建真实数据、不保存/回写 Excel、不修改 Python 或 Java、不执行写库操作。
- 正式脚本不能运行时读取被忽略的 `test_dependent_file` 或其他设计文档路径；需要的 SQL 逻辑须在实现阶段以参数化方式纳入正式测试代码。
- 不要求新增 fixture、helper、Sheet、控制列或 Workbook；每项新增都要有明确业务/工程收益。
- 方案不能改变测试点预期；发现预期缺口则退回 `api-test-plan`。

## 完成门禁

- SQL oracle 与需求/用户确认一致，参数、字段、过滤、排序、空值和副作用判据明确；不适用时有简短理由。
- 本轮每个已审核的自动化测试点都能追到数据、用例、处理函数/脚本断言和清理责任；范围外事项保留待续记录。
- 共享数据不会使单条用例依赖其他用例；新增文件和代码职责符合测试工程现状。
- 设计方案明确实施顺序与验证层次，且未越界写代码或业务数据。

## 实现契约

### 建议元数据

```yaml
name: api-test-automation-design
description: Design the independent SQL oracle when applicable and the implementation plan for one reviewed API test plan. Specify data closures, Excel and pytest mapping, fixture ownership, cleanup, and validation without changing code or data.
```

仅在一个 operation 的测试方案或用户明确同意先推进的部分已审核后触发。只为本轮预期明确、已审核的范围设计 SQL 和实施方案；被未决问题影响的场景先回到分析/测试方案，API 范围不明确时停止。阶段性结果不代表整个接口完成。

按“独立 SQL（适用时）→ 自动化实施方案”的顺序完成本 Skill 的两项产物。二者完成后报告 SQL 是否适用、审核状态、实施方案路径及阻塞项，然后停止等待用户审核；不得自动写入测试数据、生成 Workbook/脚本或启动实现 Skill。

### 输入解析

1. 从单接口目录读取 API-ID、分析路径、测试方案和问题答复；确认本轮已审核测试点序号与测试项唯一、固定，并记录范围外测试点及尚无测试点的未决问题。
2. 按方案中的 operation 找到精确 OpenAPI operation、请求响应 schema 以及 DB 表/SQL 文档；不使用相似接口的 SQL 代替本接口 oracle。
3. 进入测试代码仓库后，读取该路径的 `AGENTS.md` 规则链、三份测试工程规范的相关章节、目标服务 client/conftest 和实际相关的相似实现。按需参考历史复用回顾，核验拟复用函数的写表、返回值、副作用和清理责任；确认当前工作区是否有用户修改。
4. 当自动化能力或数据闭包依赖尚未确认的账号、数据库环境、mock、服务开关时，标为实施前决策；不猜环境状态。

### 输出模板

`api-query-oracle.sql` 仅适用时创建，文件头至少包含 operation、参数、输出字段/副作用、数据库/时区假设、只读声明和执行方式。SQL 本体应可独立复核；不得用其执行任何写操作。若不适用，在实施方案的 Oracle 章节标明 `不适用`、原因及 API 响应预期的替代验证来源。

`api-test-automation-plan.md` 保持适合本接口复杂度，建议采用以下结构：

```markdown
# <API-ID> <operation> 自动化实施方案
## 1. 范围、依据与假设
## 2. SQL oracle 与动态预期策略（不适用时写明原因）
## 3. 场景组到数据/用例/代码的映射
## 4. 数据基线、单用例增量与清理责任
## 5. Workbook、脚本及 fixture 计划
## 6. 文件修改清单与实施顺序
## 7. 验证门禁、风险与阻塞项
```

第 3 节映射建议使用以下列；它是自动化映射，不是测试点表格，不得替代/复制测试方案：

| 场景组 | 测试点序号 | 数据闭包/准备方式 | Workbook 用例/处理函数 | pytest 断言/清理 | 计划状态 |
|---|---|---|---|---|---|

### SQL 与实施方案的审核动作

- 查询接口：检查请求参数是否参数化、SQL 是否返回需要对比的字段、排序是否确定、空结果语义是否与接口契约一致。
- 写接口：检查 SQL 是否能验证写前/写后状态、重复请求/幂等及清理边界；响应字段仍由接口契约独立断言。
- 有稳定动态数据（例如自增 ID、服务端时间）时，标明如何从请求/DB 返回值计算，不将固定样本硬编码成环境依赖。
- 交叉检查本轮每个已审核测试点都有场景组映射，范围外测试点和未决问题已标为待续；每个初始化对象有 owner 和删除键；每个 generator 的职责与 Excel 路由方式符合现行规则。
- 对用户工作区现有修改仅列入审阅，不覆盖、不格式化无关文件；实施方案中的修改清单不得含“顺便重构”。

### 阻塞与交接

阻塞分两类并注明影响序号：

- **业务阻塞**：SQL/预期取决于未知业务口径，返回 `api-interface-analysis` 或 `api-test-plan`。
- **工程/环境阻塞**：实现需要未批准的框架变更、DB 身份不明或安全环境不可用；自动化方案列出最小解法和待决事项，不擅自造数据或改配置。

完成交接时写明 SQL 状态（`ready` / `not-applicable` / `blocked`）、实施方案评审状态，以及允许进入的 operation、测试点和文件范围；阶段性 SQL 状态仅适用于所列范围。未审核方案不能作为 `api-test-implementation` 的前置通过条件；后续问题确认后修订受影响的测试方案、SQL 和实施方案并重新审核。
