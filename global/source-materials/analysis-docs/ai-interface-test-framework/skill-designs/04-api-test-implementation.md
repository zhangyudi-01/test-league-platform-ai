# Skill 设计：api-test-implementation

## 目标

按已审核的接口测试点、SQL oracle 和自动化实施方案，把一个 operation 落成独立可执行的数据库准备、Excel 接口用例和 pytest 脚本。实施以相近场景组为节奏，但数据、用例和代码在同一组迭代中同步完成。

## 前置条件

- 当前 operation 的接口分析和测试方案中本轮场景已审核、预期明确；其他业务问题尚未确认时，须经用户明确同意阶段性推进，且不得影响本轮场景。未决口径不能由编码阶段猜测。
- 独立 SQL oracle（适用时；不适用理由已记录）与自动化实施方案已审核，且定义了数据闭包、初始化/清理和目标文件。
- 当前目标为受控测试环境；如配置指向生产或环境身份不明，停止任何写入型测试。
- 自动化实施方案中框架能力缺口已有审核结论；未批准的扩展不得临时塞进本次实现。

输入包含测试工程 `AGENTS.md` 和现行测试规则；每次任务仍需按目标路径读取规则链、检查 Git 状态，不能假定参考文档或用户修改未变化。

## 执行步骤

### 1. 实施前核对

核实当前 operation、方案版本、Git 未提交改动、目标 DB 环境和要改文件。有历史复用回顾或用户指定参考时，按已审核方案追读当前组拟使用的源文件；重新确认业务 helper 写表、返回 ID、共享数据副作用及恢复清理责任，不按摘要或函数名猜语义。实现与方案不符时暂停受影响组，修订方案并审核。

### 2. 按场景组纵向闭环

每组在自动化实施方案中对应一段明确测试点范围，并依次闭环：

1. **数据准备**：按方案建立本组最小数据闭包；复用已验证的造数函数，或按方案维护初始化 Workbook/fixture；需要单例差异时仅创建本用例数据。
2. **Excel 用例**：同步添加本组执行行，保持既定 Sheet/列/类型和工作簿约定；每条用例说明自身目的、关键前置和预期，处理函数映射到稳定业务 generator。
3. **pytest 代码**：在同一接口脚本中实现对应 generator/断言；从当前请求参数动态定位数据，使用参数化 SQL 构造预期，验证 API 响应或必要 DB 副作用。
4. **清理与验证**：用例和 fixture 只清理各自拥有的数据；异常路径也能清理；独立执行每条用例并检查结果及残留。该组通过后再进入下一组。

按项目规则使用 `xlsxwriter` 写 Workbook，并用项目实际读取链路（如 `pylightxl`/`ExcelReader`、`api_test_data()`）验证。若目标仓库规则有更新，以当前规则为准，不硬套历史 Excel 样例。

### 3. 维护实施映射

同步更新 `api-test-automation-plan.md` 中该组的实际状态：代码/Workbook 路径、用例行、generator/测试函数、数据清理和验证结果。区分计划、静态检查、Workbook 解析、pytest 收集、真实接口执行和清理检查。

若实施发现缺失业务规则、预期矛盾或需新增测试点，暂停该组，回到分析/测试方案修订，经确认后再继续；不得在代码或 Excel 中私自改变接口预期。

若方案中的 API 测试点因工程能力无法落地，保留该测试点和覆盖缺口，报告最小可行扩展或替代验证路径；不得通过删除用例、跳过用例或把 API 可观察行为误标为 UI 行为来绕过。

对用户明确要求核查的延期问题，可在安全的测试环境内进行受控探索性调试；实际结果回填原作用域的问题清单，记录条件、结果和脱敏证据。只有用户确认或权威契约更新可以决定业务预期；单次实测仅作实现观察，不能自动关闭问题或判定通过。确认后同步受影响的分析、测试方案、数据闭包、SQL 和实施映射；实质性变化先审核再执行，不自动扩展本轮范围。

## 实现约束

- 默认一个 operation 一个脚本和对应工作簿；场景组写入同一套目标产物，不按用例拆脚本。
- Excel `处理数据` 直接选择稳定、可读的业务 generator；不增加按标题/场景 Key 的总路由。
- 共享 fixture 仅承担方案定义的稳定基线；单用例数据和断言留在对应 generator/用例路径。
- 每条用例都可单独执行、可重复执行；不得依赖前一条用例写入的数据或测试环境残留。
- 数据清理只按本测试创建的精确键进行；共享数据、单例增量和 helper 数据的所有权不能重叠误删。数据库写入用例按规范串行执行。
- 只做方案批准的文件改动；未经需要不改公共 client、配置、业务实现、其他 API 脚本或用例 Workbook。
- 业务 SQL 文档是独立核对材料，不是运行时文件依赖；正式测试代码中只使用经过审核的参数化 SQL。

## 验证顺序

对每个场景组根据适用性完成并分别报告：

1. Python 语法/静态检查。
2. Workbook 读取验证和关键行核对。
3. pytest 收集验证，确认新增用例实际被收集。
4. 目标测试环境中的单条用例执行；DB 写入用例串行运行。
5. 代表性用例重复执行及专用数据残留/清理检查。

后续组依赖前组 fixture 或代码时，可先做局部静态/收集验证；接口真实覆盖状态须等关联用例在目标环境执行通过后再登记。禁止把静态检查或 collection-only 描述为接口测试通过。

## 失败处理与结束标准

失败先按接口契约、测试数据、脚本/Workbook、环境和被测实现分层取证。只有证据表明方案或业务口径本身有误时才回到上游修订；不为了让测试变绿而改正确预期。

完成时应能从本轮每条测试点追踪到 Excel 用例、数据准备、pytest 断言和清理责任；范围外事项保留待续记录。目标范围验证状态真实、所有专用数据无意外残留、Git diff 仅含批准范围，并按当前测试工程规则完成结构复核。未能执行真实 DB/API 时明确列为未验证。

## 实现契约

### 建议元数据

```yaml
name: api-test-implementation
description: Implement one reviewed API automation plan one scenario group at a time, synchronizing its data preparation, Excel cases, pytest generator/assertions, cleanup, and execution evidence.
```

仅在用户要求编写/继续指定 operation 的接口自动化时触发。若只要求审阅自动化实施方案，不改测试代码；若方案未审核，不自行开始创建数据、Workbook 或脚本。

默认一次只实施一个已审核的场景组。该组的数据、Excel、代码、验证和清理状态回填完成后，报告修改与验证结果并停止等待用户审核/继续指令；不得自动开始下一组。只有用户明确要求一次完成指定的多组时，才可继续批量推进，并仍需逐组更新状态、验证和报告。

### 输入与目标定位

1. 从自动化实施方案中的 API-ID/operation 读取唯一的接口分析、测试方案和本轮范围的 SQL oracle 状态（`ready` 或 `not-applicable`）。校验方案中的文件清单、数据闭包和场景组映射存在；阶段性推进须有用户明确同意并保留范围外问题与测试点的待续记录。
2. 按计划文件清单定位脚本、Workbook、初始化材料及 conftest；如果仓库实际结构与计划不符，先修订/确认计划，不猜另一个目录。
3. 读取所有目标路径适用的 `AGENTS.md`、`代码编写规则.md`、`测试脚本开发规范.md`、`测试代码知识图谱.md` 中相关章节，并按实际需要检查相似实现和拟复用 helper 源码。避免把上游方案或历史回顾中描述的模式当作当前仓库现状。
4. 执行 `git status --short` 并记录修改前状态；保留用户已有改动。执行 DB 写入测试前确认测试环境身份；目标是生产环境、身份不明或清理风险不可控时停止写入型操作。

### 场景组闭环与可恢复状态

每个场景组使用测试方案最终序号作范围标识，按以下顺序完成；同一组的数据准备、Excel 行和 pytest 代码是一项联合交付：

1. **复核数据闭包**：从请求参数和已审核 SQL 推导本组所需行。确认现有 builder 的实际表落点、返回值、唯一 ID 和清理能力；按方案选共享基线、初始化 Workbook 或单用例差异数据。
2. **实现准备和清理**：只实现方案批准的初始化入口；记录精确 owner/主键/外键清理顺序。共享 fixture 只准备共享基线，单用例的特殊行由对应业务 generator 负责；异常路径仍可靠清理。
3. **同步工作簿与代码**：在指定 Sheet 追加本组用例，再在同一 operation 脚本实现对应业务族处理函数、请求后断言和动态预期。每条用例单独运行时自行获取其必要 ID，不依赖别的用例顺序或全局环境残留。
4. **联合复核**：逐行比对测试点、Excel 参数/预期、处理函数、SQL 断言和清理对象；新增/修改 Workbook 时使用当前规范要求的工具写入并通过项目读入链路验证。
5. **验证并登记**：先做静态检查、Workbook 读回和 pytest 收集，再在已确认的目标测试环境中串行执行该组适用用例；检查失败清理和专用 ID 残留。将组状态及结果回填到自动化实施方案后，才进入下一组。

场景组状态使用简单值：`planned`、`in-progress`、`static-validated`、`collected`、`integration-passed`、`failed`、`blocked`。只有 `integration-passed` 可作为接口覆盖证据；其余状态保留缺口。

### 失败、暂停和恢复

- **业务预期不确定/矛盾**：停止受影响组，保留已完成且不受影响的组；把实际调试观察回填原问题清单，不能把实测自动提升为业务预期；回到分析或测试方案，取得确认和受影响方案审核后再继续。
- **工程规则与自动化方案冲突**：暂停编码，更新自动化方案并审核；不以临时代码绕过规则。
- **环境或写入安全不明**：不执行数据库写入；可完成不涉及写入的静态、Workbook 和收集验证，并把集成状态标为 `blocked`。
- **实现或测试失败**：先依据响应、独立 SQL、数据库快照和日志区分测试代码/数据/环境/被测实现；不得为了通过而弱化正确 oracle。
- **用户要求暂停/先 review**：当前组完成或安全停在可恢复点，报告未完成序号、修改文件和下一步，不自行跨入下一组。

### 完成报告模板

完成或暂停时至少报告：

- API-ID/operation 和本次完成的测试点序号/场景组。
- 新增/修改的脚本、Workbook、数据材料及 fixture 路径。
- 各层验证结果：静态、Workbook、收集、真实接口/DB、清理；未运行项明确写未验证及原因。
- 未通过/阻塞项及其证据分类。
- 修改前已有的用户改动是否保持；最终 diff 是否限于批准范围。

不可把 `pytest --collect-only`、SQL 静态审阅或生成成功表述为接口通过。
