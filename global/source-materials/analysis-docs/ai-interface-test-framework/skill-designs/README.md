# 接口测试 Skills 设计文档

> 状态：设计稿，用于后续编写实际 Skill；本文档本身不是可直接调用的 Skill。

## 流程

| 顺序 | Skill | 主要产物 | 交接条件 |
|---|---|---|---|
| 1 | [`api-interface-analysis`](./01-api-interface-analysis.md) | 单 operation 接口分析与待确认问题 | 关键业务问题已回答，或明确标记阻塞；输出后停止，等待用户答复/审核 |
| 2 | [`api-test-plan`](./02-api-test-plan.md) | 含接口测试点的测试方案 | 测试点可独立准备、触发和判定；输出后停止，等待用户审核 |
| 3 | [`api-test-automation-design`](./03-api-test-automation-design.md) | 适用时的独立 SQL 核对材料、自动化实施方案 | SQL（如适用）与实施方案经审核，允许进入实现；设计完成后不自动启动实现 |
| 4 | [`api-test-implementation`](./04-api-test-implementation.md) | 数据初始化、Excel 用例、pytest 脚本和验证结果 | 默认每次闭环一个场景组，完成后停止等待审核/继续指令 |

每轮单接口流程只处理一个 operation；接口执行后的模块级功能残余收敛是 `api-test-plan` 的后续模式。复用已有模块需求分析、历史参考和接口分析，不复制整套材料。四个 Skill 不要求实现复杂调度器、通用代码生成器或额外的 Skill 管理框架。

### 测试工程规范的分阶段输入

测试工程规范用于判断如何验证和实现，不是业务预期来源。按阶段加载，避免分析阶段被工程细节拖重，也避免测试方案遗漏无法落地的问题：

| 阶段 | 规范读取约定 |
|---|---|
| `api-interface-analysis` | 不默认通读三份规范。只有认证、数据获取、响应/副作用可见性等影响 API 可观察性的部分，才按需查阅并标为工程能力观察。 |
| `api-test-plan` | 读取目标服务与测试类型相关章节，检查测试点能否由 API 观察、现有框架能否直接实现；两者分开记录。框架不支持不能删掉 API 可观察的测试点。 |
| `api-test-automation-design` | 读取自动化设计所需的规范章节与相似实现，设计数据、Excel、脚本路由、断言和清理的落地方式。 |
| `api-test-implementation` | 在目标代码仓库和目标路径重新读取当前适用的规则链与规范，不能只依赖上游摘要或旧样例。 |

### 阶段审核门禁

每个 Skill 只完成自己的职责。产物完成后说明 `ready`、`blocked` 或部分完成状态及证据，然后停止等待用户审核、补充或明确的下一步指令；不得因上游产物刚生成就自动调用下一个 Skill。`api-test-implementation` 默认一次只闭环一个场景组；只有用户明确要求批量完成已审核的多组时，才可连续推进。

## 测试内容表格

接口测试方案的测试内容表格固定沿用项目格式，始终保持四列；不增加测试点 ID、优先级等列：

| **序号** | **测试项** | **测试点** | **备注** |
| --- | --- | --- | --- |
| 1 | 请求参数校验 | 【缺失必填参数】准备有效业务数据，请求缺少 `<参数>` → 按已确认契约返回 `<可判定响应>` | 来源/边界补充 |

- `序号`：按最终方案顺序编号；自动化实施方案用“序号 + 测试项 + 测试点简称”引用，不要求再造一套 TP 编号。
- `测试项`：归纳一组相关业务规则；同一组后续行可按参考文件留空，表示沿用最近一个非空测试项。
- `测试点`：尽量用一句写全前置数据、请求条件/动作和可判定预期；不可把核心预期藏在备注。
- `备注`：只放来源编号、范围说明或补充边界；不重复测试点，也不承担缺失的业务判据。
- 一个测试点应能独立准备、触发、判定并定位缺陷。只有确实具有不同输入、风险或预期时才拆多行，不按“正向/边界/异常”机械扩行。

表格依据：`tests/test-league-platform/testsuites/data-bff/match_monitoring/test_dependent_file/草稿接口测试方案.md`。

## 公共原则

- 需求和用户已确认的口径决定预期；OpenAPI、数据库/SQL 用于补齐契约和独立验证；实现代码用于发现差异，不替代需求。
- 一个 operation 一份方案、一个自动化实施方案、一个测试脚本和对应工作簿；有真实复用时才共享模块级数据 fixture/helper。
- 工程可实现性在 `api-test-plan` 阶段核对，但与业务可测性分开：框架暂不支持只产生适配/扩展事项，不得据此删减 API 可观察的测试点。
- 只改当前 operation 的目标文件；尊重现有 Git 修改和项目既定目录/Workbook 格式。
- “已计划、已写代码、已收集”不等于接口覆盖；只有目标环境实际执行通过且断言覆盖同一行为面，才登记为已覆盖。
- 若新证据改变业务口径，回到对应分析/方案阶段修订并复核下游，不在实现阶段静默改预期。

## 实施为 SKILL.md 的标准

这四份文档是可实现规格，不是要求逐字复制成四份长 `SKILL.md`。实现时每个 `SKILL.md` 至少应包含：

1. 可区分的 `name`/`description` 和触发/不触发边界。
2. 当前阶段要读取的输入、优先级、来源路径发现顺序及前置检查。
3. 按阶段执行的操作流程、主要输出路径/模板、交接条件和停止条件。
4. 本 Skill 特有的质量检查和不能越过的业务/写入边界。

只有输出模板或规则足以明显撑大入口文件时，才拆到 `references/`；在 `SKILL.md` 写清何时读取。不要复制测试工程规范全文，也不要创建空的 `scripts/`、`agents/`、示例或 manifest。实际 Skill 的实现验收至少包括格式校验，以及一条正常输入和一条信息缺失/阻塞输入的前向验证；验证输出行为，不只检查标题或措辞。

实现时必须保留阶段边界：分析 Skill 不能偷偷生成测试点；测试方案不能因框架欠缺而删点；自动化设计不写代码/不造数据；实现不能绕过已评审方案或静默改预期。每份 Skill 只携带改变该阶段决策的指令，共享规则留在本索引或必要的引用中，避免四份重复堆叠。
