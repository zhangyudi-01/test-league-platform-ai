# AI 接口测试辅助框架设计

## 1. 目标与核心决策

本框架将既有接口测试工作流整理为可追溯、可逐接口推进的过程：

> 需求与接口分析、问题澄清 → 接口测试方案（内含测试点）→ 独立 SQL 核对材料（适用时）→ 自动化实施方案 → 按场景组同步完成数据准备、Excel 用例和 pytest 脚本 → 执行验证 → 收敛接口测试后剩余的功能测试。

设计约束如下：

1. 以一个 OpenAPI operation 作为单次工作的接口范围；每个接口独立目录、一个自动化脚本和对应的接口用例工作簿，不要求一次完成模块内全部接口。
2. **测试点是接口测试方案的组成部分**，不另设测试点生成 Skill 或必须单独维护的测试点文件。
3. 测试方案之后先判断是否适用独立 SQL oracle；适用时先形成可复核 SQL，再据此和工程规范形成自动化实施方案。实施方案是编码前的设计关口，不与实际脚本实现混为一谈。
4. **用例、数据准备和脚本按场景组同步推进**。每组选取业务路径或数据构造相近的测试点，按自动化实施方案完成数据闭包、造数/初始化、Excel 用例行、可复用 generator/pytest 断言及清理后再进入下一组；不先批量生成所有用例，再隔离地编写所有脚本。
5. 功能测试在接口覆盖后收敛：接口无法观察的页面视觉、交互、自动刷新等行为保留为功能测试；接口已覆盖的规则只保留必要的页面一致性检查或少量关键路径抽查，不重复复制整套接口断言。
6. 接口测试预期以需求和已确认口径为准；适用时用独立 SQL 推导可判定的响应/数据库预期，实现代码仅作为差异证据，不反向替代需求。
7. 流程采用四个职责清楚的 Skill；SQL 与自动化实施方案由同一个设计 Skill 产出，不再拆成两个 Skill。暂不要求搭建复杂 Runner、Fork 调度或独立 Excel 转换器，是否自动化编排待纵向试点证明收益后再决定。
8. 需求覆盖与现有框架能力分开判断。框架限制可改变实现方式或形成待批准的扩展项，不能静默删除 API 可观察的测试点。

## 2. 适用范围与非目标

适用范围：以管理端 BFF/API 自动化测试为主，涉及需求、OpenAPI、数据库设计/查询 SQL、Excel 驱动用例、Python pytest、造数与清理。一个模块可有多个接口，但每次按用户指定的一个 operation 推进。

首个试点：`MOD-06-03 竞彩赛程监控`。该模块现有 `preanalysis/`、`reference-analysis/` 和模块级接口总览是有价值的上下文，应先复用和核对；已有单接口分析按指定范围整理到对应接口目录，保留内容与问题答复。不得把竞彩业务规则写死在通用 Skill 中。

非目标：替代产品决策、自动修改后端实现、把所有 operation 合成一个大脚本、要求每个接口都必须自动化，或重写现有功能测试 Skill 和历史测试产物。

## 3. 工作流

```text
模块需求 / 当前接口文档 / DB 与 SQL / 历史参考 / 测试工程规范
                              |
                              v
                 api-interface-analysis
                 单接口分析与问题澄清
                              |
                              v
                      api-test-plan
           单接口测试方案（方案内含完整接口测试点）
                              |
                              v
             api-test-automation-design
        先判断/生成独立 SQL 核对材料，再形成自动化实施方案
                              |
                              v
              api-test-implementation
                              |
     +---------------- 按场景组循环 ----------------+
     | 选一组相关测试点                              |
     |     -> 分析数据闭包与 SQL 预期                |
     |     -> 设计造数、初始化和可靠清理             |
     |     -> 写本组 Excel 用例行                    |
     |     -> 同步实现/复用 generator 与 pytest 断言 |
     |     -> 独立执行、验证并检查数据清理            |
     +-----------------------------------------------+
                              |
                              v
       更新模块接口覆盖台账（只登记真实执行证据）
                              |
                              v
 api-test-plan 的“功能残余收敛”模式：保留未被接口验证的功能点
```

### 3.1 阶段审核停点

每个 Skill 交付自己的产物后都应停止并等待用户审核、补充或明确的下一步指令；不得在同一次自动连续启动下游 Skill。接口分析可进入测试方案的状态不等于方案已获审核，测试方案完成不等于自动化设计获批，SQL/自动化实施方案完成也不等于允许写库或编码。实现阶段默认每次闭环一个场景组；只有用户明确要求批量完成指定多组时才连续推进。

### 3.2 场景组的同步实现约定

场景组用于组织工作，不改变用例独立执行要求。同组用例可复用相同业务造数函数或稳定 generator，但每条用例必须能独立准备自己的前置数据、调用接口、判断结果并清理，不依赖同组其他用例先运行或依赖环境残留。

每组按以下顺序闭环，不跨组囤积未实现内容：

1. 从已审核的测试点中选择数据关系或业务路径相近的一组，并明确每条用例要区分的风险和判据。
2. 根据接口查询 SQL、表关系和约束确定最小数据闭包；优先复用项目已有造数函数，必要时编写有明确表落点的初始化逻辑。
3. 一起完成该组的 Excel 用例行和 pytest 实现。Excel `处理数据` 绑定到稳定、语义明确的业务 generator；脚本负责调用、断言、必要的数据库核对和清理。
4. 单独运行该组中的每条用例，验证断言、数据初始化和清理；通过后再进入下一组。若实现暴露出测试点或数据设计问题，先修正并回写自动化实施方案中的映射，再继续。

最后将各组追加到同一个接口工作簿和同一个 operation 脚本中；不是每组新建一个脚本，也不是每条用例新建一个脚本。

### 3.3 状态与覆盖判定

接口状态保持精简：`not-started`、`analysis-in-progress`、`clarified`、`plan-reviewed`、`automation-design-reviewed`、`implementation-in-progress`、`locally-validated`、`integration-passed`、`failed`、`blocked`。按场景组记录实现进度即可，不另建复杂状态机。

模块覆盖台账以可观察行为面（Facet）为单位，而不是按测试点数量计算。只有目标环境中的接口用例真实执行通过，且断言确实验证了相同 Facet，才记为 `api-verified`；语法、导入、Workbook 解析或 pytest 收集成功都不能作为接口覆盖证据。

建议覆盖状态：`unmapped`、`planned-api`、`planned-ui`、`api-verified`、`ui-required`、`e2e-smoke`、`failed`、`blocked`。失败、未执行或仅计划的接口点不能用于删减功能测试。

## 4. 目录与产物

沿用模块已有的需求分析、历史参考和接口总览，不为了框架重复复制材料。在模块目录下按 operation 组织接口分析和后续方案：

```text
<module>/
  preanalysis/                         # 已有模块需求前置分析，按现有流程维护
  reference-analysis/                 # 可复用历史结论与适用边界
  interface-analysis/                 # 已有模块总览、索引及尚未迁移的历史分析
  api-coverage-ledger.md               # 模块级 Facet 覆盖与功能残余依据
  interfaces/                          # 单接口分析、方案与落地追踪；一个接口一个目录
    API-001-<operation>/
      interface-analysis.md            # 唯一接口分析
      clarification-questions.md       # 接口专属问题及答复
      context-cards/                   # 仅在确有接口专属复用需求时创建
      data-closures/                   # 仅在模块级数据闭包不足时创建
      api-test-plan.md                 # 测试方案 + 完整接口测试点
      api-query-oracle.sql              # 适用时：与接口实现独立的 SQL 核对预期
      api-test-automation-plan.md       # 数据闭包、Excel、脚本/generator、fixture、清理和验证设计
    API-002-<operation>/
      ...
```

单接口分析及问题答复统一位于 `interfaces/API-ID-<operation>/`，后续方案和自动化设计也沿用该目录。处理已有旧分析时，只迁移当前指定的 operation，同步更新模块索引和相对链接，保留原结论及答复；其他接口的旧文件不批量迁移。同一分析只能有一个权威版本。

正式自动化产物仍落在测试代码仓库现有规范位置：

```text
tests/test-league-platform/testsuites/<service>/<interface>/test_<operation>.py
tests/test-league-platform/data/<service>/接口测试用例_<业务>.xlsx
```

`api-test-plan.md`、适用时的 `api-query-oracle.sql` 和 `api-test-automation-plan.md` 是不同职责的审核产物：测试方案回答测什么，SQL 说明响应或数据库副作用如何独立核对，自动化方案说明如何在现有测试工程中落地。SQL 不适用时由自动化方案说明原因。方案中的“场景组实施映射”记录测试点范围、SQL 覆盖方式、Excel Sheet/用例标识、`处理数据` 对应的 generator、pytest 测试函数、数据初始化/清理入口及验证门禁。实际实现后可在该映射中回填代码路径和执行状态，不强制额外维护重复 manifest 或独立的用例 Markdown。若项目已有清单或文件布局，则优先按现状链接，不迁移已存在资料。

## 5. Skill 设计：四个 Skill

四个 Skill 的逐项设计、输入输出契约和质量门禁见[设计文档索引](./skill-designs/README.md)。

### 5.1 `api-interface-analysis`

**职责**：对一个 operation 深度分析“相关需求 + 接口契约 + DB/SQL + 必要实现证据”，提出真正需要业务确认的问题，并在用户答复后更新为可用于测试设计的稳定口径。

**输入**：模块需求及相关变更、指定 operation 的 OpenAPI/接口设计、数据库设计/DDL/查询 SQL、已有 `preanalysis/` 与 `reference-analysis/` 产物、必要实现代码。有历史回顾时追读与本接口行为、数据路径或边界有关的原文件/函数，记录来源和适用边界；没有时不因此阻塞。测试工程规范不是业务分析的常规必读输入；仅在认证、数据获取或观察能力影响接口可测性时按需查阅。

**输出**：单接口目录中的 `interface-analysis.md` 和 `clarification-questions.md`；按实际需要补充接口级 Context Card 或 Data Closure。分析包含请求/响应/错误语义、业务规则、边界、数据路径和来源差异，明确区分需求事实、用户决策、SQL 推导及实现现状。

**边界**：不生成独立测试点文件、不写 Excel 用例或 pytest 代码；不以实现现状取代需求预期；不扩展分析到其他 operation。可以复用模块级既有分析，不另造一套模块前置分析 Skill。

### 5.2 `api-test-plan`

**职责**：生成或更新单接口测试方案，**测试点直接包含在该方案中**；另提供模块级“功能残余收敛”模式，依据已执行的接口覆盖证据整理仍需功能测试的部分。

**单接口模式输入**：已澄清的单接口分析、相关需求、OpenAPI、DB/SQL 数据关系与预期口径、`测试代码知识图谱.md`、`测试脚本开发规范.md`、`代码编写规则.md` 的相关章节及相似有效案例。存在历史参考时按当前接口检查相关旧场景，以当前依据判断承接、变化或不适用。

**单接口模式输出**：一份可评审的接口测试方案，测试点至少明确：测试目标/风险、准备条件及关键数据状态、请求或操作、可判定的响应/数据库预期、需求/API/SQL 来源。测试点按独立判定风险划分，避免只写“正常/异常”标题或把核心 oracle 藏在备注。表格外可增加简短的自动化适配说明，但不得扩展四列表格或因现有框架限制删减需求覆盖。方案还标记需要视觉、交互或真实页面才能判断的 Facet，供功能残余阶段追踪。

**功能残余模式输入**：模块需求 Facet、各相关 operation 的测试方案和真实执行状态、接口断言覆盖证据、页面原型或交互需求。

**功能残余模式输出**：模块功能测试方案/测试点，仅保留接口无法验证的 UI/交互/自动刷新等行为；对于接口已经验证但需要人工确认页面映射的内容，设计少量、轻量的一致性或关键路径抽查，不重复复制全部接口规则测试。

**门禁**：模块最终残余点只能在相关接口状态均已明确后定稿。若用户只要求部分接口，允许输出有范围标记的阶段性结果，但不得声称其代表模块完整覆盖。只按真实通过且同一 Facet 的断言登记 `api-verified`。

### 5.3 `api-test-automation-design`

**职责**：在测试点审核通过后，先设计独立查询 SQL，再以该 SQL 为计算依据，形成可审核的接口自动化实施方案。它回答“预期如何独立计算、后续代码/数据/用例如何按工程规范实现”，不直接写入测试代码或数据库。

用户明确同意阶段性推进时，可以先设计预期明确、已审核且不受未决问题影响的测试点；实施方案须记录本轮范围、延期问题和恢复条件，SQL 与方案状态仅代表该范围，不代表接口整体完成。仅暂缓问题不等于已审核。

**输入**：已确认的接口分析、审核后的接口测试方案及测试点、数据库设计/DDL、接口查询 SQL 线索、测试工程规范、相似模块的有效实现和当前仓库状态。存在历史复用回顾时，由相关结论定位候选脚本/helper 并核验实际源码及清理责任。

**输出，按顺序生成**：

1. `api-query-oracle.sql`（适用时）：可人工独立执行、只读、参数明确的 SQL 核对材料。查询接口用它独立计算响应字段、过滤/排序和空结果；写接口用它核对请求前状态、请求后持久化副作用或幂等结果。只选该 operation 实际需要的核对方式，不要求 SQL 重算无法由数据库单独证明的全部响应字段；不照抄待测 Java 实现。需要时明确 SQL 的数据库版本、时区、输入参数和运行前提。若 SQL 不适用，在自动化实施方案中说明原因，不创建空文件。
2. `api-test-automation-plan.md`：实施规格，说明实施范围和文件清单、SQL 如何转成脚本内参数化动态预期（或为何不适用）、测试点到场景组/用例族的映射、数据闭包及共享基线/单用例增量、初始化与清理方案、Excel Sheet/列及处理函数分族、fixture 职责、脚本入口和断言边界、不可修改文件、实施顺序、验证/执行/清理门禁及失败归类。

**顺序约束**：先完成并审核查询 SQL，再根据 SQL 和测试点定自动化实施方案；实施方案不能先假设尚未验证的 SQL 口径。用户审核实施方案后，才进入数据、用例和脚本实现。

**边界**：不在 SQL 或实施方案阶段创建/更新业务数据，不生成实际 Workbook/Python 实现，不把设计计划伪报成执行结果。SQL 文件供人工独立核对；运行时测试代码不得依赖被忽略或仅供分析的文档目录，应将审核后的查询逻辑以参数化方式实现/维护在正式测试代码中。

**不再细分**：独立 SQL 和自动化实施方案前后依赖紧密、共同服务编码前设计审查，因此由本 Skill 顺序产出；不另设 SQL 生成 Skill。

### 5.4 `api-test-implementation`

**职责**：把已审核的接口测试方案按场景组落地；在同一轮迭代中完成测试数据准备/初始化、Excel 用例和 pytest 脚本，不拆成“先写完全部用例、再统一写脚本”的两个阶段。

**输入**：单接口分析、已审核接口测试方案及测试点、已审核的独立 SQL oracle（适用时，或实施方案中注明不适用）、已评审的自动化实施方案、测试工程的测试脚本开发规范/代码编写规则/测试代码知识图谱/API 覆盖清单，以及实际相关的相似实现。存在历史参考时按场景组重读拟复用源码，复核共享数据副作用、恢复与清理；实现与已审核方案不符时暂停并修订方案。

**输出**：测试代码仓库中的接口工作簿和一个 operation 脚本；需要时增补最少量的 generator/conftest 代码；自动化实施方案内同步维护场景组到 Excel 行、代码和运行结果的映射。

允许在用户明确同意的阶段性范围内实现已审核场景。实际核查延期问题后，把条件、结果和脱敏证据回填原问题清单；仅有实测时保留为实现观察，不自动代替需求或关闭问题。用户或权威契约确认后，同步受影响的分析、测试点、SQL 和实施方案，实质变化经审核后再继续，未验证场景不能标为已覆盖。

**实现约束**：

- 先检查现有脚本和 helper 的业务语义、真实表落点、返回 ID、清理副作用，再决定复用或补充；不因函数名称相似而假定其适用。
- 按 SQL 构造预期数据和结果；测试数据要能区分目标分支，不能只构造“看起来像”但无法触发查询条件的数据。
- Excel 的处理函数直接映射稳定业务 generator；遵循现有 Sheet、`api_test_data()`、`CaseDict`、client 和前后置风格，不增加总路由或重复控制列。
- 每条用例单独可执行、可重复运行；写库数据精确清理/恢复，异常路径使用 `try/finally` 等可靠机制。必要时串行运行数据库写入用例，并重复代表用例检查残留。
- 只在当前 operation 脚本内按真实复用关系抽取代码；避免为了框架统一而新增通用层、过多 fixture 或额外 Excel Sheet。
- 按项目已有工具写入和读取 Workbook：当前接口自动化工作簿使用 `xlsxwriter` 写，并使用 `pylightxl`/`ExcelReader` 及 `api_test_data()` 路径读回校验。已有 `testcase-excel-converter` 面向另一类 Markdown 功能用例，不直接替代接口工作簿生成和验证。
- 分层报告验证结果：静态检查、Workbook 读回、pytest 收集、真实 DB/API 集成执行；不得把前几项说成接口测试通过。

## 6. 测试点、SQL、用例、数据与代码的关系

测试点是风险与判据的设计单元；独立查询 SQL 是成功响应的计算 oracle；自动化实施方案是编码前的工程映射；场景组是造数和编码的组织单元；Excel 行是可执行用例输入；pytest 函数/generator 是执行实现。它们相互追溯，但不是一一对应：一个测试点可拆成多个独立用例，一个 generator 可服务同一数据路径下的多条用例。

建议最小追溯关系：

| 层级 | 标识示例 | 需要追溯到 |
|---|---|---|
| 接口 | `API-001` | OpenAPI operation、测试脚本、工作簿 |
| 接口测试点 | `ATP-API-001-001` | 需求来源、SQL/契约判据、一个或多个用例 |
| 查询 SQL | `api-query-oracle.sql`（适用时） | 已确认需求口径、接口测试点、响应字段/顺序或数据库副作用 |
| 自动化实施方案 | `api-test-automation-plan.md` | 测试点分组、SQL、初始化/清理、Excel/脚本设计 |
| 用例 | 现有 Excel 序号/用例名 | 测试点、Sheet、数据 generator、pytest 断言 |
| 场景组 | `G-01` 或方案内标题 | 数据闭包、初始化/清理、用例行、脚本函数、验证状态 |
| 功能 Facet | `FAC-xxx` | 关联接口测试点、实测证据或功能残余点 |

不为追溯强行修改现有 Excel 列结构；如果既有格式没有 ATP 列，则在自动化实施方案的落地映射中维护关系。

## 7. 功能残余的收敛规则

接口自动化完成后，功能侧不再重复全面验证每条 API 规则，但要保留接口无法证明的内容。按以下类别处置：

1. **API 覆盖的业务规则**：目标环境真实通过且断言同一规则时，在覆盖台账记录证据；功能侧不再重复完整规则，只按风险保留必要的页面显示一致性/关键路径抽查。
2. **接口无法覆盖的页面行为**：如颜色实际渲染、自动刷新、筛选控件交互、弹窗/编辑器行为、滚动位置保持等，保留功能测试点。
3. **部分可覆盖行为**：接口字段或结果由 API 验证，页面呈现/交互由功能测试验证，拆分 Facet 并分别记录，不把一方证据当作另一方覆盖。
4. **接口失败、未执行或阻塞**：相关规则仍未覆盖；功能残余分析应标注待补接口验证或临时功能验证，不得直接删除。

示例：竞彩模块中 `RSU-009` 自动刷新和筛选/滚动保持、`RSU-010` 列头筛选属于 UI 观察；`RSU-008` 行颜色需分别验证 API 返回的颜色规则和页面实际颜色渲染。生成前先以当前 `preanalysis/02-sentence-test-point-map.md` 的 RSU 映射为准，纠正旧总览中把列头筛选指向 `RSU-008` 的不一致。

## 8. 产物审核门禁

- 单接口范围与 OpenAPI operation、测试脚本和工作簿一致；需求、已确认答复、DB/SQL 和实现证据有明确来源。
- 用户需要回答的问题已闭环，或明确标为阻塞；不能把可从输入文档查明的问题再交给用户。
- 方案内每条测试点均有条件/数据状态、请求动作和可判定的响应或 DB oracle；接口不可观测的需求显式标为功能侧验证。
- SQL oracle 适用时已按需求和已确认口径审核，字段、过滤、排序、空结果和参数前提明确；不适用时方案说明理由。自动化实施方案引用对应 SQL（如适用）和测试点，并在编码前完成评审。
- 每个已实现的场景组均能从测试点追到 Excel 用例、数据初始化/清理和 pytest 断言；单条用例可独立执行。
- 造数和清理与实际表结构、外键及 helper 副作用相符；预期从需求/SQL推导，不照抄待测实现。
- 静态检查、Workbook 解析、pytest 收集与真实接口执行结果分开记录；只有实际通过才能计入 API 覆盖。
- 发现预期与实现不一致时记录为差异/缺陷候选，不擅自改变预期使测试通过。

## 9. 落地步骤

### Phase 0：收敛四个 Skill 的输入输出约定

固定单接口分析、方案内测试点、独立 SQL oracle 的适用判定、自动化实施方案、场景组同步实现、覆盖台账和状态口径。此阶段不搭建多个 Runner；已有分析按用户指定的接口范围整理，不批量迁移。

**验收**：能说明一个 API 的需求来源、已确认口径、接口测试点、SQL oracle（如适用）、自动化设计、每组数据准备、Excel 行、pytest 断言和执行状态之间的追溯关系。

### Phase 1：选择一个接口做纵向试点

从 `MOD-06-03` 选择一个 operation，完成分析与问题闭环、含测试点的接口测试方案、独立查询 SQL 和自动化实施方案评审，再选一组相近测试点按“数据准备 + Excel 用例 + pytest 实现”一起落地，单条执行并验证清理。

**验收**：SQL oracle 适用时，人工执行可复核该接口的响应结果或数据库副作用；不适用时有明确依据；真实测试数据触发已设计的数据条件；每条用例独立执行；SQL（如适用）、自动化方案、Excel、脚本与测试点互相可追溯；没有额外维护重复用例文档。

### Phase 2：按组完成该接口并校准框架

逐组推进该接口剩余测试点，更新同一工作簿、脚本和自动化实施方案映射；完成接口执行后更新 Facet 覆盖，再用 `api-test-plan` 的功能残余模式形成该范围的功能测试点。按试点发现的实际重复工作调整 Skill，不预设复杂自动化架构。

### Phase 3：逐接口复制

对模块剩余 operation 重复同一闭环；模块级功能残余在相关接口状态明确后收敛。后续模块复用通用流程，按需补充模块业务上下文，不复制业务规则。

## 10. 首期不做

- 不新增独立的 API 测试点生成 Skill；测试点属于 `api-test-plan`。
- 不新增独立的 SQL 生成 Skill；查询 SQL 与自动化实施方案由 `api-test-automation-design` 顺序产出。
- 不新增独立的用例生成、Excel 转换、脚本生成或覆盖收敛 Skill；用例/数据/脚本由 `api-test-implementation` 同步完成，功能残余由 `api-test-plan` 后续收敛。
- 不要求先把所有 Excel 用例写完再写脚本，或先把所有脚本框架搭完再填数据；按场景组纵向闭环。
- 不要求立即引入父 Runner、Fork、多层 manifest 或通用代码生成器。若后续实现自动编排，只复用被试点证明有价值的机制。
- 不重写既有 `rsu-test-point-generation`、`tp-test-case-generation` 及其消费者格式；本框架以独立接口工作流运行。
- 不把数据库连接凭证、运行 token 或固定环境样本写入 AI 分析产物。
