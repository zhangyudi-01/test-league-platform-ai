## 接口调用与契约

- **请求**：GET 查询参数 `teamId`、`currentDataSource`。`teamId` 是人工球队 `m_team.team_id`，不是任一源的 `sourceTeamId`；`currentDataSource` 是目标 B 源。OpenAPI 将二者标为 `required=false`，但其错误描述明确包含缺参错误，因此不能据 schema 标记推断业务允许缺参。Cookie 只记录为可选请求头，认证由既有 DataBff client 处理，不复制样例凭据。
- **调用路径**：OpenAPI operation 是 data-backend 内部路径 `GET /relations/team/recommendations`；测试工程经 BFF 调用时使用 `/data-backend/relations/team/recommendations` 代理路径。此处区分路由路径与业务 operation，除非本轮明确包含路由测试，不把代理连通性混入算法判定。
- **数据源方向**：`currentDataSource=1` 表示目标 B 源为纳米、反向基准 A 源为贝泰；`currentDataSource=3` 表示目标 B 源为贝泰、反向基准 A 源为纳米。
- **source 2 与不支持值**：OpenAPI 明确规定 `currentDataSource=2` 时成功返回空列表；归档设计 §D7 将非 `1/2/3` 规定为参数错误。因此 `4` 即使已属于当前项目公共数据源枚举，仍不自动成为本接口支持值。对 `4` 断言参数错误 code `2`，具体文案及错误 `data` 未由该设计单独规定。
- **错误响应**：OpenAPI 描述逐项列出 `teamId` 缺失→code 2 / `teamId不能为空`；`currentDataSource` 缺失或不存在→code 2 / `当前数据源不存在`；球队不存在→code 2 / `球队信息不存在`；服务异常→code 31 / message 以 `服务异常` 开头。`currentDataSource=2` 是另行明示的合法成功空数组分支。OpenAPI 未定义错误响应的 `data` 形状，不据此断言错误体中的该字段。
- **错误优先级与封装证据**：上一版最终分析 §3.3 记录的业务校验顺序为 teamId 缺失、数据源缺失/非法、球队存在性、source=2 分支；并记录业务错误 HTTP 200、错误 data=null，非整数类型绑定失败可能 HTTP 400。这些细节没有由当前 OpenAPI schema 完整表达，当前材料也未提供本轮接口实测或实现代码复核，故保留为“历史已记录、待当前实现/运行证据复核”，不作为已核实的当前传输契约，也不据此扩大当前成功响应 oracle。
- **成功响应**：`CommonResult` 包含 `code`、`message`、`data`；成功约定 `code=0`、`message=OK`。`data` 是候选数组，元素字段为 `sourceType`、`sourceTeamId`、`teamNameZh`、`teamShortNameZh`、`teamNameEn`、`recommendCount`、`matchStatus`、`checkStatus`、`manualTeamId`。无候选时按业务口径返回成功空数组 `[]`。
- **字段与绑定状态**：`sourceType` 等于目标 B 源。已绑定到任意人工球队的最高分候选仍返回，`matchStatus=1/checkStatus=0/manualTeamId=<已绑定人工球队>`；未绑定候选为 `0/1/null`；`checkStatus=2` 是前端选中态，后端不返回。绑定查询必须限定目标 source_type 与足球 sport_id=1，不只检查当前 teamId；同数值 sourceTeamId 在其他源/运动下的关系不能污染状态。OpenAPI 未声明 `manualTeamId` nullable，属于 schema 缺口。
- **候选名称与实体去重**：纳米字段映射为 `name_zh/short_name_zh/name_en`；贝泰为 `team_name/team_name/team_name_en`。上一版记录贝泰 `beitai_football_team` 同一 `team_id` 可因赛事维度有多行，补名称前须按 team_id 折叠，避免一个候选扩成重复响应；该结构事实当前未由 DDL 复核，作为已确认基线注明来源而非声称本轮重查。
- **排序**：按前一版最终分析 §6.4 和第13轮适配 §5、§9 沿用完整口径：非空简称正序、空简称最后、相同简称（含多个空简称）按 `sourceTeamId` 升序。纳米排序字段为 `short_name_zh`，贝泰为映射后的 `team_name`。这是响应数组顺序的一部分。
- **副作用与重复调用**：第13轮适配方案 §9 明确要求只读和幂等规则保持原确认口径；前一版 §2、§11.8 记载查询不写 `r_team_data`、重复请求不产生状态且结果稳定。作为此前确认基线继续保留；具体自动化仍需由请求前后数据快照验证，不把当前静态分析说成已运行证明。

## 已确认业务规则

以下标记“此前确认”的数据约束源自上一版最终分析 §1.2、§5.6、§15.1；当前输入没有完整 DDL，未在本轮重新查询数据库，自动化实施前应复核其环境适用性。

1. 先确定目标 B 源和反向 A 源；汇总数据中心球队在 A 源关联的全部源球队。
2. A 源参考比赛只从对应足球 `r_basic_data` 映射行中选择 `source_season_id IS NOT NULL` 的源赛季。该非空规则表示赛季已匹配；`relation_status` 不参与资格判断，`source_competition_id` 不增加赛季限制。A 赛季资格必须先于时间窗口筛选。
3. A 源全部关联球队的合格比赛合并后，按一个数据库当前时刻分别选取过去侧有效开赛时间 `<= NOW()`、时间倒序最近5场；未来侧有效开赛时间 `> NOW()`、时间正序最近5场。两侧分别最多5场，不互相补位，最多合计10场。所有 A 源球队是全局5+5，不是每队各取5+5。
4. 贝泰有效时间为 `COALESCE(resumetime, match_gtm8_time)`；纳米 Unix 秒时间用 `FROM_UNIXTIME(match_time)`，按数据库会话时区约定比较。两源精确到秒。
5. 对选中的 A 源比赛，以人工赛季桥接至 B 源对应足球赛季，匹配同一有效开赛时间、同一人工赛季的 B 源比赛；按 A 源球队当时主/客角色抽取 B 源同侧球队并累计。
6. 每条符合时间、人工赛季和角色条件的 B 源比赛命中均计数；只返回最高计数的全部并列候选。按此前确认的完整排序口径排序：非空简称正序、空简称最后、简称相同时按 sourceTeamId 升序。
7. 比赛状态不作为 A 源比赛资格；选中但无 B 源同时间/赛季候选的 A 场次仍占窗口名额，不由窗口外比赛补位。
8. **此前确认的数据前提**：各源 season_id 在对应源内唯一；`r_basic_data(source_type, source_season_id)` 唯一映射一个 manual_season_id，且不存在同源赛季残留多个历史人工赛季的脏关系。在该前提下，桥接键使用 source_type + source_season_id + sport_id=1，不需要 source_competition_id；这是带前提的简化，不能脱离这些前提泛化。
9. **B 源赛季按集合处理**：一个 manual_season_id 可对应多个 B 源 source_season_id；所有映射到该人工赛季的 B 源赛季都参与同秒匹配，不能假设一对一。缺 A 映射、缺 B 源赛季映射或 B 比赛映射到不同人工赛季均不命中。
10. **两侧非过滤规则**：不按 A 或 B 比赛状态过滤，不按 B 候选球队删除状态过滤，不因候选已绑定（包括绑定到其他人工球队）而过滤；绑定只决定返回状态。每条符合条件的 B 比赛记录均计一次，因此 recommendCount 是命中记录数，不是 A 比赛去重数，也没有由 5+5 推导出的 <=10 上限。
11. **候选唯一性与状态作用域**：最终响应以目标源 sourceTeamId 为候选粒度；匹配状态按 target source_type + sport_id=1 + source_team_id 查询并返回实际绑定的 manualTeamId。后端 checkStatus 仅为 0/1，2 属于 UI 选择态。
12. **前端/API 边界**：推荐接口不检查按钮显示条件、Tab 或页面选择状态；调用方绕过 UI 时，目标源已有匹配也不因此变成接口错误。接口不保存勾选态、不执行匹配写入。
13. **只读/幂等**：查询不得新增或修改球队关系；相同数据下重复调用结果稳定，不因首次调用改变后续状态。依据此前确认基线与第13轮适配 §9，非本轮实测结果。

以上第13轮时间窗口和赛季资格来自需求适配方案中的确认记录；第10轮“最近10场”已被替换。

## 数据路径与数据库行为

1. 请求参数进入 `Request_Context`：`teamId=m_team.team_id` 定位人工球队，`currentDataSource` 决定 A/B 源方向；source 2 是成功空列表分支，其他非法整数不进入候选计算。
2. `r_team_data` 以 `manual_team_id + source_type + sport_id=1` 取得人工球队的全部 A 源球队；关系判断同时保留 source_team_id，不能跨源或跨运动按 ID 混用。
3. `r_basic_data` 以 `source_type + sport_id=1 + source_season_id IS NOT NULL` 识别 A 源已匹配赛季；源比赛的 `season_id` 与该映射行的 `source_season_id` 对应。按有效时间构造过去/未来两组窗口。
4. 选中 A 源场次通过 `manual_season_id` 找 B 源映射行，再依据 B 源 `season_id`、精确有效时间和 A 侧主客角色生成候选命中。
5. 每条符合时间、人工赛季和主客角色的 B 源比赛形成一次命中；以目标 sourceTeamId 汇总、过滤到所有最高分候选。一个 A 时间可能对应多条 B 比赛，所以推荐次数不封顶为 10。
6. 补充候选名称：纳米读取 name_zh/short_name_zh/name_en；贝泰读取 team_name/team_name/team_name_en，并先按 team_id 折叠多赛事球队行。
7. 按 target source_type + sport_id=1 + source_team_id 查绑定状态；已绑定到任意人工球队仍保留并返回对应 manualTeamId，未绑定 manualTeamId 为 null；最后按完整简称排序规则排列。
8. 当前 SQL 与脚本只作为实现对照；旧版全局 Top-10 选择及其窗口前置顺序已被第13轮替代，不能直接作为当前 oracle。

潜在空结果包括：A 源关系不存在、没有已匹配 A 源赛季、没有有效 A 源比赛、选中场次没有符合时间/赛季/角色的 B 源比赛。人工球队不存在是参数错误，不属于成功空结果。
