## 2. 已确认业务契约

### 2.1 请求和数据源方向

1. `teamId` 表示人工球队 `m_team.team_id`；
2. `currentDataSource` 表示目标数据源 B：
   - `1`：贝泰作为 A 源，推荐纳米球队；
   - `2`：同行暂不参与推荐，成功返回空数组；
   - `3`：纳米作为 A 源，推荐贝泰球队；
3. 足球固定使用 `sport_id = 1`；
4. 只覆盖 OpenAPI 明确列出的业务错误：
   - `code=31`：服务异常；
   - `code=2`：`teamId` 不能为空；
   - `code=2`：当前数据源不存在；
   - `code=2`：球队信息不存在。

### 2.2 推荐计算链路

```text
人工球队 teamId
→ 根据 currentDataSource 确定目标源 B 和反向基准源 A
→ 查询人工球队在 A 源的全部历史球队
→ 汇总所有 A 源球队的比赛并全局取最近 10 场
→ A(sourceType + sourceSeasonId + sportId=1) 映射 manualSeasonId
→ manualSeasonId + B.sourceType + sportId=1 反查 B.sourceSeasonId 集合
→ 查询 B 源同一秒、同一人工赛季的比赛
→ 根据 A 球队在比赛中的主客角色选择 B 比赛同侧球队
→ 按 B.sourceTeamId 累计命中次数
→ 只保留并列最高分候选
→ 补充球队名称和当前匹配状态
→ 按中文简称、空简称、sourceTeamId 排序
```

### 2.3 已确认计算规则

1. 源赛季表的 `season_id` 全局唯一；
2. `r_basic_data` 中每个 `sourceType + sourceSeasonId` 只映射一个人工赛季；
3. `r_basic_data` 不存在历史脏赛季关系；
4. 测试预期的赛季桥接不依赖 `sourceCompetitionId`；
5. 纳米 `match_time` 为 Unix 秒级时间戳；
6. 贝泰有效开赛时间始终为 `COALESCE(resumetime, match_gtm8_time)`；
7. A/B 源比赛均不按比赛状态过滤；
8. B 源球队不按删除状态过滤；
9. 已匹配候选不被过滤，只改变匹配状态；
10. 所有 A 源历史球队的比赛合并后全局取最近 10 场，不是每支球队各取 10 场；
11. 同一球队同一时间参加两场比赛的场景已由业务排除，不增加同时间次级排序；
12. 排序规则为：中文简称正序、空简称最后、简称相同时按 `sourceTeamId` 升序；
13. 推荐查询只读，不新增或修改球队匹配关系。

### 6.1 Sheet 结构

2. `球队智能推荐查询` 主 Sheet；
3. `球队智能推荐查询-参数`。

`预期` Sheet、场景 Key、数据角色 Key、路由控制列、额外预期映射 Sheet 或跳过控制
Sheet。

### 6.2 接口配置

```text
接口名称：球队智能推荐查询
请求路径：/data-backend/relations/team/recommendations
请求方式：GET
是否登录：是
HTTP 状态码：200
```

参数只有：

```text
teamId|int
currentDataSource|int
```

缺失参数用例在 Excel 中保留空值，由对应处理函数在请求前从参数字典中删除，不能把空字符串当作参数发送。

### 6.3 成功预期

成功用例在 Excel 中保留响应骨架：

```json
{
  "code": 0,
  "message": "OK",
  "data": []
}
```

处理函数在请求前执行独立参数化 SQL，将结果写入 `case_dict["预期"]["data"]`。

### 6.4 业务错误预期

普通业务错误使用固定完整预期，例如：

```json
{
  "code": 2,
  "message": "teamId不能为空",
  "data": null
}
```

服务异常的异常详情可能变化，处理方式为：

1. 请求后断言 `code=31`；
2. 断言 `message` 以“服务异常”开头；
3. 断言 `data=null`；
4. 完成业务断言后，把实际动态 message 回填至预期，再由框架执行完整响应精确比较。

该方式不会弱化 `code`、消息前缀或 `data` 校验，只避免绑定不稳定异常明细。

### 6.5 用例描述格式

每条用例统一使用：

```text
【测试目的】
验证……

【前置数据】
……

【请求与校验】
请求 teamId=……、currentDataSource=……
校验……

【数据影响】
本接口只读，不应新增或修改任何业务数据。
```

### 7.1 测试入口

整个接口只保留一个参数化测试函数：

```python
@pytest.mark.parametrize(
    "case_dict",
    api_test_data("接口测试用例_球队智能推荐查询.xlsx")
)
def test_team_smart_recommendation_get(
        data_bff,
        team_smart_recommendation_data,
        case_dict
):
    ...
```

测试入口只负责：

1. 通过形参注入让 pytest 执行 module 基础数据 fixture；
2. 根据 Excel“处理数据”表达式获得生成器；
3. 调用 `data_bff.test(case_dict, generator)`。

基础数据 fixture 的返回值不是接口断言对象，因此可以在测试入口中保持未使用；不增加
`assert team_smart_recommendation_data`、占位赋值或 `pass` 来表示 fixture 已激活。测试入口不编写场景
`if/elif`。

### 7.2 业务处理函数

按稳定业务处理族划分约 11 个 Excel 直接调用的函数：

| 测试点族 | 计划处理函数 |
|---|---|
| A | `assert_documented_error` |
| B | `assert_source_direction` |
| C | `assert_base_source_team_scope` |
| D | `assert_recent_ten_matches` |
| E | `assert_season_bridge` |
| F | `assert_effective_match_time` |
| G | `assert_candidate_scoring` |
| H | `assert_team_info_and_sort` |
| I | `assert_candidate_relation_status` |
| J | `assert_response_contract` |
| K | `assert_read_only_and_idempotent` |

这些函数由 Excel 直接指定，不再经过总路由函数。

处理表达式默认只传 `case_dict`。人工球队、源球队、比赛、赛事、赛季和关系
ID，必须从 `case_dict["参数"]` 中的真实请求参数出发，再查询当前初始化数据闭包得到；
不得在 Excel `处理数据` 中传入固定 ID、ID 数组、预期次数字典或排除 ID。

只有处理函数必须继续发起 HTTP 请求时，才允许额外传入 `data_bff` 运行时 client；
该参数的作用必须在函数 docstring 中说明。不得为了省略动态查库而增加业务 ID
或预期结果参数。

不得根据测试标题解析测试点，不新增场景控制列。

### 7.3 公共成功流程

脚本内提供普通的公共动态预期准备函数，例如：

```text
prepare_expected_recommendations(case_dict)
```

职责：

1. 读取 `teamId/currentDataSource`；
2. 使用参数化 SQL计算接口 9 个响应字段；
3. 将查询结果写入 `case_dict["预期"]["data"]`；
4. 返回动态预期列表，供当前业务族在请求前验证数据闭包。

各业务处理函数直接调用该函数，在请求前完成数据闭包断言，再由业务函数自身 `yield`：

```python
expected_data = prepare_expected_recommendations(case_dict)
# 对 expected_data 做本业务族的独立闭包断言
yield
```

`DataBff.test()` 在 generator 后处理完成后统一校验首次请求的 HTTP 状态和完整 JSON。
因此业务函数不再重复断言该次请求的通用 `code/message`、HTTP 200 或完整 JSON；
不再根据实际返回动态回填异常消息，也不额外增加消息前缀断言；实际返回与 Excel 完整预期不符时，
由公共框架直接报告差异。

### 7.4 独立 SQL 预期

正式脚本不能运行时读取：

```text
testsuites/data-bff/team/test_dependent_file/球队智能推荐接口查询SQL.sql
```

应把已确认 SQL 转换成测试脚本内的参数化只读 SQL：

```sql
Request_Params AS (
    SELECT
        %s AS team_id,
        %s AS current_data_source
)
```

预期查询必须：

1. 所有请求参数均参数化，不使用字符串拼接；
2. 不使用 `SELECT *`；
3. 只返回接口约定的 9 个字段；
4. 赛季桥接不依赖 `sourceCompetitionId`；
5. 贝泰统一使用 `COALESCE(resumetime, match_gtm8_time)`；
6. 不过滤比赛状态；
7. 不过滤目标球队删除状态；
8. 不过滤已匹配候选；
9. 只返回并列最高分候选；
10. 保留最终排序规则；
11. 空查询结果转换为接口预期的 `data=[]`。

独立 SQL 中不执行拼接后的多语句 `SET SESSION ...; WITH ...`。会话时区由 fixture 单独管理。

### 7.5 只读和幂等校验

#### K-001、K-002

请求前后分别查询相关 `r_team_data` 的：

- `relation_id`；
- `sport_id`；
- `manual_team_id`；
- `source_type`；
- `source_team_id`；
- `update_time`。

结果按固定字段排序后精确比较，证明接口未新增或修改球队关系。

#### H-009、K-003、K-004

首次请求仍由 `DataBff.test()` 发起。生成器在首次请求后使用已经登录的 `data_bff.session` 发起相同请求或交替方向请求，比较：

- 完整 JSON；
- 候选顺序；
- `recommendCount`；
- 双向数据源隔离。

不得递归调用 `DataBff.test()`，避免覆盖外层请求状态和生成器生命周期。
这些后续 `session` 请求只校验当前用例要求的完整 JSON、顺序、计数和双向隔离；
HTTP 状态不是这些用例的测试点，不额外增加 `status_code` 断言。

## 8. 基础数据方案

### 8.1 主要造数方式

采用：

> **专用初始化 Workbook + module 级通用 fixture + 相互隔离的静态业务数据画像。**

不以 `common/team.py` 或 `common/season.py` 作为主要造数方式，原因是本次需要：

- 固定人工赛事和人工赛季；
- 固定双源赛季关系；
- 固定双源球队和多条历史关系；
- 精确控制 Top 10 边界；
- 精确控制同秒、差一秒和 `resumetime`；
- 精确控制 NULL、空串、相同简称和排序 ID；
- 精确控制已绑定与未绑定候选；
- 构造贝泰同一 `team_id` 的多赛事记录。

现有公共创建函数包含名称查找、旧数据备份、动态 ID 和多分支转换，不适合作为本套独立数据闭包的主要方案。

### 8.2 初始化 Workbook Sheet

5. `nami_football_season`；
6. `nami_football_team`；
7. `beitai_football_tournament`；
8. `beitai_football_season`；
9. `beitai_football_team`；

`nami_football_deleted` 只服务于“目标球队删除状态不影响推荐”的隔离用例。

### 8.3 Workbook 数据规范

- 第一行：带项目类型标记的数据库字段名；
- 第二行：字段中文说明；
- 第三行起：可直接插入数据库的真实值；

- Sheet 顺序表示插入顺序；
- 第一列表示清理定位键；
- Python 不重复定义表顺序、表名、字段名、主键或业务角色映射。

`r_basic_data`、`r_team_data` 使用固定 `relation_id` 作为第一列，确保精确清理。

`beitai_football_team` 允许相同 `team_id` 对应多个 `tournament_id`；这些记录均使用专用固定 ID，fixture 根据 Workbook 记录逆序清理，不覆盖环境原有数据。

### 8.4 静态数据画像

不为 93 条用例分别创建 93 套完整数据，而是建立相互隔离、可复用的数据画像：

| 数据画像 | 主要覆盖范围 |

| P01 参数与合法人工球队 | A-001～A-004、B-004 |
| P02 贝泰→纳米主链 | B-001、B-003、C-001、J、K-005 |
| P03 纳米→贝泰主链 | B-002、H-002、H-003、K-006 |
| P04 无关系/无比赛 | B-005、B-006、D-001、J-005 |
| P05 多历史球队与 Top 10 | C、D |
| P06 赛季桥接 | E-001～E-009 |
| P07 时间与 resumetime | F-001～F-009 |
| P08 主客角色与计分 | G-001～G-016 |

每个画像使用不同人工球队 ID、源球队 ID、赛事 ID、赛季 ID 和比赛 ID，避免互相进入关系集合、最近比赛池或同秒匹配集合。

### 8.5 共享基线、单用例增量和清理责任

#### 共享基线

专用 Workbook 提供所有可长期共存的静态业务链和边界数据。

#### 单用例增量

优先通过不同静态画像实现差异，不在 generator 中频繁新增、删除或恢复数据。只有静态数据无法安全表达且确有必要的极少场景，才允许在 generator 中创建少量单用例增量。

任何单用例增量必须：

- 只清理自己创建的数据；
- 不重复清理 fixture 数据；
- 使用 `try/finally`；
- 使用参数化 SQL；
- 返回或记录精确清理键。

#### Fixture 清理责任

fixture 只清理本 Workbook 成功插入的数据，按 Sheet 逆序和记录键精确删除。不得使用模糊名称、时间范围或全表条件清理。

### 8.6 数据写入安全

1. 使用独立固定 ID 命名空间；
2. 正式写入前重新确认数据库连接身份；
3. 插入冲突直接失败，不使用 `REPLACE INTO`；
4. 不备份、不覆盖、不恢复环境原有数据；
5. fixture 记录实际成功插入的行，只清理成功插入的数据；
6. 完整模块执行前后使用残留 SQL核对专用 ID。

## 9. 关键数据闭包

### 9.1 通用闭包

```text
m_competition / m_season
├─ 人工足球赛事
└─ 多个人工赛季

m_team
├─ 当前人工球队
├─ 无关系人工球队
├─ 已存在目标源关系的人工球队
└─ 用于绑定候选的其他人工球队

r_team_data
├─ 当前人工球队 ↔ A 源历史球队 A1
├─ 当前人工球队 ↔ A 源历史球队 A2/A3
├─ 当前人工球队 ↔ 已存在的目标源球队
└─ 其他人工球队 ↔ 已绑定候选

r_basic_data
├─ A(sourceType + sourceSeasonId + sportId=1) → manualSeasonId
└─ B(sourceType + manualSeasonId + sportId=1) → sourceSeasonId 集合

A 源
├─ 源赛事和源赛季
├─ 历史源球队
└─ 用于 Top 10、角色和状态边界的比赛

B 源
├─ 源赛事和源赛季
├─ 候选球队
└─ 同秒、差一秒、角色反转和多场命中的比赛
```

### 9.2 Top 10 闭包

必须包含：

- A1、A2、A3 三个历史球队；
- 合计至少 11 场比赛；
- 时间顺序与 `match_id` 顺序不一致；
- 第 10、11 场可产生不同候选；
- Top 10 内存在无赛季映射或无同秒目标比赛的场次；
- 第 11 场即使命中也不能补位；
- 多种比赛状态均可进入最近比赛集合；
- 贝泰通过 `resumetime` 改变第 10/11 场边界；
- 纳米严格按 `match_time` 取最近 10 场。

### 9.3 赛季桥接闭包

必须包含：

- A/B 映射同一人工赛季；
- A/B 映射不同人工赛季；
- A 源赛季缺少映射；
- 人工赛季缺少 B 源映射；
- 一个 A 人工赛季对应多个 B 源赛季；
- 跨数据源相同源赛季 ID；
- 其他运动存在相同源赛季关系；
- 多场 A 比赛复用同一赛季映射；
- 用于验证不依赖 `sourceCompetitionId` 的隔离数据。

### 9.4 时间闭包

必须包含：

- A/B 精确同秒；
- B 比 A 早一秒；
- B 比 A 晚一秒；
- 已知 Unix 秒和北京时间对应值；
- 贝泰 `resumetime=NULL`；
- 贝泰 `resumetime` 非空；
- 原始时间匹配但恢复时间不匹配；
- 贝泰分别作为 A 源和 B 源；
- B 源同一秒存在多场比赛。

### 9.5 候选、名称和排序闭包

必须包含：

- A 球队为主队和客队；
- 目标球队位于正确同侧和相反侧；
- 最近比赛中角色混合；
- 5/3/1 唯一最高；
- 5/5/3 并列最高；
- 三个及以上候选并列；
- 所有候选均为 1 分；
- 目标侧同秒多场使次数大于 10；
- 已绑定最高分候选；
- 未绑定、绑定到当前人工球队、绑定到其他人工球队；
- 纳米全称、简称、英文名相互不同；
- 贝泰同一 `team_id` 存在多 `tournament_id` 记录；
- NULL、空串、纯空格简称；
- 相同简称但 `sourceTeamId` 不同；
- 低分候选简称排序靠前但不应进入结果。

贝泰同 `team_id` 的多条名称记录应使用相同名称，只验证折叠后不重复，不引入“不同名称取哪条”的新业务规则。

### 9.6 服务异常闭包

`TSR-A-005` 使用完全隔离的数据画像，例如：

- 合法人工球队；
- 纳米 A 源关系；
- 纳米比赛 `match_time=NULL`；
- 独立人工赛季和源球队 ID。

该画像不得与任何正常场景共享人工球队、历史源球队或比赛池，避免异常数据影响正常用例。

## 10. Fixture 设计

### 10.1 Fixture 名称和作用域

计划新增：

```text
team_smart_recommendation_data
```

作用域：`module`。

### 10.2 Fixture 固定职责

1. 读取 `data/init/球队智能推荐查询基础数据.xlsx`；
2. 获取 Workbook 实际 Sheet 顺序；
3. 从第三行起读取每个 Sheet；
4. 按 Sheet 顺序逐行通用插入；
5. 记录实际成功插入的第一列清理键；
6. 保存当前数据库会话时区；

8. `yield` 基础数据；

- 不恢复环境原有业务数据；

## 11. 当前实现差异和缺陷判定基线

### 11.1 `sourceCompetitionId` 差异

已确认测试契约的赛季映射条件是：

```text
sourceType + sourceSeasonId + sportId
```

当前 Java 实现仍使用：

```text
sourceType + sourceCompetitionId + sourceSeasonId
```

因此 `TSR-E-008` 应保留为隔离场景：

- 源赛季 ID 全局唯一；
- 赛季映射关系唯一；
- 比赛赛事 ID 与映射行赛事 ID 不一致；
- 独立 SQL仍应通过源类型、源赛季和运动完成桥接。

若接口因此不返回候选，应归类为：

> 接口实现仍错误依赖冗余的 `sourceCompetitionId`。

不得为了测试通过而把预期修改成当前 Java 行为。

### 11.2 排序实现差异

Java 使用中文 `Collator`，独立 SQL 使用 GBK 转换排序。两者不是所有 Unicode 字符下的绝对等价实现。

本轮基础数据使用普通常用汉字简称，并在落数前验证：

1. Java 接口顺序；
2. 独立 SQL顺序；
3. 测试设计预期顺序。

三者必须一致。暂不使用生僻字、多音字和特殊 Unicode 字符扩展未确认范围。

### 11.3 候选球队 ID 为空

正常测试数据必须保证比赛同侧候选球队 ID 非空。若后续增加空候选边界，独立 SQL应显式排除空候选，以保持与服务层“空候选不计分”的行为一致；该边界不属于当前 93 个业务测试点，不在本轮扩展。

### 11.4 失败归类原则

接口测试失败后必须根据以下证据分类：

1. 需求和已确认业务规则；
2. 独立查询 SQL；
3. 初始化 Workbook 数据；
4. 数据库实际记录；
5. 接口实际响应；
6. 当前 Java 实现。

失败只能归类为：

- 测试代码问题；
- 前置数据问题；
- 测试环境问题；
- 接口实现问题。

不得为了通过测试而直接修改正确业务预期，也不得把数据或用例描述变化表述成接口缺陷已经修复。
