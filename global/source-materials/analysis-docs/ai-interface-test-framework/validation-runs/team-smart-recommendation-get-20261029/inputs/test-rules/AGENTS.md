# Repository Instructions

本文件适用于整个仓库。详细规则见 `docs/测试工程/代码编写规则.md`。

## 规则作用域

- 对每个准备读取、修改或新增的目标文件，都必须从仓库根目录到目标文件所在目录逐级查找并读取沿途全部 `AGENTS.md`；新增文件按计划落点确定规则链。
- 一个任务涉及多个目录时，分别确认每个目标路径的规则链；任务范围扩大后，在操作新路径前重新检查。
- 子级 `AGENTS.md` 只适用于其所在目录及后代目录，不能因业务关联自动扩展到同级或其他目录。
- 同一路径上的规则叠加生效；同一事项发生冲突时，离目标文件更近的 `AGENTS.md` 优先。

## 指令优先级

发生冲突时按以下顺序执行：

1. 用户本次明确要求。
2. 需求、接口文档、数据库设计和已确认的业务行为。
3. 目标文件规则链中适用的全部 `AGENTS.md`。
4. 最相似的 2～3 个现有模块的实际写法。
5. `docs/测试工程/代码编写规则.md`。
6. `docs/测试工程/测试脚本开发规范.md`、`docs/测试工程/测试代码知识图谱.md`。
7. 通用工程最佳实践。

除非任务明确要求，否则不要修改上述基础参考文档。

## 子级 AGENTS.md

- 子级 `AGENTS.md` 不是每个模块、接口、审核或重构任务的常规产物，默认不新增。
- 只有某个目录存在长期稳定、仅对该目录树生效、会被多个文件或后续任务重复使用，且放入根规则会误约束其他目录的差异规则时，才创建子级 `AGENTS.md`。
- 子级文件放在所有受约束文件的最近公共目录，只记录相对上级规则的增量，不复制通用规范。
- 一次性审核结论、临时迁移方案、当前实现快照、单个文件细节和可由代码或测试直接表达的要求，不写入子级 `AGENTS.md`。
- 局部规则不再满足上述条件时，应删除子级文件，或将仍具通用价值的内容合并到根规则或代码编写规则。

## 修改前必须完成

1. 执行 `git status --short`，保留用户已有修改，不回退无关文件。
2. 确认初始目标路径，并按“规则作用域”读取每个路径适用的全部 `AGENTS.md`。
3. 阅读与本次任务相关且实际存在的需求、接口资料、测试点、数据库设计或其他依据；不存在的资料不作为机械门槛。
4. 任务涉及新增或修改测试实现、fixture、Excel 或公共测试方法时，阅读 `docs/测试工程/代码编写规则.md`，并检查 2～3 个最相似的实现。
5. 任务涉及 Excel 驱动测试时，统计相似模块 Excel `处理数据` 的分布，并确认其业务处理函数、`yield from` 复用、fixture 和 common 的职责划分；不得只比较目录结构或函数名称。
6. 先向用户说明与本次任务有关的工程基线、准备采用的整体结构和修改范围，再开始编辑。
7. 涉及数据库造数时，编码前先列出数据闭包，并在“现有业务创建函数、专用 `data/init` Workbook、单用例少量直接造数”中选择主要方案，说明选择理由、共享基线、单用例增量、返回上下文和清理责任；未完成决策不得先写复杂 fixture。
8. 按任务类型列出计划新增的函数、类、文件、fixture、Excel Sheet、控制列或子级 `AGENTS.md`；不涉及的类别无需罗列，没有明确必要性时不得新增。

## 实现门禁

### 通用要求

- 优先复用已有函数和最近模块写法，保持修改范围最小。
- 默认不新增类、清理栈、一次性包装函数或其他无明确收益的中间层。
- 修改相互关联的代码、配置和测试数据时同步检查，避免只更新单侧。
- 人工保证且不会污染共享环境的互斥条件，不增加无必要的防御性分支。

### Excel 驱动测试

- 默认沿用 `Excel -> api_test_data() -> 对应服务 client.test() -> generator` 主流程。
- Excel 的 `处理数据` 应直接选择有业务含义的处理函数；不要让所有用例先进入一个总处理函数，再依赖 `场景Key`、标题或私有路由函数二次分发。
- 处理函数按稳定业务处理族划分：相同准备方式和验证方式的用例共用函数，不为每条用例建函数，也不把互不相关的业务族塞进一个巨型函数。
- 公共成功、失败或动态预期流程优先由业务处理函数通过 `yield from` 复用，保持 `yield` 前准备、`yield` 后断言和清理的项目语义。
- 默认不新增额外 Sheet、场景控制列或可由真实请求参数推导的重复字段。
- 每条 Excel 用例必须可单独执行，但可以共享 fixture 创建的基础数据。
- 修改代码分支时同步检查 Excel；修改 Excel 时同步检查代码、预期和清理逻辑。
- 新建、重建或回写项目 `.xlsx` 用例文件时，写入端必须使用 `xlsxwriter`；其他库仅可用于读取，不得使用 `openpyxl` 等库保存或回写 Workbook。
- 使用 `xlsxwriter` 重建已有 Workbook 时，必须保留现有 Sheet 名称和顺序、单元格值和类型、合并单元格、冻结窗格、列宽、行高及必要样式。
- 测试脚本若出现一个总场景路由函数、大量 `_` 私有中间函数或 Excel 全部指向同一处理函数，必须先判断是否偏离现有框架；不能以“统一入口”为理由直接保留。

### 数据准备与清理

- `conftest.py` 只负责共享基础数据；每条用例的场景数据、动态参数和动态预期留在测试层。
- 稳定的业务数据动作可以放入对应 `common/{业务域}.py`，Excel 占位符解释和接口返回结构不得放入公共层。
- helper 只清理自己创建的数据；fixture 已整体清理的数据不要重复恢复。
- 已有业务创建函数能够生成所需正常业务链、返回定位 ID 且有配套清理时，优先直接复用；需要固定多表关系、跨赛季隔离、缺失关系、NULL/空串或刻意排序 ID 的共享闭包时，使用专用初始化 Workbook；单用例少量差异留在 generator。
- 专用初始化 Workbook 默认以 Sheet 名表示表名、Sheet 顺序表示插入顺序、首列表示清理键，并保存可直接入库的真实值；Python 不得重复定义表顺序、表名、主键、字段或角色映射。
- 专用 Workbook fixture 默认只允许“通用读取、通用插入并记录成功主键、`yield`、逆序精确清理”。一旦出现 fixture 专属常量、映射、私有 helper、表级 `if/elif` 或大量字段转换，必须停止扩展代码，先重新选择业务创建函数、调整 Workbook 或把差异移回 generator。
- 简洁性按 `Workbook + fixture + 测试文件 + 清理逻辑` 的总复杂度审核，不能把复杂度从 Python 转移到 Excel，或从 Excel 转移到 Python。

## 验证门禁

根据改动范围执行并报告：

1. 修改 Python 文件时执行 `py_compile` 或等价语法检查。
2. 修改 Excel 文件时，必须确认由 `xlsxwriter` 写入，并依次通过 Microsoft Excel 实际打开、`pylightxl/ExcelReader` 读取和项目 `api_test_data()` 读取，核对用例数量、参数类型和关键值。
3. 修改测试实现或用例数据时执行目标测试的 `pytest --collect-only`。
4. 数据库写入型 pytest 必须串行运行，禁止并行执行造数用例。
5. 涉及新增、修改、唯一约束或清理时，代表性用例连续执行两遍。
6. 最后检查 `git diff`，删除未使用函数、字段、Sheet、import 和调试残留。
7. 所有文件新增和修改都必须重新读取磁盘最终内容，确认目标改动已落盘、旧表达和错误副作用已消失；代码改动还要验证函数定义、调用方及完整调用链兼容。
8. 新增或修改测试实现、fixture 或 Workbook 后，必须完整串行执行目标测试模块；失败时依据需求或确认 SQL、数据库数据、接口返回和被测实现，归类为测试代码、前置数据、环境或接口问题，不得为通过而直接修改正确预期。
9. 完工后按 `docs/测试工程/代码编写规则.md` 独立执行结构审核；pytest 通过不能替代规范审核。编写任务发现不符合项先整改，纯审核任务则按文件、行号、违反条款和建议修改明确报告。
