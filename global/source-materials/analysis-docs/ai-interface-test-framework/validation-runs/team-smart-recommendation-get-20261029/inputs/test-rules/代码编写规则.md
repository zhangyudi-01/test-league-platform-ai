# 代码编写规则

> 适用范围：本仓库新增或修改的测试脚本、Excel 用例、fixture、公共测试辅助方法及相关 SQL。
> 基础资料：`docs/测试工程/测试脚本开发规范.md`、`docs/测试工程/测试代码知识图谱.md`。
> 本文只定义可执行的编码决策和审核门禁；基础资料中的框架事实与完整说明不在本文重复展开。
> 本文同时用于编码前设计、编码过程约束和编码完成后的审核。功能正确、语法通过或测试通过均不代表符合本文；审核任务也必须按本文指出范围内的不符合项。

---

## 1. 规则优先级

发生冲突时，严格按以下顺序处理：

1. 用户本次任务中的明确要求。
2. 当前需求、接口文档、数据库设计和已确认的业务行为。
3. 目标文件规则链中适用的全部 `AGENTS.md`。
4. 与当前接口最相似的 2～3 个现有模块的实际写法。
5. 本文及项目其他规范。
6. 通用 Python 或测试工程最佳实践。

补充要求：

- “工程上更通用、更安全”不能单独成为新增类、框架、Sheet 或 helper 的理由。
- 现有项目已经有直接写法时，默认沿用；确需偏离时，必须在修改前说明差异和原因。
- 不得为了形式上满足某条规则而偏离项目主流结构。

### 1.1 AGENTS.md 作用域与子级文件

执行任何任务时，先确定目标文件，再从仓库根目录到目标文件所在目录逐级读取沿途全部 `AGENTS.md`。任务涉及多个目录时，各目标路径分别建立规则链；新增文件按计划落点确定规则链；任务中途扩展到新目录时，操作前重新检查。

同一路径上的规则叠加生效，子级规则仅约束其所在目录及后代目录。同一事项发生冲突时，在不违反用户要求和已确认业务规则的前提下，以离目标文件更近的 `AGENTS.md` 为准。业务上相关不代表目录作用域自动扩展；修改其他目录的文件时，必须读取该文件自身路径上的规则链。

子级 `AGENTS.md` 不是模块开发、代码审核或重构任务的常规产物，默认不创建。只有同时满足以下条件时才应新增：

- 规则长期稳定，不是本轮重构方案或当前实现快照；
- 规则仅适用于某个目录树，放入根规则会误约束其他目录；
- 规则会被该目录下多个文件或后续任务重复使用；
- 规则不能更合适地由代码、配置、测试、已有规范或自动化检查表达。

常见合理场景包括：该目录有稳定且独有的运行命令、生成文件限制、外部资源隔离要求、数据所有权边界或目录布局约定。以下内容不应产出子级 `AGENTS.md`：

- 一次审核的发现和整改清单；
- 临时迁移步骤或正在收敛中的目标风格；
- 单个接口、脚本、函数或 Workbook 的当前结构；
- 已适用于全仓库的编码偏好和验证规则；
- 可由测试、lint、类型检查或配置直接强制的要求。

确需创建时，应放在所有受约束文件的最近公共目录，只记录相对上级规则的增量，不复制通用规范，也不通过固定路径把作用域扩展到目录树之外。局部差异消失后应删除；具有全仓库价值的内容应提升到根 `AGENTS.md` 或本文。

## 2. 编码前强制门禁

任何新增或重构开始前，必须完成以下工作：

1. 阅读与本次任务相关且实际存在的需求、接口定义、测试点、数据库设计及其他业务资料；不存在的资料不作为机械门槛。
2. 检查工作区状态，识别并保留用户已有修改。
3. 确认准备读取、修改或新增的目标路径，并按 1.1 节读取各路径适用的全部 `AGENTS.md`。
4. 任务涉及测试脚本、fixture、Excel 或公共测试辅助方法时，至少阅读 2～3 个最相似的现有测试实现，包括：
   - 测试脚本；
   - 同目录或相似目录的 `conftest.py`；
   - Excel Sheet 和参数列结构；
   - 已有造数、预期构造和清理方法。
   - 根级 `conftest.py`、模块 `conftest.py`、`common` 初始化方法和 `data/init` Workbook 组成的实际数据链路。
5. 任务涉及 Excel 驱动测试时，对相似模块进行结构性比较，而不是只浏览文件：
   - 统计 Excel `处理数据` 表达式的种类和用例分布；
   - 识别哪些函数是 Excel 直接选择的业务处理函数；
   - 识别哪些公共成功、失败或预期流程通过 `yield from` 复用；
   - 识别 fixture、测试文件和 `common` 各自实际承担的数据准备职责；
   - 记录相似脚本的函数数量、主要函数粒度和是否存在内部场景路由。
   - 当 Workbook、测试脚本或 fixture 经不同提交者、不同迭代修改时，使用 Git 历史确认各部分是否属于同一实现版本；不得把旧测试脚本和后来重写的 fixture 拼接成一个项目先例。
6. 在修改前明确与任务有关的工程基线：
   - 基础数据由谁创建；
   - 初始化入口是否位于目标测试的实际执行路径，单独运行目标用例时能否触发；
   - 单用例场景数据在哪里准备；
   - 动态参数和预期在哪里替换；
   - 哪一层负责清理；
   - 是否已有可直接复用的方法。
7. 列出计划新增的函数、类、文件、fixture、Excel Sheet、控制列和子级 `AGENTS.md`，并逐项说明必要性。

默认新增预算：

- 新类：0。
- 新的通用清理框架：0。
- 额外 Excel Sheet：0。
- `场景Key`、`数据源` 等非接口控制列：0。
- 只调用一次且仅转发参数的包装函数：0。
- `conftest.py` 中仅供单个 fixture 使用的私有 helper：0。
- 专用初始化 Workbook 已表达的表顺序常量、Sheet/表名映射、主键映射和字段/角色映射：0。
- fixture 中按表名、Sheet、场景或测试标题执行的业务条件分支：0。
- 子级 `AGENTS.md`：0。

只有现有结构不能清晰完成需求时，才能突破上述默认值。

### 2.1 数据准备方案必须先决策

“数据闭包”是指一个业务对象能够被接口正确查询或处理所需的父表、主表、关系表和数据源表等完整关联数据。只要任务涉及新增或修改数据库基础数据、fixture 或初始化 Workbook，编码前必须先明确数据闭包，并在方案说明中写清：

1. 需要哪些稳定共享数据，哪些只是单用例差异；
2. 已有哪些业务创建、删除、恢复或初始化方法可以直接复用；
3. 选择“现有业务创建函数”“专用 `data/init` Workbook”还是“单用例少量直接造数”；
4. 选择理由，以及 fixture、测试 generator 和公共方法分别负责什么；
5. fixture 返回哪些最小必要 ID 或上下文，由谁清理或恢复；
6. 使用 `data/init` Workbook 时，哪个有效入口负责读取和装库，单独执行目标用例时如何保证入口被触发；
7. 计划新增的 fixture、helper、常量、Sheet、控制列和业务分支数量。

未完成上述决策，不得先编写复杂 fixture，再根据代码反向补 Workbook、常量或 helper。

数据准备方式按以下边界选择：

| 方式 | 优先采用的场景 | 不应采用的信号 |
| --- | --- | --- |
| 现有业务创建函数 | 已有稳定函数可以创建正常业务对象链，返回本次数据的 ID 或上下文，并有配套删除/恢复方法；测试允许动态 ID、时间或普通业务值；每条用例只需在创建结果上做少量状态调整 | 调用后仍要跨多张表大量改写、反查和回填，或为了凑出固定关系增加多组分支 |
| 专用 `data/init` Workbook | 多条用例复用同一组稳定的多表数据闭包；需要同时精确控制跨赛季、映射/未映射、NULL/空串、字段来源、去重或刻意错开的排序关系；现有业务函数无法直接表达，强行复用会产生大量后置改写 | 只需单表或少量记录、已有业务函数已能直接创建，或 fixture 仍需解释角色、回填外键、逐表转换字段和维护第二套表结构信息 |
| 单用例少量直接造数 | 差异只属于一条或一类用例，涉及少量可定位记录，使用 `DB_CONN` 直接增删改比新增共享基线更清楚 | 多条用例重复创建同一完整业务链，或数据关系已经形成稳定可复用闭包 |

允许组合使用，但必须有单一、清楚的数据所有权。例如现有业务函数创建正常赛程池，测试 generator 只修改当前场景状态；或者专用 Workbook 创建稳定闭包，generator 只增加、删除或恢复本用例差异。不得由两种方式重复创建同一层业务数据。

选择标准不是让 Python、Excel 或某一个文件单独最短，而是比较 `Workbook + fixture + 测试文件 + 清理逻辑` 的总复杂度，优先选择业务分支更少、重复信息更少、数据关系更直观、清理责任更明确的方案。出现以下情况时，说明原方案可能选错，必须暂停编码并重新决策：

- 使用业务创建函数后，fixture 立即开始跨多表改值、重建关系或反查自身刚创建的 ID；
- 使用专用 Workbook 后，fixture 又新增表顺序、字段、角色、主键或外键映射；
- 为了维持当前方案不断新增一次性 helper、context、恢复注册表或表级 `if/elif`；
- 稳定基线、单用例差异和清理责任无法分别归属到 fixture、generator 或已有公共方法。

## 3. 整体结构与职责边界

对现有 Excel 驱动接口测试，优先延续项目主流程：

```text
Excel -> api_test_data() -> 对应服务 client.test() -> 处理数据 generator -> API 请求 -> 后置清理
```

各层职责如下：

| 位置 | 应承担的职责 | 不应承担的职责 |
| --- | --- | --- |
| `conftest.py` | 为多个用例提供共享基础数据、API client 或显式 fixture | 接口每个细分场景的参数分支、动态预期和大量断言逻辑 |
| 测试文件 | 解释 Excel 场景、选择目标数据、准备本用例数据、构造动态预期、协调本用例清理 | 重复实现已有公共造数和删除能力 |
| `common/{业务域}.py` | 稳定、明确、可清理的业务数据动作 | 某个 Excel 的占位符解释、接口专属路由、接口预期结构 |
| Excel | 测试目的、请求参数、可维护的场景配置和预期骨架 | 为方便代码分支而新增的重复控制信息 |
| `constants.py` | 需要跨测试文件 import 的常量 | fixture 和运行时上下文 |

公共方法不以“当前是否已有两个调用方”作为唯一标准。满足以下任一条件，可以放入对应业务域的 `common` 文件：

- 已被多个接口或测试文件复用；
- 表达稳定的业务数据动作，后续同业务域接口会自然复用；
- 与该业务域已有方法职责一致，放在测试文件中反而造成重复 SQL 或错误归属。

单接口专属的参数解释、预期拼装和一次性场景编排仍留在测试文件中。

### 3.1 Excel 与业务处理函数的路由原则

对采用 Excel 驱动的测试，场景调度入口是 Excel 的 `处理数据` 列，不应在测试脚本内部再建立一套重复的场景路由系统。

- `处理数据` 应直接选择能说明业务目的的 generator，例如成功处理、失败处理、状态处理、字段来源处理或某一类结果处理。
- 多条用例具有相同数据准备和验证算法时，应共用同一个处理函数。
- 不同数据准备、断言口径或清理责任的稳定业务族，应拆成不同处理函数。
- 不为每条 Excel 用例建立一个函数；也不把所有业务族全部交给一个总处理函数。
- 业务处理函数可以通过参数复用相同逻辑，也可以通过 `yield from` 复用公共成功、失败或动态预期流程。
- `处理数据` 表达式应优先只传 `case_dict`；能由真实请求参数、fixture 返回上下文或
  动态查库得到的业务 ID、预期 ID 集合和预期计数，不得作为函数实参硬编码在 Excel 中。
- 只有无法从 `case_dict` 及当前运行上下文推导的稳定运行时依赖或业务语义参数，
  才可增加为处理函数入参；每个额外参数的来源、用途及为何不能动态推导，必须在
  函数 docstring 中说明。
- 能由 `处理数据` 表达式或真实请求参数完成的分流，不再增加 `场景Key`、测试标题匹配或 `_route_*`、`_prepare_all_*` 一类二次路由。

推荐结构：

```python
def assert_common_result(case_dict: CaseDict, fixture_data: dict):
    "构造该接口共用的动态预期并完成请求。"
    # 公共参数替换和动态预期
    yield


def assert_business_status(case_dict: CaseDict, fixture_data: dict):
    "准备状态类场景并复用公共动态预期。"
    # 当前业务族的数据准备
    try:
        yield from assert_common_result(case_dict, fixture_data)
    finally:
        # 只清理当前业务族创建或修改的数据
        pass
```

以下结构通常表示已经偏离框架，需要先重新划分业务处理函数：

- Excel 大量或全部用例都指向同一个处理函数；
- 总处理函数再按 `场景Key`、用例标题、动作类型等字段分发；
- 一个场景准备函数包含多个互不相关业务族的大量 `if/elif`；
- 为支撑总处理函数新增通用 context、恢复注册表或成组私有中间函数；
- 阅读 Excel 无法直接判断一条用例采用哪种数据准备和验证流程。

## 4. 测试文件规则

1. 一个测试文件围绕一个接口或高度相关的一组接口。
2. 参数化测试入口保持薄，只负责接收 fixture、`case_dict` 并调用项目已有 API 测试入口。
   fixture 名出现在测试函数形参中就会由 pytest 执行；如果测试入口不需要使用其返回值，
   允许形参保持未引用，不得为“显式激活”或“消除未使用”增加 `assert fixture_data`、
   无业务意义的赋值、`pass` 或其他占位语句。只有 fixture 返回内容本身就是当前测试点时，
   才在测试或处理函数中对其做业务断言。
3. 复杂接口可以保留一个参数化测试函数，但必须拆成多条具有独立目的的 Excel 用例。
4. 每条用例必须可以单独选择执行，不能依赖其他用例先执行或遗留状态。
5. 用例独立不等于每条用例都重新创建整套共享基础数据及其关联记录；共享部分可以由 fixture 一次创建，单用例只编排自己的场景数据。
6. 同一个测试点存在多个独立输入分支、数据源分支或返回差异时，应拆成多条用例；不要强行保持“一个测试点只对应一行”。
7. 测试函数中不堆放大段造数 SQL；查询接口的动态预期 SQL 可以留在测试文件的处理函数中。
8. Excel 已提供完整预期骨架时，代码只替换动态字段，不再额外重建同一层固定结构。
9. 新增或修改的测试函数、fixture 和辅助函数应提供一行 docstring，说明业务用途，不重复解释语法。
10. 业务处理函数优先直接完成当前场景所需的参数替换、简单查库、少量造数和后置验证，不为每个技术步骤继续提取一层私有函数。
11. 查询接口可以保留一套公共动态预期构造流程；各业务族负责准备自己的场景后，通过直接调用或 `yield from` 复用该流程。
12. `_` 开头函数不是绝对禁止，但只适用于确实独立且复杂的查询、转换或业务计算；不得用大量私有函数隐藏 Excel 本应直接选择的业务流程。
13. 由 `client.test(case_dict, generator)` 发起的首次请求，已由公共框架在 generator 后处理结束后
    校验 `HTTP_STATUS_CODE` 和完整预期 JSON。业务处理函数不得再对该次请求重复断言
    通用 `code`、`message`、HTTP 200 或完整 JSON 相等；只保留框架无法表达的动态部分匹配、
    数据库副作用、排序稳定性等业务断言。
14. 处理函数为验证幂等、重复请求或双向隔离，在首次请求后直接调用 `session`
    发起的后续请求，只校验当前用例明确要求的业务结果，例如完整 JSON 是否幂等、
    候选顺序是否稳定或双向结果是否隔离。除非 HTTP 状态本身就是当前测试点，否则不机械增加
    `status_code` 断言、响应头断言或其他与测试目的无关的通用校验。
15. `pytest.mark.parametrize` 的写法必须优先贴近最相似的现有模块。现有同类用例未使用
    `ids`、额外 mark、自定义参数显示函数或其他 pytest 展示定制时，不得仅为输出更美观或
    调试更方便而擅自增加。

标准入口优先保持项目既有形式：

```python
@pytest.mark.parametrize(
    'case_dict',
    api_test_data(Path(TEST_DATA_DIR, 'service-name', '接口测试用例_xxx.xlsx')))
def test_xxx(service_client, case_dict: CaseDict):
    service_client.test(case_dict, eval(case_dict['处理数据'] or 'None'))
```

示例中的服务目录和 client 名称应替换为目标服务的现有实现。

## 5. Excel 用例规则

1. 优先复制并调整最相似接口的 Workbook 结构，不自行设计新的 Sheet 组织方式。
2. 接口用例的完整预期返回默认直接放在主 Sheet 的 `预期|json` 列；动态预期也应以
   该 JSON 为骨架，只由处理函数替换变化字段。只有最相似的现有接口 Workbook 已使用独立
   `接口名-预期` Sheet，且复制该结构有明确维护收益时，才能继续使用；否则不新增预期
   Sheet、场景 Sheet 或映射 Sheet。
3. 新增或修改参数 Sheet 前，必须把每一个承载参数值的业务字段列明确归入以下三类之一；`参数说明`、内容类型等框架元数据不属于本分类：
   - 真实接口参数：最终请求会直接发送给接口的字段；
   - 业务定位键：只用于从已明确初始化的共享基线中查询运行时 ID 或目标记录的稳定业务键；
   - 非接口场景配置：场景控制、造数开关、断言开关、预期值、造数结果或可由真实参数推导的辅助字段。
4. 参数 Sheet 默认只保留真实接口参数。能通过真实请求参数表达场景或路由时，不得重复增加 `数据源`、`场景Key` 等非接口字段。
5. 业务定位键只有同时满足以下条件时才允许作为例外放入参数 Sheet：
   - 定位的是本次测试运行已明确创建或初始化的共享基线，而不是环境中偶然存在的数据；
   - 没有可直接使用的真实接口参数、fixture 返回 ID 或更清楚的现有定位方式；
   - 字段含义稳定、名称清楚，不承担场景分支、造数动作或断言控制职责；
   - 处理数据函数会在请求前删除该字段，或整体重建 `case_dict['参数']` 为真实接口结构，最终请求中不包含该定位键。
6. 非接口场景配置不得放入参数 Sheet。应优先通过真实接口参数表达场景，通过 Excel `处理数据` 选择业务处理函数，或由 fixture、专用初始化 Workbook 和 generator 按职责准备数据；不得仅为减少函数入参或方便 `if/elif` 而增加控制列。
7. `处理数据` 列应让审核者直接看出本行所属的业务处理族；不同业务族不得全部填写同一个函数后再由代码隐式分流。
8. 参数 Sheet 的列顺序原则：
   - 符合第 5 条例外的业务定位键在前；
   - 真实接口参数其次；
   - `参数说明` 放在最后。
9. `内容类型`、`HTTP_STATUS_CODE|int` 等框架可默认处理的字段，不需要时可以留空。
10. 每一行必须有独立测试目的，`测试内容` 应能直接作为 Allure 标题定位业务点。
11. 多行可以共享基础数据，但不得依赖上一行产生的状态；参数和预期必须能锁定本行目标。
12. 不允许只修改用例描述而继续验证完全相同的请求和同一份大响应。
13. 用例之间不得插入整行空行，避免 `api_test_data()` 提前停止读取。
14. 动态占位值必须在一个明确位置统一解释，不能散落在多个函数中硬编码。
15. 删除代码分支、参数或场景后，必须同步删除 Excel 中对应的列和值；新增字段时也必须同步代码读取逻辑。
16. 新建、重建或回写项目 `.xlsx` 用例文件时，写入端必须使用 `xlsxwriter`；`openpyxl` 等其他库仅可用于读取，不得执行保存或回写。
17. 使用 `xlsxwriter` 重建已有 Workbook 时，必须保留现有 Sheet 名称和顺序、单元格值和类型、合并单元格、冻结窗格、列宽、行高及必要样式。
18. 修改 Workbook 后，必须依次使用 Microsoft Excel 实际打开、`pylightxl/ExcelReader` 读取和项目 `api_test_data()` 读取并核对用例数量、参数类型和关键值；Excel 能正常打开不代表符合项目读取规范。

### 5.1 专用初始化 Workbook 规则

专用初始化 Workbook 与接口用例 Workbook 职责不同：接口用例 Workbook 描述请求、场景和预期；专用初始化 Workbook 放在 `data/init`，只保存多个用例共享的稳定数据闭包。采用专用初始化 Workbook 时，默认约定：

- 一个业务表一个 Sheet，Sheet 名直接使用数据库表名；
- Sheet 顺序就是满足依赖关系的插入顺序，清理时按相反顺序执行；
- 第一列就是该 Sheet 数据的清理定位键，通常为表主键；
- 第一行使用数据库字段名及项目支持的类型表达，第二行写字段或业务说明，第三行开始存放数据；目标模块已有一致格式时沿用，但不得新增 Python 映射弥补 Workbook 含义不清；
- 单元格填写可直接入库的真实值、固定 ID 和关联 ID；
- SQL `NULL`、空字符串、数值和时间按项目 Excel 读取约定直接表达，不在 fixture 中再次解释；
- 不增加仅供 Python 路由使用的角色列、表顺序 Sheet、字段映射 Sheet 或其他第二套元数据；
- 人工可通过 Sheet 名、顺序、字段和值直接看懂数据闭包，不依赖阅读 fixture 才知道某行代表什么；
- Workbook 只承载稳定基线；当前用例独有的新增、修改和删除仍由测试 generator 管理。

Workbook 文件存在、仓库中存在初始化函数或当前环境已经有数据，都不能单独证明前置数据方案有效。使用 `data/init` Workbook 时还必须确认：

- 根级或模块级 fixture、显式测试 fixture 或其他目标测试必经入口会在本次运行中实际调用初始化方法；
- 单独选择任一目标用例执行时，仍能建立所需共享基线，不依赖先运行其他测试；
- 初始化调用没有被注释，也不受恒不成立、仅供人工临时修改的条件控制；
- 初始化方法返回或保留清理所需的稳定标识，清理责任属于创建该基线的 fixture；
- 历史通用 Workbook 使用业务名称定位运行时 ID 时，只复用已有且稳定的 `common` 初始化方法；新增专用 Workbook 和 fixture 不重新实现名称、角色与外键解析层。

Workbook 已经能够表达的信息，Python 不得再通过常量、字典或分支重复维护。默认直接使用 `excel.file.ws_names` 获取表及顺序，使用首列获取清理键。若无法按上述约定直观表达，应重新判断是否改用现有业务创建函数或稳定公共方法，不得优先在 `conftest.py` 中增加映射和转换层。

历史用例即使采用 Workbook，如果仍依赖整表备份、整表清空、`REPLACE` 覆盖共享数据、环境长期残留数据、失效的初始化入口，或在 Python 中逐字段完成大量类型和空值转换，也只能作为局部思路的参考，不能作为新 fixture 的实现模板。新增测试必须只插入本次拥有的数据，并按明确主键或唯一标识精确清理。

## 6. fixture、Generator 与数据所有权

1. `conftest.py` 中的重型造数必须使用显式 fixture，除非目录内所有测试确实都需要该 autouse fixture。
2. fixture 只创建共享基础数据，并将用例需要的 ID、目标记录集合或上下文直接返回。
3. 接口专属场景数据由处理数据 generator 在 `yield` 前准备，在 `yield` 后清理。
4. generator 的业务语义必须清晰：`yield` 前准备请求参数和场景数据，`yield` 后断言数据库结果或清理；公共流程使用 `yield from` 复用，不手工重复其步骤。
5. generator 后置逻辑必须放在 `try...finally` 可到达的路径中，确保接口或断言失败时仍执行清理。
6. setup 可能部分成功时，应使用当前项目已有的直接 `try...finally` 和删除方法保护已创建数据；没有现有先例时，不新增 `CleanupStack` 等通用清理类。
7. 数据归属必须明确：
   - fixture 清理 fixture 创建的基础数据；
   - 单用例 helper 只清理自己新增的数据；
   - fixture 已整体删除的数据，单用例 helper 不重复恢复或删除。
8. 修改共享已有行时记录原值并恢复；新建且可整体删除的数据优先直接删除。
9. 不依赖环境中碰巧存在或历史运行残留的事件、进程、审核数据及其他业务数据；场景需要的数据应由本次测试运行中的有效 fixture、公共初始化方法或当前 generator 明确创建。
10. 不通过“最大 ID”“最新一条”等环境顺序反查本次 fixture 数据；优先使用 fixture 返回值或本次创建的唯一标识。
11. 不允许为了单条用例重复调用已有基础造数函数创建整套数据，也不重复封装已有删除函数。

### 6.1 `conftest.py` 简洁性硬门禁

`conftest.py` 是共享基础数据的薄编排层，不是新的数据准备框架。单个 fixture 默认只能采用以下两种主结构之一：

| 数据来源 | 默认主结构 |
| --- | --- |
| 现有业务创建函数 | 调用创建函数 → 保存其返回的最小上下文 → `yield` → 调用现有配套删除或恢复方法 |
| 专用初始化 Workbook | 通用读取各 Sheet → 通用插入并记录已成功插入的清理键 → `yield` → 按 Sheet 逆序通用清理 |

除 `try...finally`、已插入 ID 非空判断等清理安全判断外，fixture 默认不得包含业务条件分支。出现下列任一情况时，视为当前实现未通过结构审核，必须停止继续增加代码并重新设计：

- 新增仅供该 fixture 使用的表顺序常量、Sheet 列表、表名映射、主键映射或字段/角色映射；
- Workbook 已包含某项信息，Python 又通过常量、字典、循环前置配置或分支重复表达；
- 新增仅被该 fixture 调用一次的包装函数、私有 helper、通用 context、恢复注册表或清理栈；
- 根据 Sheet 名、表名、场景名、测试标题或角色执行多组 `if/elif`；
- 在 fixture 中解释 Excel 占位符、构造接口预期或准备单用例差异；
- 在 fixture 中逐字段转换本可由 Workbook 表头类型、`null`、空串和真实值直接表达的数据；
- 读取 Workbook 后仍需动态回填多表外键、按角色查询 ID，或通过“最大 ID”“最新一条”重新定位自身数据；
- 未检查 `Excel`、`DB_CONN` 或已有 `common` 方法，就自行新增读取、插入、删除、恢复的包装层；
- fixture 无法直接按“读取或创建、插入或保存上下文、`yield`、清理”四段理解；
- 实际新增结构超过编码前声明的预算。

命中硬门禁后，必须按以下顺序重新检查，不能继续用 helper、常量或分支修补当前方案：

1. 能否直接复用已有业务创建及删除函数；
2. 能否把稳定的表名、顺序、字段、类型、ID 和关联值放回 Workbook；
3. 能否直接使用 `Excel.get_asdict()`、`DB_CONN` 的批量能力或已有公共方法；
4. 当前数据是否实际属于单用例 generator，而不是共享 fixture。

确实无法满足默认结构时，必须在继续修改前说明不可避免的业务原因、被否决的更简单方案、最相似的项目先例以及预计新增的结构；没有这些证据，不得突破门禁。

### 6.2 Excel 与代码必须作为一个实现共同审核

简洁性不按单个文件判断。不得为了让 `conftest.py` 看起来短而把大量路由元数据塞进 Excel，也不得为了让 Excel 看起来简单而在 Python 中维护第二套表结构、角色和关联关系。审核时必须同时阅读 Workbook、fixture 和测试 generator，并确认：

- Workbook 直观声明稳定基线；
- fixture 对所有 Sheet 或创建结果执行通用编排；
- generator 只管理当前业务族或当前用例的差异；
- 清理逻辑只处理本层自己创建或修改的数据；
- 同一事实只有一个维护位置。

如果审核者必须在多个常量、映射、分支和 Sheet 之间来回推导才能理解数据关系，即使代码行数较少，也视为实现复杂，必须重新设计。

## 7. 函数与 helper 精简规则

新增函数前必须同时回答：

1. 是否已有函数可以直接调用？
2. 该函数是否表达完整、稳定的业务动作？
3. 它是否被多次调用，或确实显著降低了主流程复杂度？
4. 参数、返回值、副作用和清理方式是否清晰？

具体要求：

- 仅调用另一个函数、不增加业务语义的兼容包装函数应删除。
- 仅给 `case_dict['参数']` 或 `case_dict['预期']` 赋少量固定字段的函数，直接写更清楚时不要提取。
- 不为每条 Excel 用例创建独立函数；但数据准备、验证口径或清理责任不同的稳定业务族，应使用不同的处理函数，不能为追求函数数量少而塞入一个总路由函数。
- 处理函数名称应表达业务目的，并优先作为 Excel `处理数据` 的直接入口；纯技术步骤才考虑作为内部 helper。
- 公共成功、失败或动态预期函数应通过 `yield from` 被业务处理函数复用，避免复制同一套请求前后逻辑。
- 相邻几行只使用一次的中间转换逻辑，默认保留在调用处。
- 多个分支共享且复杂的业务计算可以提取，但函数名必须表达业务规则。
- 人工能够保证且不会破坏共享数据的互斥组合，不额外增加防御性校验。
- 可能导致误删共享数据、污染环境或产生难定位错误的条件，仍必须保留必要校验。
- 会写库的公共 helper 必须返回清理所需 ID，或提供现有风格一致的配套删除/恢复方法。
- helper 不直接理解某个 Excel 的占位符，也不直接构造某个接口的固定返回外壳。

## 8. DB、SQL 与动态预期

1. 优先使用 `DB_CONN` 已有查询和增删改方法。
2. 原生 SQL 必须参数化；动态 `IN` 只拼接 placeholders，值通过参数传入。
3. 查询只选择断言或后续处理需要的字段，不用 `SELECT *` 构造接口预期。
4. 动态预期必须来自需求、数据库设计和已确认业务口径，不能从偶然接口返回反推规则。
5. 字段来源、主客队方向、状态优先级、排序和分页等规则，应锁定目标数据后独立验证。
6. Excel 已有固定返回结构时，动态预期函数只填充变化的数据字段。
7. 断言失败信息必须包含实际值、预期值、关键 ID 或差异内容。
8. 不得为了让用例通过而扩大预期范围、删除关键字段或忽略真实差异。

## 9. 代码风格

1. import 按标准库、第三方库、项目模块分组。
2. 函数和变量使用 `snake_case`，类使用 `PascalCase`，常量使用 `UPPER_CASE`。
3. 使用项目当前 Python 版本支持的类型标注风格。
4. 注释说明业务原因和边界，不解释显而易见的语法。
5. 不保留未使用 import、变量、函数、调试 SQL、临时 `print` 或大段注释代码。
6. 不使用无意义命名，例如 `test1`、`data2`、`tmp_func`。
7. 不使用 bare `except:`；确需汇总清理异常时，保留具体错误上下文。
8. 不在测试代码中硬编码服务地址、密码或其他敏感配置。

## 10. 修改后强制验证与规范审核

功能验证与结构审核是两个独立门禁。根据改动范围完成以下验证，不得只检查代码能否保存，也不得因为 pytest 通过而跳过规范审核：

1. 查看 `git diff`，确认没有覆盖用户修改和无关文件。
2. 对修改的 Python 文件执行 `py_compile` 或项目等价语法检查。
3. 确认修改的 Excel 由 `xlsxwriter` 写入，未使用 `openpyxl` 等其他库保存或回写。
4. 使用 Microsoft Excel 实际打开修改后的 Workbook，确认文件、Sheet 和单元格内容可正常访问。
5. 使用 `pylightxl/ExcelReader` 和项目 `api_test_data()` 读取修改后的 Excel，核对：
   - 用例数量；
   - Sheet 关联；
   - 参数类型；
   - 空值、`0`、`null`、列表和 JSON 的转换结果。
6. 执行目标脚本的 `pytest --collect-only`，确认参数化数量正确。
7. 数据库写入型用例必须串行执行；未经证明具备数据隔离时禁止并行运行。
8. 新增或修改测试实现、fixture 或 Workbook 后，必须至少完整串行执行一次目标测试模块；`--collect-only`、单条冒烟或抽取部分用例不能代替完整执行。
9. 发生失败时，必须结合请求、需求或确认 SQL、数据库实际数据、接口返回和被测实现，将原因明确归类为测试代码错误、前置数据错误、环境问题或接口缺陷；不得为了通过而直接修改正确预期。
10. 涉及新增、修改、唯一约束或清理时，代表性用例至少连续执行两遍，并在模块结束后按本次固定 ID 或唯一标识查询残留数据。
11. 复查 Excel 与代码是否仍存在已删除分支对应的遗留列、值、函数或 import。
12. 对所有新增和修改执行代码变更闭环验证：
   - 重新读取磁盘上的最终文件，不能只依据编辑工具返回成功、内存内容或替换次数判断修改已落盘；
   - 正向确认目标函数、调用方式、参数和分支已经生效；
   - 反向搜索被替代的旧函数、旧调用、旧字段和错误副作用是否已经完全消失；
   - 同时检查函数定义、所有调用方和组合调用路径，避免只修改调用方或只修改被调用方；
   - 对共享可变对象的 `pop()`、`clear()`、`update()` 等原地修改，确认后续调用不会再次依赖已删除或已覆盖的数据；
   - 涉及 generator、`yield from`、fixture 或前后置清理时，至少走通一次完整控制流，并验证正常路径和部分失败路径都能进入预期清理逻辑。
13. 与编码前选定的相似模块重新对比；存在结构偏离时必须说明理由。

### 10.1 完工后的规范符合性审核

实现完成后必须回到编码前方案，重新审核最终实现，而不是只确认功能结果。审核至少包括：

1. 将实际新增的 fixture、helper、常量、Sheet、控制列和业务分支与编码前预算逐项比较；
2. 用最终代码重新判断数据准备方式是否仍然正确，是否已经出现应从业务创建函数切换到 Workbook、从 Workbook 切换到业务创建函数，或下沉为单用例直接造数的信号；
3. 将 fixture 中每段代码归入“读取或创建、插入或保存上下文、`yield`、清理”之一，无法归类的代码必须说明归属；
4. 检查 Workbook 已表达的信息是否又在 Python 中重复，或 Python 已能返回的信息是否又在 Excel 增加控制字段；
5. 检查自定义循环、转换和包装是否已有 `Excel`、`DB_CONN` 或 `common` 方法可以直接替代；
6. 检查单用例差异是否错误进入共享 fixture，或 fixture 创建的数据是否又被 generator 重复清理；
7. 检查参数 Sheet 各业务字段列是否已归类为真实接口参数或必要业务定位键，最终请求是否已移除所有定位键且没有非接口场景配置；
8. 使用 `data/init` Workbook 时，从目标测试入口走查一次初始化调用链，确认单独执行用例时入口实际生效；
9. 重新读取最终 Workbook、fixture、测试文件和调用链，确认三者配合仍是总复杂度最低且职责清楚的实现。

审核结论必须明确给出以下结果，不能省略：

- 功能验证执行了什么，结果如何；
- 数据准备方式是否符合 2.1 节选择边界；
- `conftest.py` 是否命中 6.1 节任何硬门禁；
- Excel 与代码是否存在重复事实源；
- 是否存在不符合规范的点；没有也应明确写“未发现”。

编写或修改任务中发现不符合项时，必须先修正再宣布完成；不能以“测试已通过”“代码已经能运行”或“以后再优化”为理由保留。任务仅要求代码审核、未授权修改时，不直接改动，但必须按“文件与行号、违反条款、影响、建议修改”报告范围内的不符合项。确需保留例外时，必须明确记录业务原因、替代方案为何不可行以及适用边界。

## 11. 禁止事项

- 禁止未调查现有模块就直接设计整体框架。
- 禁止未完成数据闭包和准备方式决策就先编写 `conftest.py`，再反向补 Workbook、常量或 helper。
- 禁止已有业务创建函数和配套清理方法能够满足需求时，在 fixture 中手工重建同一正常业务对象链。
- 禁止以通用工程最佳实践为由，无依据新增类、清理栈、上下文对象或中间层。
- 禁止新增没有调用方或只有转发作用的函数。
- 禁止重复封装项目已经提供的创建、删除或恢复函数。
- 禁止把 Workbook 已表达的 Sheet 顺序、表名、主键、字段、固定值或角色关系再次写成 Python 常量和映射。
- 禁止使用表级分支、逐字段转换和一次性 helper 修补本应通过 Workbook 真实值或已有业务函数解决的数据准备问题。
- 禁止在参数 Sheet 中增加场景控制、造数开关、断言开关、预期值、造数结果或可由真实请求参数推导的辅助列。
- 禁止把业务定位键保留到最终接口请求中，或使用业务定位键承担二次场景路由职责。
- 禁止让大量或全部 Excel 用例进入同一个总处理函数，再通过 `场景Key`、用例标题或动作字段进行二次业务路由。
- 禁止用大量 `_` 私有中间函数、通用 context 或恢复注册表掩盖本应由业务处理函数直接表达的场景流程。
- 禁止在没有项目先例和维护收益时增加额外 Sheet。
- 禁止将本应由请求参数、fixture 上下文或动态查库定位的球队、比赛、赛事、赛季、
  关系 ID、ID 数组或预期计数，直接硬编码到 Excel `处理数据` 表达式。
- 禁止为了减少函数内的动态查询，给业务处理函数增加可从 `case_dict` 推导的冗余入参。
- 禁止在测试入口中用 `assert fixture_data`、占位赋值或 `pass` 表示 fixture 已执行；pytest 形参注入本身就是执行入口。
- 禁止在 `client.test()` 的 generator 后处理中，重复实现框架已对首次请求执行的 HTTP 状态、
  通用 `code/message` 和完整 JSON 校验。
- 禁止在后续 `session` 请求中机械增加与当前业务测试点无关的 `status_code`、响应头或通用字段断言。
- 禁止在同类现有用例无先例时，擅自给 `pytest.mark.parametrize` 增加 `ids` 或其他纯展示性配置。
- 禁止分别以“Python 很短”或“Excel 很简单”作为实现简洁的证据；必须审核两者配合后的总复杂度和事实源数量。
- 禁止让单条用例依赖另一条用例先执行。
- 禁止依赖环境中偶然存在的数据完成关键场景。
- 禁止因 Workbook 或初始化函数存在就认定前置数据已准备；被注释、目标用例不会触发或由恒不成立条件控制的入口均视为无效。
- 禁止未核对 Git 历史和完整数据链路，就把不同迭代的 Workbook、测试脚本、fixture 或公共方法拼接成同一个参考实现。
- 禁止并行运行会写入同一数据库造数范围的 pytest 命令。
- 禁止修改代码后遗漏同步更新 Excel，或修改 Excel 后遗漏代码清理。
- 禁止以语法通过、接口返回正常或 pytest 通过为理由跳过规范审核，或保留未说明的结构超预算实现。
- 禁止把一次审核结论、临时重构方案或单文件实现快照固化为子级 `AGENTS.md`。
