# 比赛监控列表 - 查询结果数据准备需求分析（V2）

> **分析对象**：`GET /s-match` 查询比赛列表接口  
> **分析范围**：查询结果 a~s 字段中**接口实际返回**的数据准备（排除前端处理逻辑）  
> **分析时间**：2026-06-22  
> **核心原则**：只分析与接口返回值相关的数据准备，前端展示逻辑（时间格式化、置灰、超链接样式、状态文案映射等）不在本接口测试范围

---

## 一、关键原则：接口返回 vs 前端处理

本接口是**纯数据查询接口**，职责是：从多张表取数、按业务规则聚合后返回结构化 JSON。前端负责所有"怎么显示"的逻辑。

### 接口职责边界

| 接口负责（数据准备范围） | 前端负责（不在本接口测试范围） |
|--------------------------|-------------------------------|
| 从数据库取原始值 | 文案映射（如 status_id → 中文状态） |
| 按业务规则计算字段值 | 时间格式化（`10'`、`45'+1'`） |
| 三级优先级取值（如比分） | 置灰/超链接样式 |
| 主客队对调后的 ID/名称/排名 | 显示/隐藏逻辑（如空值不显示） |
| 统计各类计数（告警/变更/事件等） | 排名空值时"不显示"的渲染 |
| 返回 `beitaiFootballMatchLiveDTO` 原始对象 | 直播时钟的拼接显示规则 |

**所以像 `beitaiFootballMatchLiveDTO` 这种，接口只是把数据库的 `status/matchClock/stoppageClock` 原样返回，至于怎么拼成 `45'+1'` 是前端的事，我们接口测试只验证返回的三个原始字段是否正确。**

---

## 二、字段分类：按数据准备必要性

### 2.1 A 类：接口直接取单表字段，造数时已覆盖（无需额外准备）

这些字段在 `create_bd_batch_matchup` 造数后即有值，接口直接 SELECT 返回。

| 需求字段 | 接口字段 | 数据来源 | 造数状态 |
|----------|----------|----------|----------|
| **a 编号** | `matchNo` | `bd_batch_matchup.matchup_unique_no` 截取流水号 | ✅ 造数自动生成 |
| **b 运动项目** | `sportId` | `bd_batch_matchup.sport_id` | ✅ 造数指定 |
| **e 轮次** | `bdRound` | `bd_batch_matchup.bd_round` | ✅ 造数生成 |
| **f 开赛时间** | `matchTime` | `s_match.match_time` | ✅ 造数指定 |
| **i 开奖状态** | `prized` | `s_match.status_id IN (1206,1606,1306,1406,1506)` 计算 | ⚠️ 需按场景调整 status_id |

### 2.2 B 类：接口需聚合多表数据，需针对性造数（本分析重点）

| 需求字段 | 接口字段 | 复杂度 | 核心数据来源 |
|----------|----------|--------|--------------|
| **c 赛事级别** | `relationsSeason.competitionLevel` | ⭐ | `m_season.competition_level` |
| **g 主客队名称** | `homeTeamNameZh`/`awayTeamNameZh`/`homeSeasonBdTeamName`/`awaySeasonBdTeamName` + ID 字段 | ⭐⭐⭐⭐ | `m_team` + `r_season_team` + **主客队对调计算** |
| **h 主客队排名** | `homePosition`/`awayPosition` | ⭐⭐ | `s_match.home_position` + **对调后映射** |
| **i 比赛基础状态** | `matchBaseStatus` | ⭐⭐ | `s_match.status_id` 计算 |
| **j 半场/全场比分** | `homeScore`/`awayScore`/`homeScoreHalf`/`awayScoreHalf` | ⭐⭐⭐⭐ | **三级优先级计算** |
| **k 赛果状态** | `matchResultStatus` | ⭐⭐⭐ | 三态计算 |
| **m 告警** | `warningCount` | ⭐⭐⭐ | `s_event` + `task` 统计 |
| **n 变更** | `changeCount` | ⭐⭐⭐ | `s_event` + `task` 统计 |
| **o 预警** | `preWarningCount` | ⭐⭐ | `s_event` + `task` 统计 |
| **p 事件** | `eventCount` | ⭐⭐⭐⭐ | `s_event` 开售后统计 |
| **q 备注** | `remarkCount` | ⭐ | `m_match_remark` 统计 |
| **贝泰直播对象** | `beitaiFootballMatchLiveDTO` | ⭐⭐ | `beitai_football_match_live` 原始字段 |
| **比赛事件对象** | `seventEntity` | ⭐⭐⭐⭐ | `s_event` + `task` 开售后取优先级最高 |

### 2.3 C 类：前端逻辑，接口不涉及（本分析排除）

| 需求描述 | 排除原因 |
|----------|----------|
| 直播时间显示 `10'` / `45'+1'`（需求 2.i.i/ii/iii） | 纯前端根据 `matchClock`/`stoppageClock` 拼接，接口只返回原始字段 |
| 级别为空时"不显示"（需求 2.c） | 前端渲染逻辑，接口返回空即 `competitionLevel: null` |
| 排名无则"不显示"（需求 2.h） | 前端渲染，接口返回 null |
| 比分无比分时显示"-"（需求 2.j） | 前端渲染，接口返回 null |
| 告警/变更/预警/事件/备注 条数为 0 时"置灰"（需求 2.m/n/o/p/q） | 前端样式，接口只返回数字 |
| 各字段的"超链接样式"（需求 2.d/g/m/n/o/p/q） | 前端交互 |
| **s 置顶状态**（需求 2.s） | 用户行为，本接口未返回该字段（见待确认） |

### g. 主客队名称 + 顺序（核心难点 ⭐⭐⭐⭐）

#### 接口实际返回逻辑

接口返回 4 个名称字段 + 4 个 ID 字段：

```text
名称字段（接口原样返回，不做"北单全称 vs 球队全称"的兜底判断）：
  homeTeamNameZh        ← m_team.name_zh（display_home_team_id 对应）
  awayTeamNameZh        ← m_team.name_zh（display_away_team_id 对应）
  homeSeasonBdTeamName  ← r_season_team.season_bd_team_name
  awaySeasonBdTeamName  ← r_season_team.season_bd_team_name

ID 字段（体现对调结果）：
  homeTeamId            ← display_home_team_id（计算后的主队）
  awayTeamId            ← display_away_team_id（计算后的客队）
  bdScheduleHomeTeamId  ← bd_batch_matchup.home_team_id（赛程原始主队）
  bdScheduleAwayTeamId  ← bd_batch_matchup.away_team_id（赛程原始客队）
  bdMatchupHomeTeamId   ← s_match.bd_matchup_home_team_id
```

> **注意**：需求说"名称显示比赛所属赛季关联的球队北单全称，为空时显示球队全称"——这个"为空时回退"的判断是**前端**做的。接口同时返回 `homeTeamNameZh` 和 `homeSeasonBdTeamName` 两个字段，前端自行决定用哪个。所以接口测试只需验证**两个名称字段都正确返回**。

#### display_home_team_id 计算逻辑（接口核心）

```sql
-- match_base CTE 中的计算
display_home_team_id = CASE
    WHEN bm.match_result_status = 1                          -- 已确认
        THEN bm.home_team_id                                  -- 用赛程主队
    WHEN emc.check_id IS NOT NULL 
     AND emc.bd_matchup_home_team_id IS NOT NULL             -- 用户已审核
        THEN emc.bd_matchup_home_team_id                      -- 用审核主队
    ELSE sm.home_team_id                                      -- 默认用 s_match 主队
END
```

#### 数据准备方案（4 种核心场景）

**场景1：未审核，默认顺序**
```sql
-- 默认状态，无需额外操作
-- 前提：match_result_status = 0，当前用户无 event_match_check
-- 预期：homeTeamId = s_match.home_team_id
```

**场景2：已审核，主客队对调**
```sql
INSERT INTO event_match_check (
    check_source_id, check_type, bd_matchup_home_team_id,
    change_info, create_account, update_time
) VALUES (
    '<match_id>', 2, <原客队team_id>,   -- 关键：指向客队即对调
    NULL, 'zhangyudi', NOW()
);
-- 前提：match_result_status = 0
-- 预期：homeTeamId = 原客队ID，awayTeamId = 原主队ID
```

**场景3：已确认**
```sql
UPDATE bd_batch_matchup
SET match_result_status = 1
WHERE match_id = <match_id>;
-- 预期：homeTeamId = bd_batch_matchup.home_team_id
```

**场景4：北单全称缺失（验证两个名称字段都返回）**
```sql
UPDATE r_season_team SET season_bd_team_name = NULL 
WHERE manual_team_id = <team_id> AND manual_season_id = <season_id>;
-- 预期：homeSeasonBdTeamName = null，homeTeamNameZh 仍有值
```

#### 测试覆盖点
- [ ] 未审核 → 4 个名称字段 + 5 个 ID 字段均正确返回
- [ ] 已审核对调 → ID 对调，名称随之对应
- [ ] 已确认 → ID 为赛程主队
- [ ] 北单全称缺失 → `homeSeasonBdTeamName` 为 null，`homeTeamNameZh` 正常

### i. 比赛基础状态 + 开奖状态

> ⚠️ 需求 2.i 中关于足球"比赛中"显示 `match_clock`/`stoppage_clock` 的拼接规则（`10'`、`45'+1'`）是**前端逻辑**，接口只返回 `matchBaseStatus`（数字）和 `beitaiFootballMatchLiveDTO`（原始对象）。

#### 接口实际返回

**字段1：matchBaseStatus（基础状态，去掉北单后两位）**
```sql
matchBaseStatus = mb.status_id - MOD(mb.status_id, 100)
```

**字段2：prized（开奖状态）**
```sql
prized = CASE WHEN mb.status_id IN (1206,1606,1306,1406,1506) THEN 1 ELSE 0 END
```

**字段3：beitaiFootballMatchLiveDTO（原始直播对象）**
```sql
-- _query_beitai_live_dto_map 中
SELECT bl.match_id, bl.status, bl.match_clock, bl.stoppage_clock
FROM beitai_football_match_live bl
WHERE bl.match_id IN (<beitai_match_id>)
```
接口**原样返回**数据库的 4 个字段，拼装成 DTO 对象。

#### 数据准备方案

**matchBaseStatus 场景**
```sql
-- 未开赛（1000）
UPDATE s_match SET status_id = 1003 WHERE match_id = <match_id>;
-- 接口返回：matchBaseStatus = 1000, prized = 0

-- 已完赛已开奖（1206）
```

```sql
-- 接口返回：{matchId, status:"2nd_half", matchClock:"67:23", stoppageClock:null}

-- 无直播数据（不插入或删除）
-- 接口返回：beitaiFootballMatchLiveDTO = null
```

#### 测试覆盖点
- [ ] 各种 status_id → matchBaseStatus 和 prized 计算正确
- [ ] 有贝泰直播数据 → DTO 对象完整返回 4 个字段
- [ ] 无贝泰直播数据 → DTO 为 null

### j. 半场/全场比分（⭐⭐⭐⭐ 三级优先级）

#### 接口实际返回逻辑

```sql
homeScore = CASE
    WHEN match_result_status = 1                              -- 已确认
        THEN bd_batch_matchup.home_score
    WHEN emc.check_id IS NOT NULL                             -- 用户已审核
        THEN JSON_EXTRACT(emc.change_info, '$.homeScore')
    WHEN display_home_team_id = sm_home_team_id               -- 未对调
        THEN sm.home_score
    WHEN display_home_team_id = sm_away_team_id               -- 对调后取客队比分
        THEN sm.away_score
    ELSE sm.home_score
END
```
接口已实现三级优先级 + 对调映射，**返回最终的比分数字**。

#### 数据准备方案（覆盖优先级）

**场景1：系统采集比分（优先级3，默认）**
```sql
UPDATE s_match SET home_score=2, away_score=1, 
                   home_score_half=1, away_score_half=0
WHERE match_id = <match_id>;
-- 前提：match_result_status=0，无 event_match_check
-- 接口返回：homeScore=2, awayScore=1
```

**场景2：用户审核比分（优先级2）**
```sql
-- 1. s_match 有系统比分（如上）
-- 2. 创建审核记录，change_info 含审核比分
INSERT INTO event_match_check (
    check_source_id, check_type, bd_matchup_home_team_id,
    change_info, create_account, update_time
) VALUES (
    '<match_id>', 2, <home_team_id>,
    '{"homeScore":3,"awayScore":2,"homeScoreHalf":1,"awayScoreHalf":1}',
    'zhangyudi', NOW()
);
-- 接口返回：homeScore=3, awayScore=2（覆盖系统比分）
```

**场景3：已确认比分（优先级1）**
```sql
UPDATE bd_batch_matchup SET match_result_status=1,
    home_score=4, away_score=3, home_score_half=2, away_score_half=1
WHERE match_id = <match_id>;
-- 接口返回：homeScore=4, awayScore=3（最高优先级）
```

**场景4：无比分**
```sql
UPDATE s_match SET home_score=NULL, away_score=NULL,
                   home_score_half=NULL, away_score_half=NULL
WHERE match_id = <match_id>;
-- 前提：match_result_status=0，无 event_match_check
-- 接口返回：homeScore=null（前端再显示"-"）
```

#### 测试覆盖点
- [ ] 三级优先级：确认 > 审核 > 采集
- [ ] 主客队对调时比分正确反转
- [ ] 无比分返回 null

### n. 变更数（changeCount）

#### 接口实际返回逻辑
```sql
SELECT COUNT(*)
FROM task t JOIN s_event se ON se.event_id = t.event_id
```

### p. 事件数（eventCount）⭐⭐⭐⭐

#### 接口实际返回逻辑（开售后 + 贝泰/纳米渠道）
```sql
-- 1. 找开售时间
WITH opening AS (
    SELECT source_id, MAX(create_time) AS openingTime
    FROM s_event
    WHERE source_id IN (...)
      AND event_type = 0
      AND reason_title = '比赛状态变更（开售）'
      AND (identity_data LIKE '%贝泰%' OR identity_data LIKE '%纳米%')
    GROUP BY source_id
)
-- 2. 统计开售后的异常/预警
SELECT COUNT(*)
FROM s_event se JOIN opening ON opening.matchId = se.source_id
WHERE se.event_type IN (1, 3)
  AND (se.identity_data LIKE '%贝泰%' OR se.identity_data LIKE '%纳米%')
  AND se.create_time >= opening.openingTime
```
接口**返回数字**。

#### 数据准备方案

**有开售后事件**
```sql
-- 1. 开售事件（时间较早，identity_data 含渠道）
INSERT INTO s_event (event_id, event_type, source_type, source_id,
                     reason_title, identity_data, create_account, create_time)
VALUES ('<open_eid>', 0, 's_match.match_id', <match_id>,
        '比赛状态变更（开售）',
```
