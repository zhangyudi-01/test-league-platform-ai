# 测试点/测试用例编写规范（必读）

> 适用范围：本项目所有模块的迭代深度分析、测试点、测试用例编写。
> 背景：由 MOD-06-01-04 赛果审核第 12 轮冲刺的教训沉淀——分析过程中曾把"类推/反推得出的结论"直接写进测试点断言（冰球加时取 ot、融合优先级必跟纳米、下标语义），被质疑后修正。本规范明确正确的处理流程。

---

## 一、核心原则：测试点必须以需求为准

1. **测试点/测试用例中的每一条断言，依据只能是以下四类之一**，且需可追溯：
   - ① **需求原文**：模块需求包、PRD、《数据模型设计》等需求文档的明文规定（首选，标注文档与位置）；
   - ② **需求方/开发确认**：用户在沟通中明确给出的结论（标注"已确认"与来源）；
   - ③ **接口/数据契约**：OpenAPI 规范、开发提供的枚举/字段定义（如 dataSource 枚举 NAMI(1)/BEITAI(3)）；
   - ④ **实库既有数据形态**：仅用于"落库格式/存量数据兼容"类断言（如 change_info JSON 键结构、-1:-1 固定值），且须标注核验日期。
2. **推断内容一律不得直接作为断言**。推断 = 从 A 运动/数据源的规则类推到 B、从数据样本反推规则、从备注推导为绝对规则等。推断只能进入"待确认问题"清单。

## 二、遇到三种典型情形的处理流程

### 情形 1：需求明确写了
- **处理**：按需求原文写测试点，断言措辞与需求一致，备注标注需求出处（文档名+章节/表格）。
- 示例：`贝泰标签及非足球显示 s_match 开奖用比分`（需求原文"显示标准化比赛信息中的比赛状态和开奖用的比分"）。

### 情形 2：需求写了但自身标注"待确认/待定"
- **处理**：**仍然按需求写的执行**（需求当前版本即契约），在测试点备注中同步标注"需求标注待确认"；同时把该问题列入待确认清单交需求方拍板。
- 示例：橄榄球"优先取 scores.ot[0]，为空时取 scores.ft[0]"——需求单元格自带"待确认"标记，按需求写+标注，并列入待确认清单。

### 情形 3：需求没写 / 我靠推断补的
- **处理**：**测试点不写该断言**（或只写需求已覆盖的部分），推断内容单独整理为"待确认问题"输出给用户，由用户去找需求方/开发确认；确认结论回来后再补进测试点。
- 示例（教训）：冰球 status=105 加时完场取值——需求冰球列只写 scores.ft，我把橄榄球列的 ot 优先规则类推过去写成断言，错误。正确做法：冰球测试点只断言"取 scores.ft"，105 场的加时口径作为待确认问题提出。

## 三、推断性内容的正确出口：待确认问题清单

1. **出口位置（两处都要有，且编号互通）**：
   - 迭代深度分析报告的"遗留待确认问题"章节（分析阶段就应提出——**推断在分析时产生，就该在分析时暴露**，不能等到写测试点被发现）；
   - 测试点文档末尾的"待确认问题"章节（引用分析报告编号，不重复展开）。
2. **每条待确认问题必须包含**：问题描述、推断来源（从哪个文档哪条规则/哪批数据推出来的）、为什么存疑（需求未写/实库反例/类推跨度）、建议找谁确认（需求方 or 开发）。
3. **待确认 ≠ 测试空白**：需求已覆盖的部分照常测试；待确认部分在用例中可做"探索性验证"（记录实际表现、不断言对错），并明确标注【探索性验证】。

## 四、实库/接口信息的使用边界

| 允许 | 不允许 |
| --- | --- |
| 用实库验证需求规则的可行性（验证通过可增强备注可信度） | 用实库样本反推"规则"并写成断言（如下标语义） |
| 用实库数据形态断言落库格式、存量兼容（JSON 键、固定值） | 用实库例外推翻需求明文后自行改写断言（例外只进待确认清单） |
| 用 OpenAPI/开发枚举做契约断言 | 把文档滞后差异当需求（以实库/OpenAPI 为准的结论须标注依据类型③） |

## 五、文档体系与产出顺序（每模块迭代）

```
1. 00-module-requirement-pack.md     需求包（输入）
2. 01-迭代深度分析报告.md            分析：需求拆解 + ✅更新识别 + 数据形态核验
                                      ★ 推断性问题在本步骤就进入"遗留待确认问题"章节
3. test-points/01-迭代测试点.md      测试点：断言仅来自四类合法依据
                                      末尾"待确认问题"引用分析报告编号
4. test-points/测试用例-*.xlsx       用例：前置条件/步骤/预期 与测试点一一对应
5. 用户确认回流                      待确认问题获得答复 → 更新测试点/用例，并在
                                      "已确认结论"章节记录答复与来源
```

## 六、自查清单（测试点/用例发出前逐条过）

- [ ] 表格结构：是否严格为 4 列（`序号 | 测试项 | 测试点 | 备注`），且**每一行的“测试项”均已明确填写（严禁留空）**？
- [ ] 排版高亮：每条测试点是否以 `**【核心考点】**` 开头？关键条件/结果是否已 `**加粗**`？表名、字段名、特殊值（如 `` `m_team` ``、`` `NULL` ``、`` `""` ``、`` `utf8mb4_bin` ``）是否已用 `` ` ` `` 包裹？
- [ ] 语言凝练度：是否做到了语句简短精炼、直击校验核心，杜绝长篇大论与机械啰嗦重复？
- [ ] 备注列恰当性：备注列是否仅用于填写简短的技术验证点/防漏测提醒（如 `sql验证`、`防后端只校验 IS NULL 导致的漏测。`），未写入“需求 x.x.x”等过程痕迹？
- [ ] 范围纯粹性：是否**只保留本次迭代改动相关**的测试点，剔除了无关的历史存量功能？
- [ ] 每条断言能指出依据类型（①需求原文/②已确认/③契约/④数据形态），且无主观类推或反推？
- [ ] 待确认问题是否同时出现在分析报告与测试点文档，编号互通？用户已确认结论是否已归档至文末？

## 七、测试点格式与表达红线（标杆范式沉淀）

### 1. 表格列格式红线（严禁擅增改列、严禁测试项留空）
- **列数严格固定为 4 列**：`| 序号 | 测试项 | 测试点 | 备注 |`，严禁自行增删列或给表头加括号修饰。
- **测试项逐行必填（严禁留空）**：**每一行的“测试项”列都必须填写**，严禁因为与上一行同属一个模块就留空！推荐采用 `阶段/功能点-校验维度` 的精炼分类命名（如 `用户确认-拦截校验`、`用户确认-业务规则`、`用户确认-逻辑查重`、`用户确认-覆盖更新`、`用户确认-防篡改`、`技术边界-空字符容错`、`技术边界-字符严格校验`、`技术边界-极限并发`）。

### 2. 测试点排版与凝练度规范（拒绝长篇大论）
- **句首提纲加粗标签**：每条测试点必须以 `**【核心考点短语】**` 开头（如 `**【未补全强拦截】**`、`**【自身重名误伤放行】**`），一眼看清测试重心。
- **正文重点加粗与代码包裹**：
  - 关键前置特征、阈值条件、核心动作与预期结论使用 `**加粗**` 突出（如 `**全称>20，简称>16**`、`**不执行更新**`、`**全量覆盖更新**`）；
  - 凡涉及物理表名（如 `` `m_team` ``、`` `r_season_team` ``）、字段名、特殊字面量（如 `` `NULL` ``、`` `""` ``、`` `acmilan` ``）、字符集/异常码（如 `` `utf8mb4_bin` ``）等技术标识，必须使用反引号 `` ` ` `` 包裹。
- **表达简短精炼**：用 1~2 句短句讲清“针对什么场景/操作 → 校验什么核心结果”，严禁长篇大论、严禁写入繁琐的 UI 点击流水账或大段 SQL 语句。

### 3. 备注列编写规范（点睛技术提醒，拒绝过程痕迹）
- **该写什么**：备注列用于填写简短精悍的**技术验证手段、底层防漏测提醒或专项测试目的**（例如：`sql验证`、`防后端只校验 IS NULL 导致的漏测。`、`字符集匹配与Trim清洗测试。`、`极端场景下代码鲁棒性测试。`）。常规业务校验无需额外补充时直接留空。
- **严禁写什么**：严禁在备注列写入“需求 1.3.2”、“已确认：问题1选A”等需求溯源编号或沟通流水账（沟通结论统一放在文末“已确认结论”章节）。

### 4. 标杆示例（参考《赛事运营系统第十轮冲刺测试方案》）
```markdown
| 序号 | 测试项 | 测试点 | 备注 |
| --- | --- | --- | --- |
| 1 | 用户确认-拦截校验 | **【未补全强拦截】** 针对带有空值的球队，用户**不填补**直接点击【关联】并【确认】。校验系统成功阻断入库，强提示全称/简称不能为空。 |  |
| 2 | 用户确认-拦截校验 | **【超长及当前赛季重名拦截】** 针对空值球队，用户填补名字超长（**全称>20，简称>16**），或填补的名称与**当前赛季已有的其他球队重名**。校验点击【确认】时系统能否准确弹窗拦截。 |  |
| 3 | 用户确认-业务规则 | **【全局重名时的“静默跳过”与“连坐机制”】** 针对空值球队，填补的名称未与本赛季重名，但与**系统内其他赛季/其他球队**重名。校验点击【确认】时，系统不报错、不弹窗，提示关联成功；但底层 `m_team` 表**不执行更新**（遵循一假全假的连坐跳过规则）。 | sql验证 |
| 4 | 用户确认-逻辑查重 | **【自身重名误伤放行】** 针对仅一项为空的球队，用户补全空项，**保持原本有值的项不变**。校验系统顺利关联，且底层 `m_team` 成功更新（**验证查重时精准排除了当前球队自身**）。 | sql验证 |
| 5 | 技术边界-空字符容错 | **【`NULL` 与空字符串 `""` 的等效识别】** 模拟底层表对应字段为**空字符串 `""`**（而非 `NULL`）。校验系统能否正确识别为“空”，前端显空并成功触发覆盖更新逻辑。 | 防后端只校验 `IS NULL` 导致的漏测。 |
```

### 5. 交付推进节奏
- **严格遵循推进闭环**：`迭代深度分析报告（提待确认问题） → 用户确认答复并拍板 → 产出/修订测试点 → 用户确认 → 产出 Excel 用例与 SQL`。严禁未确认前抢跑生成用例，严禁跨步脑补。
