# Test Case Readiness Rules

## 目标

在模块最终测试点通过校验后，判断现有资料是否足以生成可执行、可复现的测试用例，并把缺失输入作为下游交接问题显式记录。此阶段不展开等价类、边界值、步骤或用例编号。

以“足以设计用例”为门禁，不以“所有发版后实现细节都已知”为门禁。开发和测试默认并行；能在执行时绑定、参数化或通过标准测试工具发现的值，不得阻断用例生成。

## 两类门禁

- `upstream-gap`：来源或已确认上下文支持某个测试意图，但最终测试点没有覆盖，或测试点结论与来源冲突。停止就绪性审查，回到前置分析/逐 RSU/模块测试点汇总修复；不得用 CIQ 回答绕过。
- `blocked-input`：测试点本身正确，但缺失信息会导致无法写出测试准备、执行动作或可判定的业务结果，且该信息既不能从现有来源推导，也不能在执行时通过常规工具绑定。只有满足这一条件才使用 `CIQ-ID`。

## CIQ 准入门禁

提出任何 pending CIQ 前，必须依次判断：

1. **范围必要性**：该信息是否直接影响当前 TP 的准备、动作或业务断言？若只是实现细节、辅助诊断、非本次验收重点或更细的证据，不提问。
2. **来源可推导性**：是否可从需求、Context Card、配置、目录/命名规则或已回答问题得出？可推导时直接形成“已闭合关键输入”。
3. **常规方法可解性**：是否可使用标准测试方法解决？例如 Network 识别请求与语义值、日志/任务状态判定调用结果、文件存在性/数量/大小/修改时间/哈希判定传输和覆盖。可解时直接写入方法，不向用户提问。
4. **执行时绑定性**：具体值是否可在发版或用例执行时获取，且不改变用例设计？若是，使用语义名或参数化占位，标记执行时绑定，不阻断。
5. **真实不可替代性**：只有经过前四项后，仍然无法得出可判定预期或可执行准备方法，才创建 pending CIQ。

禁止仅因缺少以下内容而阻断：尚未实现的前端/接口参数名、日志固定关键字、发版后才产生的 Job/Pod 实例名、可在执行时选定的具体样本值，以及已有常规观察方法可判定的文件时序或覆盖证据。

## 审查维度

逐个 `TP-ID` 判断是否具备：

1. 可构造的正常、边界、异常或重复执行数据，以及可重复的数据查找/准备方法。没有数据库设计时，允许使用语义数据状态和执行前确认方法，例如“选取一个经业务查询确认无数据的合法历史日期 `D_empty`”；不得为了写死样本值而阻断。
2. 能定位被测页面、接口、任务、消息、文件、数据库或外部系统的环境信息。
3. 能判断结果的预期算法、枚举、数量、命名、目录、覆盖/清理和跨系统一致性规则。
4. 能取得必要证据的语义观察入口，例如浏览器 Network、任务状态/日志、文件属性或数据查询。只要能说明“观察什么语义值、如何判断”即可，不强制提前知道实现字段名或日志关键字。
5. 来源足以支持测试点，不依赖模型猜测实现、示例值或聊天记忆。

执行时才会提供、且不改变用例设计的环境地址、账号、权限、具体样本值和运行实例均可作为用例前置条件或参数化输入，不要求 readiness 阶段预先证明其已开通或实际可用。readiness 只需确认用例能明确说明执行者应使用何种语义环境/权限，并能在条件满足后按既定方法准备、观察和判定；不得仅因尚未取得凭据、尚未选定样本或尚未开通环境而创建 pending CIQ。

只有当环境/权限缺失会改变用例设计，或现有资料无法定义安全且可判定的数据准备、观察、清理/恢复方案时，才可用 `blocked-input`。生产环境造数或未授权数据修改不得作为默认准备动作；安全边界应写入用例前置条件。对数据库型 TP，Data Closure 提供的语义数据画像、查询/断言口径和隔离环境恢复约束足以支持设计时，实际隔离环境、账号和样本在执行阶段绑定，不构成 readiness 阻断。

## 输出判定

- `ready`：所有 TP 都具备用例生成所需输入；可以进入测试用例 Skill。
- `blocked-input`：至少一个 TP 依赖尚未回答的 CIQ；可以保存审查产物，但不得生成正式用例。
- `upstream-gap`：至少一个 TP 暴露需求映射或测试点覆盖缺口；先回退修复并重新进行模块测试点汇总。

已经从来源闭合的关键结论写入“已闭合关键输入”，避免后续把已知规则重复问给用户。待补问题必须具体到“缺什么、用于哪些 TP、已有依据是什么”，不能写“请补充更多信息”。

生成后对每个 pending CIQ 做一次反向自审：删掉该问题后，是否仍能使用语义参数、执行时绑定或常规观察方法写出步骤和预期？如果能，必须删除该 CIQ 并将 TP 标为 `ready`。

Data Closure 的 `test-point-ready` 表示上游曾记录用例 SQL、造数或清理细节缺口，不能单凭该状态自动创建 CIQ 或判定 `blocked-input`。Readiness 必须重新执行上述五项准入判断；若语义状态、查询对象和预期已知，具体任务 ID、样本、SQL 参数、物理字段核对或发版后接口信息可在执行时绑定，则 TP 可以为 `ready`。只有闭包状态为 `blocked` 时才构成确定性硬门禁。

pending CIQ 的“回填答案/资料”只需明确表达尚未回答，可以使用“未提供”“待回填”“pending”“not provided”等等价占位，不要求固定中文、大小写或单一措辞；`answered` 则必须包含实质答案或资源。
