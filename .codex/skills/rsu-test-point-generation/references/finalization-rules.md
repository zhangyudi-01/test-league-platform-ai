# Module Test-Point Assembly Rules

## 汇总阶段角色

你是高级测试工程师，但本阶段只负责审查已验证候选的语义边界并执行模块级汇总；不得为了数量压缩测试点，也不得在没有候选阶段追溯依据时补造或改写新的业务语义。

## 汇总目标

基于已校验的逐 RSU 候选，确定性形成模块级、可追溯的最终测试点。此阶段只做精确重复去重、稳定编号和引用继承，不重新从原文补造候选，也不生成测试用例。

## 候选处置准则

- 默认一个候选对应一个最终测试点，不按目标数量增删、压缩或扩充测试点。
- 只有两个候选的 `测试项`、完整 `测试点` 与 `备注` 在忽略排版空白后均完全相同时，才允许确定性合并为同一 TP；备注差异不能丢弃。
- 标题相近、业务对象相同、属于同一页面或生命周期、共享状态集合，或者使用页面/API/数据库/日志等不同观察层，都不能作为自动合并依据。
- 不同操作、状态门禁、业务结果、状态迁移、异常处理或边界约束，只要需求表达了可独立验证的行为，就应保留为独立测试点。
- 状态值、错误码、字段、等价类、边界值和观察层均由高级测试工程师结合需求语义判断。它们若对应不同操作、不同控件/对象、不同状态迁移、不同业务结果或不同异常/恢复路径，候选阶段就应拆分，汇总阶段不得合并；若只是同一操作、同一对象、同一生命周期阶段和同一预期结果下的等价输入或共同证据，才允许作为同一候选的内容。
- `测试点` 直接说明必要条件、操作或事件和通过/失败判据，不得容纳多个独立测试点的长列表。`测试项` 为简洁分类，`备注` 可为空且只作补充。
- 精确重复合并后必须继承全部 Source RSUs、Source Candidates、Question Refs、Context Refs 和 Data Closure Refs。
- `excluded` 只用于候选明确越出模块范围、违反授权或结构契约，或者已经由精确重复项完整覆盖的情况；不得用于模糊的“同一风险”“回归价值较低”或数量压缩。
- 汇总前对照来源与 Context Card 复核数量算法、对象粒度、重复执行、覆盖/替换、清理和跨系统完整性。来源已支持但候选缺失时停止并回退逐 RSU/前置分析，不在最终表中凭空新增无候选测试点。
- 若发现某个候选本身混入多个可独立验证的行为，停止汇总并重新打开对应 RSU；不得在 module assembly 中拆出未经候选阶段追溯的新语义。

## 编号和覆盖

- 按候选在逐 RSU 产物中的稳定出现顺序分配连续 `TP-001`、`TP-002`……。
- 每个候选必须在候选归并表中恰好处置一次：`retained`、`merged` 或 `excluded`。
- `merged` 必须指向测试项、完整测试点和备注均完全重复的保留项，并明确记录该事实。
- 每个 RSU 必须在 RSU 覆盖表中恰好出现一次；零候选 RSU 保留逐 RSU 阶段的具体原因。
- 最终测试点必须继承对应候选的全部 Source RSUs、Question Refs 和 Context Refs，不得缩减依赖。
- 只填写最终测试点表中的 `Context Refs`；不要手工维护“上下文资源入口”。最终校验器会取实际引用资源的并集，并从 RSU map 的唯一权威“引用入口”自动派生可点击路径和定位用途。

## 结果边界

最终文件中的“生成结果”只能是 `test-points` 或 `zero-test-points`。仅当所有 RSU 均有合法、可审计的零候选结论且最终表为空时，才能使用 `zero-test-points`。
