# Data Closure Generation Extension

## 启用条件

当前模块资源索引存在 `DC-INDEX` 和至少一个 `DC-xxx` 时启用本扩展。没有数据闭包的模块继续使用基础候选契约，不补空图、不猜数据库表。

## 生成要求

- 输入包中的 `DC-ID` 不是标签。必须阅读全文，并继续读取卡片“引用入口”中的 schema、SQL、API、代码或人工确认来源。
- 对照卡片核实表角色、完整 Join Predicate、基数、附加过滤、数据 Profile、预期推导和清理边界；不能只看 Mermaid 连线。
- 候选测试点实际依赖数据库状态、关联、过滤、聚合、写入或数据库观察结果时，在 `Data Closure Refs` 中列出全部相关 `DC-ID`。
- `Data Closure Refs` 中的每个 `DC-ID` 也必须出现在 `Context Refs`，证明对应卡片已物化并参与推导。
- 当前测试意图与数据库无关时写 `无`；不要因为模块存在数据库就把同一闭包机械绑定到 UI、文案等无关候选。
- 若已物化闭包的缺口会改变测试点语义，停止生成并回到前置分析；不能用 `Data Closure Refs=无` 绕过。
- 若闭包状态为 `test-point-ready`，可以生成语义已闭合的候选，但“推导依据”必须说明现有闭包足以支持什么；可执行 SQL/造数缺口留到用例就绪性审查。
- 与当前验证直接相关的数据库字段、状态码、数据过滤和持久化结果在 `测试点` 中写清，数据路径和准备细节由 Data Closure 引用承载。`备注` 不替代关键断言；不要给简单 UI 测试点附加无关数据校验。是否拆分仍由独立测试承诺决定。

## 数据维度

仅在来源和闭包支持时考虑：

- 查询数据的非空、空、边界、断链、重复映射和多结果展开。
- 来源类型、业务类型、删除状态、租户/中心、时间和状态等过滤是否共同生效。
- 一对多、多对多、并集、去重、排序、聚合和空结果语义。
- 写入后的新增、更新、覆盖、幂等、回滚、并发和级联影响。
- API/页面/任务/消息/文件结果与数据库状态的一致性。

这些仍是测试点意图，不在本阶段展开具体 SQL、字段值、步骤或用例数据组合。
