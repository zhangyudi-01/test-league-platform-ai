# Data Closure Readiness Extension

## 逐 TP 审查

对每个带 `Data Closure Refs` 的最终 TP，至少确认：

1. 卡片中的物理表、字段、Join Predicate、过滤、基数和数据所有权足以生成查询。
2. 至少有一个可重复的数据 Profile，能够说明查找或准备方法、动态预期推导和清理策略。
3. 写操作明确插入/更新/删除顺序、自然键冲突、事务/回滚和级联影响；只读操作明确空结果与非空结果的判定。
4. 环境地址、账号、权限、具体样本主键和运行实例可在用例执行时绑定；readiness 不要求预先确认其已开通或实际可用。用例必须写清语义环境、所需权限及安全边界，不得把生产造数或未经授权的数据修改列为准备步骤。
5. 用例能够建立非空动态预期；不能把数据库预期和 API 实际结果同时为空当作有效闭环。

## 缺口归类

- 闭包缺少会改变业务测试意图的表关系、过滤或状态语义：`upstream-gap`，回退前置分析和测试点生成。
- 测试点语义正确，但缺少无法由现有闭包、语义参数、常规查询/观察或执行时绑定替代的准备方法、查询对象/关系、动态预期、断言口径或安全清理/恢复方案：`blocked-input`，创建对应的 `data-contract`、`test-data`、`environment` 或 `configuration` CIQ。
- `ready`：现有闭包已经足以定义查询、语义数据准备方法、动态预期、断言及安全清理/恢复方案；不要求实际环境、账号、权限和样本已在 readiness 阶段交付。任务 ID、样本值、SQL 参数及可在执行时选择的获授权隔离环境和账号可以作为执行时绑定，不因尚未取得或验证可用性而阻断。

`test-point-ready` 是上游记录的待复核信号，不是 readiness 的机械结论。必须按当前全部材料重新判断：缺口若已由其他来源闭合，或不改变用例设计且可在执行时绑定，直接标记 `ready`；只有仍存在真实不可替代输入时才标记 `blocked-input`。

环境未开通、凭据未发放、尚无已选定样本不是“准备方案缺失”。若安全的准备/只读查询/预期计算/清理恢复方式已经明确，应将环境及授权要求写为用例前置条件，并将具体值标为执行时绑定；若无法在不越权或不触碰生产数据的前提下写出可重复且可判定的方案，才阻断。

没有 Data Closure Refs 的非数据库 TP 不强制数据库输入；若 TP 明显依赖数据库却写 `无`，标记 `upstream-gap`。
