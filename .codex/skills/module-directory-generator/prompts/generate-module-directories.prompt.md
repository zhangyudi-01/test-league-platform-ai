# 提示词：根据源文档生成层级化目录结构（通用版）

## 任务说明

根据源文档中的内容结构，生成对应的层级化目录结构。

此提示词适用于以下场景：
- 根据需求文档生成模块目录
- 根据知识库目录生成文档结构
- 根据功能列表生成项目目录
- 其他需要"文档结构 → 目录结构"映射的场景

核心要求：目录命名必须具有**唯一性**和**可追溯性**，严格对齐源文档内容。

---

## 输入资料

**源文档**：{指定文档路径}

**参考章节**：{指定要映射的章节或部分}

**层级深度**：{指定需要创建的目录层级，如1-3级}

---

## 输出要求

**输出目录**：{指定目标目录路径}

**目录结构**：按源文档中的层级关系创建完整的目录树

## 目录命名规范设计原则

### 核心要求

1. **唯一性**：每个目录必须有唯一标识符
2. **层级性**：通过标识符能看出层级关系
3. **可读性**：目录名称清晰表达内容
4. **可追溯性**：能快速定位到源文档对应位置
5. **严格对齐**：与源文档内容完全一致，**不添加额外文字**

### 推荐格式

```
{前缀}-{层级ID}-{内容名称}
```

**组成部分**：
- `{前缀}`：标识目录类型或用途（如 MOD-模块、DOC-文档、FEAT-功能）
- `{层级ID}`：层级化的数字编号，用`-`分隔
  - 一级：`01`, `02`, `03`, ...
  - 二级：`01-01`, `01-02`, `02-01`, ...
  - 三级：`01-01-01`, `01-01-02`, `02-01-01`, ...
  - 更深层级：继续追加数字
- `{内容名称}`：源文档中的原始名称，**严格对齐，不修改、不增减**

**通用示例**：
```
MOD-01-用户管理/
MOD-02-订单系统/
  MOD-02-01-订单创建/
    MOD-02-01-01-下单流程/
    MOD-02-01-02-支付确认/
  MOD-02-02-订单查询/
    MOD-02-02-01-我的订单/
DOC-01-API文档/
FEAT-01-登录功能/
```

## 命名规范演进：从错误中学习

> 本章节记录了真实的命名规范演进过程，展示了如何通过迭代找到最佳方案。

### ❌ 第一次错误尝试：擅自添加内容

**错误格式**：`01-{功能名称}管理/`

**典型问题**：
1. ❌ 添加了源文档中不存在的后缀（如"管理"、"模块"）
2. ❌ 创建了未经请求的文件（如 README.md）
3. ❌ 遗漏了某些层级目录

**错误示例**：
```
源文档：刻录功能
错误目录：01-刻录管理/  ← 擅自添加了"管理"
```

**问题根源**：
- 主观认为添加"管理"等词汇更规范
- 自作主张创建初始化文件
- 对源文档理解不完整

**用户反馈**：
> "你不要给我乱加文字，跟源文档对齐，不要乱加内容和其他操作"
> "没让你添加readme.md你就加上了"
> "不能遗漏目录层级"

**教训**：
- ✅ 严格按照源文档命名，一个字都不要擅自增减
- ✅ 不要创建未明确要求的文件
- ✅ 必须创建完整的目录层级，不能偷懒

---

### ⚠️ 第二次改进：命名过于冗长

**改进格式**：`{前缀}-01-{英文缩写}-{功能名称}/`

**改进点**：
✅ 添加了唯一标识符前缀
✅ 去掉了擅自添加的文字
✅ 创建了完整的目录层级

**新问题**：
❌ 加入了冗余的英文缩写部分，导致命名过长

**错误示例**：
```
MOD-01-M-AUTH-登录/  ← 英文部分 M-AUTH 冗余
MOD-02-M-ORDER-订单管理/  ← 过于冗长
```

**问题根源**：
- 过度设计，试图在目录名中包含过多信息
- 未考虑实际使用中的便捷性

**用户反馈**：
> "你觉得目录命名的英文部分还需要保留吗，是不是有点太长了？"
> "如果只叫 MOD-01-登录，可不可以？"

**教训**：
- ✅ 保持命名简洁，避免冗余信息
- ✅ 层级ID已经提供了唯一性，不需要额外的英文标识
- ✅ 优先考虑使用便捷性

---

### ✅ 第三次最终方案：简洁且唯一

**最终格式**：`{前缀}-{层级ID}-{内容名称}/`

**示例**：
```
MOD-01-登录/
MOD-02-订单系统/
  MOD-02-01-订单创建/
    MOD-02-01-01-下单流程/
  MOD-02-02-订单查询/
```

**优点**：
✅ 具有唯一性（通过层级ID）
✅ 简洁清晰（去除冗余部分）
✅ 层级关系明确（从ID可看出父子关系）
✅ 严格对齐源文档（内容名称不修改）
✅ 易于使用（命名长度适中）

**核心原则总结**：
1. **唯一性** > 冗余信息
2. **简洁性** > 过度设计
3. **对齐性** > 主观修改

## 关键边界和约束（适用于所有场景）

### 🚨 严格禁止的操作

#### 1. 禁止擅自修改源文档内容

**错误示例**：
```
源文档：用户登录
❌ 错误：01-用户登录管理/        ← 添加了"管理"
❌ 错误：01-用户认证/             ← 改变了原始用词
❌ 错误：01-Login-用户登录/      ← 添加了英文
```

**正确做法**：
```
✅ 正确：{前缀}-01-用户登录/      ← 完全对齐源文档
```

**原则**：
- 源文档是什么，目录名就是什么
- 不要自作聪明地"优化"或"规范化"名称
- 不要添加任何额外的修饰词、后缀、前缀

---

#### 2. 禁止创建未明确要求的文件

**错误示例**：
```
❌ 在每个目录下创建 README.md
❌ 创建 .gitkeep 文件
❌ 创建初始化脚本
❌ 创建配置文件
```

**正确做法**：
```
✅ 只创建目录结构
✅ 如果需要文件，会在任务说明中明确指出
```

**原则**：
- 任务要求创建目录，就只创建目录
- 不要自作主张添加"可能有用"的文件
- 保持最小化操作原则

---

#### 3. 禁止遗漏或跳过层级

**错误示例**：
```
源文档层级：
├── 一级：订单管理
│   ├── 二级：订单创建
│   │   ├── 三级：下单流程
│   │   └── 三级：支付确认
│   └── 二级：订单查询

❌ 错误：只创建到二级
MOD-01-订单管理/
  MOD-01-01-订单创建/    ← 缺少三级
  MOD-01-02-订单查询/
```

**正确做法**：
```
✅ 正确：完整创建所有层级
MOD-01-订单管理/
  MOD-01-01-订单创建/
    MOD-01-01-01-下单流程/
    MOD-01-01-02-支付确认/
  MOD-01-02-订单查询/
```

**原则**：
- 源文档有几级，就创建几级
- 不要因为某一层级"看起来简单"就跳过
- 保持结构完整性

---

#### 4. 禁止自行判断和过滤内容

**错误示例**：
```
❌ "这个功能点太小了，不用单独建目录"
❌ "这两个功能相似，合并成一个目录吧"
❌ "这个章节看起来不重要，跳过"
```

**正确做法**：
```
✅ 源文档中列出的所有条目，一个不少地创建对应目录
✅ 保持源文档的结构和粒度
```

**原则**：
- 不要根据"重要性"判断是否创建
- 不要擅自合并或拆分
- 严格按照源文档的结构执行

---

### ✅ 必须遵守的规则

#### 1. 严格对齐源文档

- 内容名称必须与源文档**完全一致**
- 保持源文档的层级关系和顺序
- 一个源文档条目 = 一个对应目录

#### 2. 保证唯一性

- 每个目录必须有唯一的标识符（层级ID）
- 同级目录的ID连续递增（01, 02, 03...）
- 子目录的ID继承父目录ID前缀

#### 3. 保持完整性

- 创建完整的层级结构，不遗漏任何层级
- 所有源文档中列出的条目都要创建
- 保持源文档的逻辑结构

#### 4. 最小化操作

- **只**创建目录，不创建文件（除非明确要求）
- **只**使用源文档中的信息，不添加额外内容
- **只**按照规范格式命名，不自行发挥

## 执行步骤（通用流程）

### 步骤 1：读取并理解源文档

**操作**：
1. 完整读取源文档
2. 识别文档的层级结构（标题、章节、列表等）
3. 确认需要映射的范围（哪些章节需要创建目录）

**检查点**：
- [ ] 已完整读取源文档
- [ ] 已识别所有层级关系
- [ ] 已明确映射范围

---

### 步骤 2：分析层级关系

**操作**：
1. 列出一级内容清单
2. 列出每个一级下的二级内容
3. 继续细化到所需的最深层级
4. 确认层级深度和每个节点的内容

**检查点**：
- [ ] 层级关系清晰
- [ ] 所有节点都已识别
- [ ] 没有遗漏或重复

---

### 步骤 3：设计层级ID体系

**操作**：
1. 确定前缀（根据目录用途）
2. 为一级内容分配ID：01, 02, 03...
3. 为二级内容分配ID：{父ID}-01, {父ID}-02...
4. 继续为更深层级分配ID

**ID分配规则**：
```
一级：{前缀}-01, {前缀}-02, {前缀}-03...
二级：{前缀}-01-01, {前缀}-01-02, {前缀}-02-01...
三级：{前缀}-01-01-01, {前缀}-01-01-02...
```

**检查点**：
- [ ] ID连续无跳号
- [ ] ID无重复
- [ ] 子目录ID正确继承父目录ID

---

### 步骤 4：创建目录结构

**操作**：
1. 按照格式 `{前缀}-{层级ID}-{内容名称}/` 创建目录
2. 先创建一级目录
3. 在对应的一级目录下创建二级目录
4. 继续创建更深层级

**注意事项**：
- **只创建目录，不创建任何文件**
- 目录名称严格对齐源文档
- 不添加、不修改、不删减任何文字
- 保持源文档的顺序

**检查点**：
- [ ] 所有目录都已创建
- [ ] 目录命名格式正确
- [ ] 未创建任何文件
- [ ] 未添加额外文字

---

### 步骤 5：完整性验证

**验证清单**：
- [ ] 目录层级与源文档完全对应
- [ ] 所有源文档条目都有对应目录
- [ ] ID格式正确且唯一
- [ ] 目录命名无额外文字
- [ ] 所有层级都已创建
- [ ] 未创建任何文件
- [ ] 子目录ID正确继承父目录ID
- [ ] 目录顺序与源文档一致

**对照检查方法**：
1. 打开源文档和生成的目录结构
2. 逐条对照源文档的每个条目
3. 确认每个条目都有对应的目录
4. 确认目录名称与源文档一致
5. 确认层级关系正确

## 常见错误模式及纠正

### 错误模式1：擅自"优化"名称

❌ **错误思维**："源文档写的太口语化，我帮忙规范一下"

**错误示例**：
```
源文档：用户登录功能
AI创建：01-用户认证模块/     ← 自作聪明改成了"认证"和"模块"
```

✅ **正确思维**："源文档是什么，我就写什么"

**正确示例**：
```
源文档：用户登录功能
AI创建：{前缀}-01-用户登录功能/  ← 完全对齐
```

---

### 错误模式2："贴心"地创建初始文件

❌ **错误思维**："空目录不好，我创建个README方便后续使用"

**错误示例**：
```
创建目录的同时在每个目录下创建 README.md
或者创建 .gitkeep、index.md 等
```

✅ **正确思维**："只做被明确要求的事"

**正确示例**：
```
只创建目录结构，不创建任何文件
如果需要文件，任务说明中会明确指出
```

---

### 错误模式3："简化"层级结构

❌ **错误思维**："三级目录太深了，二级就够了"

**错误示例**：
```
源文档有三级层级，但只创建到二级
理由：觉得第三级"太细"或"不重要"
```

✅ **正确思维**："保持源文档的完整结构"

**正确示例**：
```
源文档有几级，就创建几级
不根据"重要性"判断是否创建
```

---

### 错误模式4：命名过度设计

❌ **错误思维**："加上英文缩写和分类标识更专业"

**错误示例**：
```
MOD-01-M-AUTH-USER-LOGIN-用户登录/
← 包含模块类型、功能域、业务类型、英文名等
```

✅ **正确思维**："简洁就是最好的设计"

**正确示例**：
```
MOD-01-用户登录/
← 前缀+ID+名称，足够了
```

---

### 错误模式5：自行判断和过滤

❌ **错误思维**："这两个功能相似，合并一下更合理"

**错误示例**：
```
源文档：
- 订单创建
- 订单提交

AI创建：
01-订单创建和提交/  ← 擅自合并
```

✅ **正确思维**："源文档怎么分，我就怎么分"

**正确示例**：
```
源文档：
- 订单创建
- 订单提交

AI创建：
01-订单创建/
02-订单提交/  ← 严格对应
```

## 后续应用场景

生成的目录结构可用于：

## 核心思想总结

### 三个"不要"

1. **不要擅自添加**：源文档有什么，就创建什么
2. **不要自作聪明**：不要试图"优化"或"改进"源文档
3. **不要过度设计**：简洁、唯一、对齐即可

### 三个"必须"

1. **必须严格对齐**：与源文档完全一致
2. **必须保持完整**：所有层级和条目都要创建
3. **必须保证唯一**：通过层级ID确保每个目录可追溯

### 最高原则

**源文档是唯一真理来源（Single Source of Truth）**

- 源文档说什么，就是什么
- 不要根据"常识"、"经验"、"最佳实践"来修改
- AI的任务是**映射**，不是**设计**
