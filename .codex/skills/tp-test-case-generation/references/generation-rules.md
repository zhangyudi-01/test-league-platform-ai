# 生成规则

## 生成单位

一次处理脚本准备的唯一下一批；批内每个 TP 各自输出到 `by-tp/<TP-ID>.md`。简单和查询展示批次最多 10 个 TP，复杂批次只有一个 TP。

前置无要求填 `无`；简单条件直接一句，复杂多类信息才分类。步骤只写实际动作，预期只写对应结果；两者从 `1.` 连续编号、逐项换行、数量一致并一一对应。禁止“来源场景”“场景矩阵”“数据闭包执行计划”“当前 TP 核心操作”等占位话术。内部 TP/RSU/DC/DP 标识只用于追溯，不进入执行正文。

## 场景展开

上游最终 TP 已完成原子化收敛时，也必须逐 TP 判断用例数量，不得把 `1 TP = 1 TC` 设为默认或硬性目标。对同一 TP，若不同验证具有可合并的前置/操作，且可在同一用例中得到清晰、独立可判断的结果，应合并；若有充分证据满足下列四项，则拆为多条。正常、边界、非法、空值、状态或重复等数据维度本身不构成拆分依据，也不构成必须合并的理由；关键在于四项是否同时成立。

仅在下列四项**同时**成立时，才可把一个 TP 拆为多条：

1. 每条具有独立业务风险；
2. 前置条件或实际操作不可合并；
3. 每条具有独立、可判断的预期；
4. 每条具有独立回归价值。

多条用例时，追溯索引中的“用例设计说明”必须逐条使用可校验格式：`独立业务风险=...；不可合并前置或操作=...；独立可判断预期=...；独立回归价值=...`。四项都必须给出当前用例的具体非空理由；任何一项不能成立或无法说明时，不因该维度单独拆分，并将可合并验证收敛。单条用例也必须是可执行且覆盖当前 TP 全部承诺的设计，不代表无需评估拆分。不适用的维度不强行造用例；每一项保留验证必须能从输入包追溯到规则、确认结论或数据闭包。

## 用例写法

- 每条用例只验证当前 TP 的一个清晰测试意图；同一意图内的数据组合可以包含必要的多个值和操作步骤。不得提前验证相邻 TP 的默认值、单选、筛选、详情、权限、日志等独立意图，也不得跨模块补造泛化联动。
- TP 来源包含多个值、状态或条件时，直接在前置或步骤中列出这些具体组合及执行顺序；不能用“多个来源场景”“各场景”代替实际条件，让执行者返回 TP、DC 或计划查找。
- 没有前置填 `无`；简单条件直接一句。只有确实存在多类复杂信息时才使用 `页面状态：`、`Mock配置：` 等分类，分类名单独一行并以 `<br>` 分隔内容，不得凭空制造分类。
- 数据值优先使用 `$A`、`$B`、`$X1`、`$X2`、`$A1`、`$A2` 等与环境无关的变量；可在前置条件中用 `24011`、`240112` 或 `123` 等示例解释关系。变量在前置条件或执行步骤的实际使用位置保持同名；查询 SQL 的简洁预期无需重复变量。
- `数据变量` 中的字段描述可使用中文或英文，大小写、空格、下划线和命名风格均不受限制；示例值不是必填项。每条声明必须有非空描述并恰好包含一个 `$A`/`$B`/`$X1` 等变量，多条声明用中文或英文分号分隔。
- 执行步骤必须能让测试人员定位页面、接口、任务、日志、文件或查询入口。
- 普通 UI 用例的前置条件只保留必要账号、页面、数据和环境；不要复制完整构造链、会话独占、清理细节或前后重复 SQL 比对。
- 预期结果必须可判断，写出具体状态、文件、字段、数值关系或观察证据；不得写“功能正常”。每项预期独占一行并使用从 `1.` 开始的连续编号，即使只有一项也必须写 `1.`。
- 既有的需求范围排除继续生效。不能以通用测试清单为由重新加入已经明确不测的权限、审计或无要求页面反馈。

## 引用规则

- `RSU Refs` 至少包含一个当前 TP 来源 RSU。
- `Question Refs` 只可使用输入包内的 `Q-*` 或 `CIQ-*`；没有时填 `无`。
- `Context Refs` 只可使用输入包已物化资源；没有时填 `无`。
- `Data Closure Refs`、`Data Profile Refs` 只能使用当前 TP 允许的闭包和 Profile；非数据库 TP 两列都填 `无`。
- `TC-ID` 三位序号从 `001` 递增，不跳号、不复用。

## SQL-backed 场景

- SQL 只根据当前输入包已经分析好的 Data Closure 和 Context Refs 编写；禁止猜表、字段、连接、软删除或状态含义。
- SQL 原文保存在 `test-cases/sql/<SQL-ID>.sql`，通过 `sql-manifest.json` 统一登记；多个用例需要同一查询时复用同一个 SQL-ID，不复制 SQL 原文。
- 查询用例的步骤引用 SQL-ID 和文件名；预期必须保留具体 SQL-ID，但只需简洁写明“页面或接口结果与 `SQL-ID` 查询结果一致”。多条查询写“页面或接口结果分别与 `SQL-A`、`SQL-B` 查询结果一致”。预期不重复参数绑定、变量值、数据准备方式或“前置、操作和比对使用同一组取值”等过程说明。只做人工功能测试比对，不生成接口与 SQL 的自动化比对脚本。
- 需要增加过滤条件时，直接维护已有 SQL 文件并在新增 `WHERE`/`AND` 条件旁写用途注释；同步更新 manifest 的参数和示例，所有引用该 SQL 的用例继续使用同一个 SQL-ID。
- 新规划 SQL 只允许 `SELECT`，须通过静态单语句检查和 MySQL `EXPLAIN`。

发现某个场景需要输入包外的事实时，停止生成并回到上游补资料；不要在备注里隐藏假设。
