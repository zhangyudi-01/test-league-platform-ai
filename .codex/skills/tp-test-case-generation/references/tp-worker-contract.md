# TP Worker Contract

本契约由 `module-session` 的模块基础会话完整读取一次，规划、SQL 和批次分别从该基础会话独立 fork。它约束分支行为，不替代业务输入。

1. `generation-state.json` 是唯一调度与恢复依据；不得读取 runner 历史日志判断进度。Runner 先完成模块规划和 SQL 阶段，再处理唯一的下一批。
2. 简单和查询展示批次可含 1～10 个 TP，复杂批次恰好一个 TP。先填写本批全部 `by-tp/<TP-ID>.md`，再统一校验；仅当前输出格式、编号、变量声明或已有输入引用填写错误时，允许同一 worker turn 内最多 2 轮修正重验（含首次最多 3 次），通过才报告完成。达到上限或缺事实、来源漂移、SQL资产/报告不一致时停止，不得处理其他批次。
3. 当前批次分支已继承完整 Skill 和固定输出契约，并通过批次清单定位模块基线、必要上下文基线及各 TP delta。不得重新读取完整 INPUT，也不得读取清单外 TP 的 INPUT/OUTPUT、`runner-logs`、固定来源全文或兄弟批次补充业务事实。写入前必须读取 runner 已创建的各 `OUTPUT` 模板，只能填充模板，不得改名、删除或新增固定章节和表头。若清单给出的基线加 delta 仍不足，停止并报告阻断，不得自行全文回退或猜测。
4. SQL 已在批次前按模块计划统一生成和校验，本阶段只读。只能引用计划分配给当前 TP 的 SQL-ID；不得因 TP 引用 DC 而新增 SQL。入库或更新用例只描述期望记录，不生成 DML。
5. 只写当前批次清单中的 `by-tp/<TP-ID>.md`。人工修改 Markdown/SQL/JSON manifest 必须使用 `apply_patch`。
6. 输出固定表头保持不变。简单前置可以填 `无` 或一句关键条件；多类复杂准备才使用分类。TP 含多个值或状态组合时，直接列明具体条件和执行顺序，不能用“多个场景/各场景”代替。步骤与预期从 `1.` 连续编号、逐项换行、数量一致并一一对应。禁止“当前 TP”“来源场景”“场景矩阵”“数据闭包执行计划”“核心操作”等占位话术。查询预期简洁写与具体 SQL-ID 查询结果一致。未执行时三列测试结果统一填 `未执行`。
7. 对批内每个 TP 单独判断用例数量，不预设 `1 TP = 1 TC`。只有独立业务风险、不可合并前置或操作、独立可判断预期、独立回归价值四项同时成立才拆分；否则合并可在同一用例中执行和判定的验证。若拆分，每条用例都须在追溯说明中给出四项具体理由。用例只验证当前 TP 独有断言，不得跨 TP/模块扩展，也不得重复相邻 TP 已覆盖的单一分支。生成后运行 runner 给出的 `validate_batch_test_cases.py <BATCH-ID>`。
8. 不得在 worker turn 内启动 `run_generation.py`，不得切换模块、目录参数或状态文件。不得调用或等待 compaction；兄弟批次隔离由独立 fork 保证，自动压缩不是调度或事实恢复机制。

机械输出约束：多条前置、步骤、预期在表格单元格内用 `<br>` 分行；每条变量声明恰好一个 `$变量`，多条声明用分号分隔；冲刺、备注等不适用填 `无`。元数据的 `生成结果` 填 `validated` 仅是待校验的文档声明，调度状态必须由校验脚本原子写入，worker 不得直接改写为通过。
