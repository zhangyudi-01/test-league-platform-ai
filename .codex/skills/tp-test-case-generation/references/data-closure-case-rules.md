# 数据闭包用例规则

## 适用边界

`DC-*`/`DP-*` 提供数据事实和准备依据，不是强制 SQL 或强制输出执行计划的信号。纯 UI、纯前端限制或外部黑盒验证不得伪造表、字段、SQL、造数或数据库断言。

`DC-*` 说明“这条测试意图依赖哪条最小业务数据路径”；`DP-*` 说明“用哪一种可重复的数据状态实例化该路径”。它们来自前置分析，不由用例阶段补画或猜测。

## 单用例落地

TP 引用 DC 不等于必须选择 DP、写 SQL、输出独立执行计划或复制完整构造链。只有 generation plan 明确分配 SQL 的 TP 才引用查询 SQL；入库和更新预期描述目标表、关联键、字段状态和数量，不自动生成 DML。确实采用 DP 准备复杂数据时，按执行需要把以下内容写入前置、步骤或预期：

1. 查询/验证入口：SQL、只读查询工具、接口或日志入口；只使用闭包卡已登记的表、字段、连接与过滤契约。
2. 目标数据状态：本用例所需业务状态、关键关联、范围和唯一性要求。
3. 准备或变更动作：如何创建、调整或选择该状态，并说明准备成功的可观察证据。
4. 动态预期推导：从哪些数据字段、规则或聚合口径得到预期，不能写“结果正确”。
5. 清理/隔离：测试数据的标识、回滚、删除、覆盖恢复或独立环境策略。

一个 `DC-*` 可被多条用例复用；一个用例也可覆盖多个闭包。追溯表中的 DC 必须属于当前 TP，并在用例正文中体现它实际提供的关键数据事实；不要求为了 DC 单独生成 SQL、DP 或完整造数说明。

## SQL 与数据准备约束

- SQL 原文不写进用例表，统一存放在 `test-cases/sql/<SQL-ID>.sql` 并注册到 `sql-manifest.json`；同一查询可以被多个用例复用。
- SQL 不需要写死环境地址、账号或密码；连接来自 `--db-config` 或自动发现的 `database.toml`，旧 `config.txt` 只作为兼容回退。
- 新规划 SQL 每个文件只能包含一条 `SELECT`；参数使用 `:A`、`:B` 等名称，并在注释和 manifest 中说明用途及 EXPLAIN 示例值。
- 数据变量填写“字段描述 + `$A`”等虚拟变量；字段描述可使用中文、英文、数字、空格、大小写、下划线或自然语言，不强制固定命名格式，也不强制填写示例。每条声明只能包含一个变量且描述不得为空。变量须在前置条件或执行步骤中落到实际数据或操作，参数 `:A` 必须绑定为 `:A=$A`；预期无需为保持变量形式而重复过程信息。
- 查询型用例在步骤引用 SQL-ID 和文件名；预期保留具体 SQL-ID，简洁写明页面/接口结果与查询结果一致即可。多条查询可统一写“分别与 SQL-A、SQL-B 查询结果一致”，不重复参数绑定、变量值或准备过程；具体对比由测试人员手工执行，不由本 Skill 自动比对接口结果。
- 数据准备采用已确认的业务流程、Mock 或环境方式；入库/更新结果以文字描述目标记录，不生成准备型 SQL。
- 不能按表名、字段名或惯例猜外键、删除标记、租户条件、时间范围、排序、聚合或覆盖语义。
- 闭包卡没有提供可执行字段、连接谓词、过滤条件、准备策略或清理策略时，新增或恢复相应 `CIQ-*`，将模块置为 `blocked-input`；不要在用例备注中隐藏假设。
- 前置只写当前用例必要的数据状态；简单条件直接一句，复杂多类信息才分类。数据可使用 `$A/$B/$X1` 等变量，查询 SQL 的简洁预期不重复变量。
- 若 SQL 增加新的 `WHERE`/`AND` 条件，必须在 SQL 文件对应条件旁添加用途注释，并同步维护 manifest 参数；不要为每条用例复制一个近似 SQL。

## 验证口径

校验器会检查：引用的 `DC-*` 属于当前 TP、实际引用的 `DP-*` 属于已引用闭包、SQL-ID 与模块计划一致、变量与 SQL 参数一致。SQL 阶段统一执行一次 MySQL `EXPLAIN`；批次和最终阶段只核对验证报告与资产指纹未变化。
