# 单接口测试方案与功能残余收敛

## 职责与模式选择

本 Skill 有两种模式，按用户请求选择，不要混为一次输出：

1. **接口测试方案**：针对一个指定 operation 形成测试方案，完整测试点直接写入方案的测试内容表格。测试点是接口测试方案的一部分，不另建测试点 Skill 或重复测试点文件。
2. **功能残余收敛**：在接口用例已有真实执行证据后，按需求行为面/Facet 判断仍需功能测试的点，保留 API 不可观察的视觉、交互、自动刷新等行为，并减少对已由接口有效验证规则的重复测试。

用户指定 API、测试点或单接口测试方案时使用模式 1。用户要求“接口测完后剩余功能点”且提供接口执行状态/证据时使用模式 2。只看到脚本存在、测试方案已写或 pytest 收集成功，不足以进入已覆盖结论。若模式或 operation 不明确且会改变范围，先确认，不擅自覆盖整个模块。

不生成独立 SQL 文件、Workbook、数据初始化、pytest 代码或自动化实施方案。

## 输入发现

### 接口测试方案模式

先定位一个唯一 operation 及其当前资料：

1. 用户指定的 API-ID、路径/方法、需求及本轮确认。
2. 唯一有效的 `api-interface-analysis` 文档；确认 `测试方案就绪：是`，未决业务口径已回答。
3. 接口分析文档链接的接口专属 `clarification-questions.md`、Context Card 和 Data Closure；旧产物以其链接的问题单为准，仅读当前 operation 相关内容。检查 pending/deferred 问题是否影响测试预期；优先复用接口分析明确引用的模块级/接口级 DC，不复制闭包内容。
4. 相关模块需求、`preanalysis/`、OpenAPI、数据库结构/查询 SQL 或数据来源描述。若存在 `reference-analysis/` 或用户指定的历史参考，读取与当前接口相关的复用结论，并按需追读对应旧需求、测试方案或脚本中的相关场景；未提供且不存在历史参考时不因此阻塞。指定资料无法读取时记录缺口，影响当前预期的部分返回接口分析处理。
5. 测试工程中目标服务和测试类型相关的 `测试代码知识图谱.md`、`测试脚本开发规范.md`、`代码编写规则.md` 章节，以及一个最相似的现有方案/实现样例。通常从测试代码仓库的 `docs/测试工程/` 定位规范；路径不符时以真实仓库为准。

如果本接口有上一版最终测试方案/测试点，且本轮需求、适配记录写明某些行为“保持”“沿用”或“未变更”，必须将上一版 API 测试点逐项与本轮确认进行承接对照：保留仍受支持的行为，按新口径改写被修改的行为；只有已被替代、明确排除或不再属于本接口范围的点才可移除，并说明依据。不得因本轮只改一个算法分支，就默认其他已确认的 API 行为无需测试；也不得把过时实现/旧 SQL 的预期当成沿用契约。

相似接口的历史场景用于发现当前接口可能遗漏的风险，并结合当前需求、接口契约及用户确认判断其承接、变化或不适用；只有有当前依据的行为才能写成确定测试点。当当前需求或契约规定了字段、子对象或规则的适用前置条件时，历史实现、复用结论或结构示例仅作字段参考，不得用来弱化或推翻该前置条件，必须围绕该条件补充满足与不满足的正反向测试点。已确认的差异说明变更或排除依据即可；只有历史资料暴露了影响预期的当前口径歧义时，才返回接口分析澄清。不因旧脚本存在就自动沿用，也不要求另建历史对照表。

工程资料回答“如何观察/实现”，不定义业务预期。分别判断：

- **API 可观察性**：行为能否通过请求、响应或可验证的数据库副作用判断。
- **现有框架可实现性**：当前 client、Generator、fixture、Excel、DB helper 是否能直接实现。

测试工程能力不明时查证真实 helper/样例；不得因暂时找不到 helper 就判成 API 不可测。

### 功能残余收敛模式

读取模块需求行为面、相关 API 的测试点、实际执行报告/结果、断言内容和页面/交互要求。按同一行为面关联需求与接口断言；证据必须能说明哪条用例实际验证了哪项行为。

## 接口测试点编写规则

测试内容表格始终恰为以下四列及顺序，不增加 TP-ID、优先级或自动化状态列：

| 序号 | 测试项 | 测试点 | 备注 |
| --- | --- | --- | --- |
| 1 | <规则分组> | 【<场景>】<关键前置数据/状态；请求方法、参数或操作> → <确定的响应字段、错误码或数据库副作用> | <来源/边界> |

编写时遵守以下约束：

- 对需求行为逐项建立覆盖去向：接口表格、功能侧/分层检查，或有来源依据的排除项。不能遗漏需求中 API 可观察的行为。
- 每条测试点包含足以执行的关键前置、请求/操作和可判定结果。避免“正常返回”“符合预期”等空泛判据；复杂字段、状态、顺序、数量或副作用写清楚。
- 数据库相关测试点在 `备注` 中标注接口分析引用的 `DC-*` 或 `ADC-*`；不依赖数据库时不加闭包引用。该引用用于让自动化设计阶段沿用闭包，不增加测试内容表格列。
- 一个测试点聚焦一个主要风险；预期或错误结果不同就拆行。按业务风险组织测试项，不机械按“正向/边界/异常”扩行，也不把多个独立结果塞进一行。
- 只对需求、接口契约或用户确认支持的语义写确定预期。字段缺失、`null`、空数组、默认值、错误状态、边界、跨字段、排序/分页、状态变化和数据库副作用按接口实际适用情况检查。
- **集合谓词与状态分区展开**：当业务规则按状态阶段、类型集合或条件谓词（如“进行中/已终结/有效/可操作”）分支处理时，必须核查枚举定义或数据字典，覆盖该谓词包含的全部有效子状态，以及非目标分区的各阶段代表值与 `null`/缺失态，不得仅抽样单个枚举值代替整个状态族。
- **多源分流与对偶分支对称覆盖**：当接口按参数、业务类型或方向路由到不同物理表、不同数据源或对偶处理分支（如不同业务类型分表查询、正反方向/主从角色对调）时，字段映射、缺省回退、关联缺失、跨类型错配和方向转换必须在各分流分支上对称覆盖，不得只测单一路径而默认其他分支同理。
- **合成字段真值表、空串边界与归并反序构造**：由多字段拼接、计算或优先级回退生成的合成字段，必须覆盖“全部有效、部分为 `null`（单侧缺失）、全部为 `null`、零值 `0`、空字符串 `""`/格式非法占位符”组合；字符串类补充或回退字段必须同时验证 `null` 与空字符串 `""` 的归一化或回退差异；多数据源或多分支合并后按统一规则全局排序时，必须构造后查询分支排序键先于先查询分支的交叉样本，验证全局排序而非简单拼接。
- 区分公共枚举与当前接口允许的取值；接口已明确排除的值即使后来加入公共枚举，也不能因为实现接受而删除其测试点。已确认错误码与未定义的错误文案分开断言；预期有冲突时回到接口分析，不用当前返回裁决。
- Legacy implementation, historical SQL, existing tests, and examples may reveal risks or automation constraints, but must not alone define a formal test expectation. If they show behavior not promised by requirements, contract, or user confirmation, keep it outside the formal test-point table as an explicitly unconfirmed observation, or exclude it from scope. Promote it to a formal point only after an authoritative requirement/contract update or user confirmation.
- `备注`仅写来源编号、补充边界或 SQL 核对提示，不能藏前置、操作或核心 oracle。使用需求条款/API-ID/已确认问题等可追溯标识。
- 不为形式强行要求 SQL。只标记需后续独立 SQL 核对的响应/数据库逻辑，本 Skill 不生成最终 oracle SQL。

### 自动化适配说明

只有存在非默认路径、扩展需求或阻塞时才在测试点表格外写简短说明，并通过最终序号引用。说明必须拆开“API 可观察性”和“框架实现状态”，例如：

`序号 12：API 可观察；现有框架需扩展参数化 DB 校验；由自动化设计评估最小实现。`

API 可观察但当前框架没有 helper，仍保留接口测试点并登记扩展/阻塞；不能转成功能测试或删点。只有行为本身无法由 API 请求、响应或可核验副作用观察，才归入功能测试。适配说明不是第二份测试点表，且不改变四列表头。

## 功能残余判定

- 只有目标环境实际执行通过、且断言覆盖同一 Facet 的用例，才能将该行为记为接口已覆盖。报告、日志和断言都应能追溯；不能仅凭测试名推断覆盖。
- 失败、跳过、未执行、仅 `pytest --collect-only`、计划中的测试或无相关断言都算未覆盖；不要据此删减功能测试。
- 页面视觉、控件交互、自动刷新、页面状态保持等 API 边界不可观察的行为保留为功能测试。接口已经验证的规则不复制整套功能用例；仅按风险保留少量页面数据映射一致性/关键路径抽查。
- 相关 API 尚未全部完成时，只能给明确标注接口范围、未决接口及未覆盖面的阶段性残余结果，不声称模块功能覆盖完整。

## 文件与交付

沿用模块已有测试方案章节和版式：

- 单接口模式：更新该 operation 已有方案；没有时在接口工作目录创建 `api-test-plan.md`。不另建重复测试点文档。
- 残余模式：更新模块现有功能测试方案的测试内容；若没有既定目标文件，先确认模块约定，不能平行创建多个“最终版”。
- 新建单接口方案可使用 `一、测试类型`、`二、测试内容`、测试项/预期目标及上述四列表格；已有方案只补缺失内容，不整体改版。

业务口径未决、operation 不唯一或来源版本冲突改变预期时，停止定稿并列明阻塞。若仅自动化能力未明，可保留测试点并将适配结论标为待设计确认。

完成后检查：operation 范围唯一；需求行为去向齐全；前置条件正反向、状态枚举子集与非目标分区、多源分流对称分支、合成字段部分缺失/空串边界及多源合并交叉排序均已展开；每条测试点前置/动作/预期明确；表格列名和顺序准确且没有重复/意外断号；备注不承担 oracle；框架限制与需求覆盖分开；残余模式每个已覆盖结论有真实运行与同 Facet 断言证据。

交付后报告文件路径、模式、覆盖范围、未决/阻塞和 `ready`/`blocked`/阶段性状态，然后停止等待用户审核或修订；不自动启动 `api-test-automation-design`，也不自动将接口测试计划视为已执行。
