# 单接口分析与澄清

## 目标与边界

围绕用户指定的一个 OpenAPI operation，形成可供测试方案直接引用的业务行为基线。识别必须由用户决定的歧义，并在答复后更新同一份分析文档。

本阶段不生成接口测试点、最终 SQL oracle、Excel 用例、测试脚本或自动化实施方案。可以指出某项需求只能在页面/交互层观察，但不在此整理功能残余测试点。

若用户只要求测试点、自动化设计或代码，且现有分析已有效，不重复执行本阶段；引用并核对现有分析即可。一次只深入一个 operation。

## 输入发现与证据

按以下顺序定位资料，优先复用已有产物，不因文件名相似而默认其内容适用于当前接口：

1. 使用用户指定的模块、API-ID、路径/方法、文件路径和本轮答复。若目标接口不唯一，先确认范围，不把多个 operation 合并分析。
2. 查模块接口总览，确认 API-ID 与 OpenAPI operation 的唯一映射；检查现有 `interface-analysis/` 是否已有该接口的权威文档。
3. 从模块 `preanalysis/`、`reference-analysis/`、需求包和已确认答复中定位本接口相关规则与复用限制；读取相关模块级 Context Card 和 Data Closure 索引，并只打开本接口需要的卡片。模块级闭包是可复用基础，不要求接口分析重新生成一份模块闭包。若本轮是已有接口的迭代，读取上一版最终分析及相关答复。
4. 读取当前需求相关段、准确的 OpenAPI operation、相关数据库设计/DDL/查询 SQL；按需读取下游接口契约。只读与本接口有关的实现、日志或运行记录来识别现状和差异。
5. 对会改变结论的来源读到足以理解完整语义；若工具输出截断，继续读取未覆盖部分。记录实际来源文件和具体定位（需求条款/章节/行号、OpenAPI operation/JSON Pointer、SQL 片段或代码符号）；关键结论不得只引用文件名或笼统写“参考需求文档”。

模块存在 `reference-analysis/` 时，读取其索引及与当前 operation 相关的复用回顾，追读会影响本接口行为、数据路径或边界判断的历史需求、接口、SQL、测试脚本或实现中的具体段落/函数；用户明确指定的历史资料也按同样范围查阅。仅影响后续造数或工程实现的细节可交由自动化设计深入核验，不必通读所有历史文件。目录不存在时不创建、不因此阻塞；相关资料无法读取时如实记录，只有影响业务预期的缺口才阻塞相应结论。

按结论类别使用证据，不把不同来源混成同一种事实：

- 当前需求与用户明确确认决定业务预期。
- OpenAPI/接口设计说明传输契约；数据库结构和查询 SQL 说明数据路径与可核对事实。
- 历史需求与实现用于识别可能承接、变化或不再适用的行为及风险；只有当前需求或接口契约支持，或用户明确确认时，相关行为才能成为本接口预期。
- Java/Python 实现、日志和现象只说明当前实现，不因其存在就把它提升为需求。
- 公共枚举存在某个值，不代表本 operation 接受该值；分别核对接口允许范围、已确认的特殊分支和非法值处理。实现新增枚举或实际返回变化，不自动修改原有接口预期。
- 来源冲突并列记录、说明对测试的影响；不擅自选择实现代码或单一来源覆盖冲突。

来源中出现的 Cookie、Session、Authorization、访问令牌、密码或个人账号标识不得复制到分析文档、日志或后续产物。只记录认证字段名称、是否必需及来源位置；样例值一律脱敏。

测试工程的知识图谱、脚本规范和代码规则不是业务契约的常规输入。只有认证、数据获取、响应/副作用的观察方式等影响“接口是否能观察某行为”时，才查阅对应能力章节，并标为工程能力观察。框架限制不能改变需求结论。

## 分析流程

1. **固定范围**：记录 API-ID、HTTP 方法、路径、调用方、认证上下文、上下游边界和本次不分析的邻接接口。
2. **抽取行为**：从需求与答复提取本接口负责的可观察行为，并区分纯页面表现/交互。每条结论附来源。
3. **还原契约**：检查请求字段、类型、必填/默认值、校验、认证、成功和错误响应、字段缺失与 `null`、空集合、分页/排序、跨字段约束及副作用。逐项映射文档列出的错误条件、错误码和 message；错误码重复时按描述中的条件分别记录，不能因未单独写响应 schema 就称文案未定义。只有来源确实未提供时才标未知。
4. **追踪数据路径**：梳理关键表、关联键、过滤条件、排序、状态/时间字段、数据来源和写入副作用；说明请求参数如何影响路径，标出可能导致空结果或歧义的边界。不要在这里设计造数脚本或复制待测 SQL 作为独立预期。
5. **判断接口级辅助产物**：对照模块级 DC，判断它是否已覆盖本接口的数据路径、字段、连接、过滤和结果语义。已足够则引用，不复制；缺少接口专属路径或关键细节才新增接口级 DC。只有跨来源、跨规则段且下游会复用的稳定上下文才建立 Context Card；分析文档的摘要不另存为卡片。
6. **分级结论与提问**：按当前已确认口径、来源差异/实现观察、待用户决定组织内容。先自行检索现有资料；仅将无法查明且会改变业务预期、范围或测试判据的问题写入接口问题清单。
7. **维护答复**：问题使用稳定编号，记录关联来源、歧义、影响、需决定内容和状态。用户答复后更新原问题、接口分析及受影响的接口级 DC/Context Card；若问题实际属于模块级需求，则回填模块问题清单并在本接口引用其 Q-ID，不重复造一个问题。

问题确实影响预期时，将分析标记为 `blocked`，不得把猜测写成已确认规则。可继续交付不受影响的分析草稿，但要清楚标出阻塞范围。

## 输出

按 operation 将分析产物统一放在 `<module>/interfaces/<API-ID>-<slug>/`：主文档为 `interface-analysis.md`，问题单为 `clarification-questions.md`，必要的接口级 Context Card 和 Data Closure 也放在此目录内。目录、ID、索引和模板按[接口分析产物契约](./references/interface-artifact-contract.md)执行，不与模块级 `preanalysis/` 混放。

先定位已有权威文件。当前 operation 的旧分析或问题单位于 `interface-analysis/endpoints/`、`interface-analysis/artifacts/` 等旧位置，或接口目录的问题单仍使用旧名称 `03-clarification-questions.md` 时，分析或重构该 operation 时迁入单接口目录并使用当前名称，保留已有内容、问题答复和状态，同步更新已有索引与链接；不迁移本次未指定的其他 operation。模块级 `preanalysis/03-clarification-questions.md` 保持原名。发现多个候选权威文件时先核对索引并合并到一个明确文件，不平行维护副本。

每个 operation 维护接口分析文档和 `clarification-questions.md`；问题文档即使无问题也保留，并明确写“当前无待确认问题”。`data-closures/` 仅在数据库相关且模块级闭包不能直接满足本接口语义时创建；`context-cards/` 仅在存在下游可复用的复杂局部上下文时创建。不得复制整模块闭包、重复模块问题或为满足目录结构创建空卡。

下游衔接：`api-test-plan` 读取接口分析、接口问题清单中的未关闭问题及其引用的 FC/DC；未关闭且影响预期的问题不能转成确定测试点。`api-test-automation-design` 沿用测试点引用的接口级或模块级 DC；具体环境参数、可执行 SQL 和用例数据由该阶段补齐，不回写为接口分析产物。

分析文档应让读者先看懂接口最终负责什么、核心规则是什么，再沿着请求和数据流查到细节。新建文档优先采用以下结构；已有文档结构清楚时沿用并补齐，不适用的章节可以省略或合并，不为凑齐标题引入无关内容。

```markdown
# <模块/API 名称>接口分析
> operation：<HTTP method + path + operationId>
> 分析状态：<ready/blocked>

## 1. 接口定位与结论摘要
## 2. 分析范围与依据
## 3. 请求与接口契约
## 4. 业务规则与数据处理流程
## 5. 响应字段与结果分支
## 6. 职责边界与副作用
## 7. 来源差异、假设与待确认问题
## 8. 测试方案交接
```

各部分按以下方式组织，避免把同一规则在“结论、算法、总结”中重复写多遍：

- **接口定位与结论摘要**：用一小段说明接口的业务用途、关键输入和输出，以及已确定的核心处理口径。摘要只概括结论，不代替后文依据。
- **分析范围与依据**：列清本次 operation、调用路径与相邻职责边界；用来源表说明需求、适配答复、OpenAPI、数据库材料及必要实现资料各自用于判断什么，并注明版本/状态和关键定位。列出实际查阅的相关历史来源及具体定位，简述哪些历史行为经当前依据确认沿用、已变化/不适用或待确认，以及可参考的经验；不要求单独制作历史对照表。列出复用的模块级 FC/DC 与接口专属辅助产物链接。不要把实现资料列成业务规则来源。
- **请求与接口契约**：说明外部调用路径与内部 operation 的差别（如存在）、参数含义及枚举/方向映射、必填/默认/null 语义、校验顺序和错误返回。多个错误条件可用一张表表达 HTTP 状态、业务 code、message、data；框架绑定错误与业务校验错误分开。
- **业务规则与数据处理流程**：按需求或已确认的业务决策顺序讲清输入对象如何被筛选、映射、关联、排序/选取、计数或聚合；实现实际执行顺序若有差异，作为实现观察另行标明。对双向数据源等关键分支，用小表明确每种请求值对应的来源/目标。说明会改变结果的时间精度、时区、状态过滤、唯一性、缺失映射、重复记录及边界条件；只写有证据且影响本接口的规则。可用简短流程图辅助，不复制实现代码或待测 SQL。
- **响应字段与结果分支**：用字段表说明字段的业务含义、取值/枚举、来源映射、nullable 或条件返回；再区分成功有结果、成功空结果、业务错误和服务异常。空数组、`null`、缺字段等不得混为一谈；示例仅用于解释有歧义的组合，不重复完整 schema。
- **职责边界与副作用**：明确接口负责和不负责的行为，区分后端可观察契约、前端交互以及相邻写接口；说明读写副作用和重复调用语义。只列与本接口容易混淆或会影响测试归属的边界。
- **来源差异、假设与待确认问题**：将当前需求/用户确认、接口契约、数据库事实、实现观察分开描述。冲突项说明当前依据、未决点和对预期的影响；数据库约束或环境行为未验证时标为假设/未知。问题正文维护在 `clarification-questions.md`，分析文档只摘要阻断影响并链接，避免维护两份问题表。
- **测试方案交接**：简要收束接口最终行为、需关注的规则边界、可复用 FC/DC、已知资料缺口及测试归属；不列测试点，不写 SQL oracle、具体造数步骤、Excel 用例或脚本步骤。Data Closure 记录数据语义、关系及准备/清理边界，不记录测试样本或可执行 SQL。

若为已有接口迭代，摘要中说明本轮改了什么、哪些相关旧规则继续适用或不再适用；按需要用简短说明或小表，不要求逐条复制历史文档或固定生成历史审计矩阵。不要把旧数据库快照、过期样例、测试用例清单或下游实施内容混入接口业务基线；只有它们能解释当前规则或风险时才简述并标明来源性质。

文末注明 `分析状态：ready/blocked` 和 `测试方案就绪：是/否`。就绪为“否”时列出阻断问题；就绪为“是”时用一句话说明主要业务口径已足以进入测试方案。状态不能代替结论和问题正文。

## 停止条件与自检

- 需求、operation 或权威接口文档无法唯一确定，或关键来源缺失/版本冲突影响结论：交付可确认部分并标记阻塞，不猜测。
- 只有业务决策需要用户回答；信息能从资料查到时先自行查证。
- 核对 operation、请求/响应/空值语义和数据库路径没有串到相似接口。
- 问题清单存在且只维护接口专属问题；模块级问题通过原 Q-ID 引用，不重复登记。
- 数据库相关时核对模块级 DC 是否足够；仅在有接口专属缺口时建立最小 DC，并确保与分析文档一致。
- Context Card 仅为下游可复用复杂上下文建立；无必要时不创建空目录或索引。
- 产物含 Mermaid 图时，用可用解析器或目标预览检查语法及渲染；节点文本中的括号等特殊字符使用引号。无法验证时如实说明，不声称渲染通过。
- 每条关键结论均可追溯；实现现状没有伪装成需求；没有生成测试点、oracle SQL、用例或代码。
- 分析文档和问题清单完成后即停止，不自动启动 `api-test-plan`。报告路径、状态和需要用户处理的事项，等待答复/审核或明确的下一步指令。
