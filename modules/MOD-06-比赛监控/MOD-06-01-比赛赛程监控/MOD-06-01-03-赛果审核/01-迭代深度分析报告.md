## 一、模块定位与迭代背景

### 1.1 模块在系统中的位置

赛果审核是**比赛监控 → 赛果确认链路的第一环**（赛事运营的核心风控环节）：

```
比赛完场 → 【赛果审核】(本模块, 每人独立审核) → 赛果确认/批量确认(≥2人一致)
        → 赛果批次(≥3人审核) → 提交赛果文件(A2) → 开奖
```

- **接口**：POST `/data-backend/event-match-check`（提交）、GET `/data-backend/event-match-check/check-source-id`（回显）、GET `/data-backend/event-match-check`（列表）、**POST `/data-backend/event-match-check/batch`（OpenAPI 新增：批次维度批量创建/修改）**、GET `/event-match-check/event-match`（按比赛查审核记录）；
- **数据落点**：`event_match_check`（check_type=**2** 赛果审核，与 type=1 事件核实共表）；审核内容 JSON 存 `change_info`；审核时主队存 `bd_matchup_home_team_id`；
- **权限点**（实库 toto_permission #81）：比赛监控-比赛赛程监控-赛果审核。

### 1.2 本次迭代核心变化（PBL-611：支持辅数据源）

**一句话概括**：审核界面从"单一标准化数据视图"升级为**贝泰/纳米双数据源标签页**，足球项目可在两源间切换查看比赛状态与比分后填写核实结果；提交时记录所选数据源。

版本对照（✅ 上轮更新 + **⭐ 本次需求变更** vs 旧版删除线内容）：

| # | 旧版（删除线） | 上轮更新（✅） | 本次变更（⭐） |
| --- | --- | --- | --- |
| 1 | 无数据源概念 | 展示**贝泰数据、纳米数据标签页**，可切换 | **非足球项目不展示数据源标签**（原为"默认纳米+贝泰置灰"） |
| 2 | ~~比分显示系统采集的开奖用的比分~~ | 比赛状态、比分按**所选数据源**分规则显示 | **纳米标签下比赛状态为"未开赛"时不显示比分** |
| 3 | 无 | 回显审核信息时，**数据源标签**也回显审核时所选（历史数据显示默认值） | — |
| 4 | "比赛状态非完场时不可选赛果正确" | 细化为"**当前标签**的比赛状态非完场时不可选赛果正确" | — |
| 5 | 提交时按核实结果更新 | 提交时按"选择的**数据源**及核实结果"更新赛果、主客队顺序 | — |

## 二、本次更新逐条深度拆解

### 2.0 ⭐需求变更点 A：非足球项目不展示数据源标签（需求包条目 1.1.2，替换原✅规则）

**规则原文（⭐）**：非足球项目不展示数据源标签。

**深度解读**：
1. **替换关系明确**：该⭐条目直接替换上轮✅的"非足球项目默认选中纳米数据，贝泰数据标签页置灰"——非足球从"双标签+贝泰置灰"变为**整组标签隐藏**，弹窗无任何数据源切换 UI；
2. **交互一致性推论**：非足球无标签 → "当前标签"概念在非足球下不存在 → 更新点④"当前标签的比赛状态非完场时不可选赛果正确"在非足球下退化为**按标准化（s_match）状态判断**（与条目 1.4.1"非足球项目显示标准化比赛信息"一致，形成逻辑闭环）；
3. **影响面（实库）**：正式赛程中非足球比赛共 1457 场（篮球 647、冰球 751、橄榄球 50、网球 71、其他 8+2）——这些比赛的审核弹窗形态全部改变；
4. **连带影响**：
   - 回显规则（更新点③）：非足球比赛无标签可回显——历史数据源标签"显示默认值（非足球=纳米）"的规则**随之失效**，非足球回显时不存在标签项；
   - 提交落库（更新点⑤）：非足球提交时 dataSource 取值——界面无标签选择，**提交应固定写纳米（NAMI=1）或按实现不写**，需在测试中验证（推测固定 1，待实测确认，不作断言预设）；
   - "切换标签重置表单"（已确认结论①）：非足球无从切换，规则仅对足球生效；
5. **与"无源运动兜底"的关系**：上轮确认"网球等无源运动正常显示标签、走标准化兜底"——⭐变更后**非足球（含无源运动）统一不展示标签**，该确认结论的非足球部分作废；但"数据显示标准化（s_match）状态和比分"的兜底逻辑不变（条目 1.4.1 非足球本来就读标准化）。

### 2.0.1 ⭐需求变更点 B：纳米标签"未开赛"不显示比分（需求包条目 1.4.2.1，新增子规则）

**规则原文（⭐）**：足球项目选中纳米数据时……比赛状态为"未开赛"时，不显示比分。

**深度解读**：
1. **适用范围仅纳米标签 + 仅"未开赛"态**：规则挂在条目 1.4.2（足球纳米标签）之下，只约束纳米源显示；
   - 贝泰标签/非足球（读 s_match）无此规则——需求未要求，不扩散；
2. **"未开赛"的判定口径**：纳米 status_id=1（状态定义表纳米足球列）；
3. **数据形态核验（为什么要加这条规则）**：纳米源存在**未开赛但 home_scores 已有值**的脏数据（实库 2 场：4416273 scores=[4,3,...]、4590190 scores=[1,1,1,0,3,...]，status=1）——若不加屏蔽会显示"未开赛 + 比分 4:3"的矛盾 UI。⭐规则本质是**前端按状态屏蔽比分展示**；
4. **边界问题（已按需求原文解答）**：
   - **"待定"态（0/13）有比分时是否显示**？——需求 1.4.2 总规则要求显示纳米源的开奖用比分，1.4.2.1 仅将"未开赛"列为不显示的例外，**待定等其他状态按原规则显示**（实库待定 13 共 1194 场、其中 91 场有值，可造数验证）；
   - **推迟/中断/腰斩/取消态有比分时**同理，不在"未开赛"例外之列，**按原规则显示**（实库推迟 4765 场中 188 场有值、取消 979 场中 7 场有值）；
5. **与"赛果正确可选性"的联动**：纳米标签"未开赛"时【赛果正确】本就置灰（更新点④），无比分显示与该规则方向一致，无冲突；
6. **半场/全场都受影响**："不显示比分"应覆盖全场与半场两个展示项（未开赛时两项均不显示，而非显示 0:0）。

### 2.1 更新点 ①：双数据源标签页（需求包条目 1.1）

**规则原文**：展示贝泰数据、纳米数据标签页，点击可切换数据源；足球项目默认选中贝泰数据，比赛未匹配纳米数据时纳米数据标签页置灰；~~非足球项目默认选中纳米数据，贝泰数据标签页置灰~~ → **⭐非足球项目不展示数据源标签**。

**深度解读（结合实库源覆盖数据）**：

| 场景 | 标签展示 | 实库数据支撑 |
| --- | --- | --- |
| 足球 + 双源匹配 | 贝泰/纳米两标签，默认贝泰，可切换 | 足球 32485 场中 27569 场双源（85%） |
| 足球 + 仅贝泰 | 默认贝泰，**纳米置灰** | 足球 4905 场仅贝泰；活跃比赛 4227 场无纳米匹配 → 高频场景 |
| **非足球（⭐变更后）** | **不展示任何数据源标签** | 正式赛程非足球 1457 场（篮球 647/冰球 751/橄榄球 50/网球 71 等）全部受影响 |
| 足球 + 仅纳米 | 理论分支，数据不可达 | 实库 0 场 |

**隐含规则挖掘**：
1. "比赛未匹配纳米数据"的判断依据 = `s_match.nami_match_id IS NULL`（已确认）；
2. 置灰是**不可点击**而非隐藏（足球场景）；
3. 贝泰源状态是字符串枚举、纳米是数字状态码——双源切换时状态展示口径不同（见 2.2）。

### 2.2 更新点 ②：状态与比分按数据源分规则显示（需求包条目 1.4）

**规则原文**：
- 非足球项目 + 足球选贝泰 → 显示**标准化**比赛信息（s_match）的状态和开奖用比分，状态映射见 PRD"通用需求"；
- 足球选纳米 → 显示**该比赛关联的纳米数据源比赛**（nami_football_match）的状态和开奖用比分，映射见《数据模型设计》；
- 比分顺序与主客队一致。

**深度解读——这是本次迭代技术含量最高、测试价值最大的点**：

#### （A）两个数据源读的是两张不同的表

| 当前标签 | 数据读取表 | 状态字段 | 比分字段 |
| --- | --- | --- | --- |
| 贝泰（或非足球） | `s_match`（标准化，已融合贝泰主源） | `status_id`（复合状态码 4 位） | `home/away_score_half` + `home/away_score`（开奖用 int） |
| 纳米（足球） | `nami_football_match`（原始源表，经 `s_match.nami_match_id` 关联） | `status_id`（纳米足球 0–13 枚举） | `home_scores/away_scores` JSON 数组 |

#### （B）状态映射关系（两套映射，测试必须分别覆盖）

**贝泰标签 / 非足球 → PRD"通用需求"映射（s_match.status_id → 8 个展示状态）**：

| 展示状态 | s_match.status_id 集合（xx=比赛态, yy=赛程态） |
| --- | --- |
| 未开赛 | 1000/1001/1002/1003（10xx） |
| 比赛中 | 1100/1101/1102/1103（11xx） |
| 完场 | 1200/1201/1202/1203/**1205/1206**（12xx，含赛果已提交/已开奖） |
| 推迟 | 1300–1306（13xx） |
| 中断 | 1400–1406（14xx） |
| 腰斩 | 1500–1506（15xx） |
| 取消 | 1600–1606（16xx） |
| 待定 | 1700 |

> 注意：审核场景下比赛必然已开售（yy≥3），实际可见的是 xx03/xx05/xx06 等；但映射函数按 xx 段归类。实库 s_match 状态分布印证主态为 1206（已开奖 9 千）、1003、1203 等。

**纳米标签 → 《数据模型设计》映射（nami_football_match.status_id → 展示状态）**：

| 展示状态 | 纳米足球状态码 |
| --- | --- |
| 未开赛 | 1 |
| 比赛中 | 2 上半场 / 3 中场 / 4 下半场 / 5 加时赛 / 7 点球决战 |
| 完场 | 8 |
| 推迟 | 9 |
| 中断 | 10 |
| 腰斩 | 11 |
| 取消 | 12 |
| 待定 | 0（异常未判）/ 13 待定（6 加时已弃用） |

> 同一个"完场"在两个标签下分别是 s_match.status_id=12xx 与 nami status_id=8——**双源状态可能不一致**（实库样本：s_match=22222 纳米 status=8 完场、贝泰 status=postponed、标准化=1306 推迟已开奖）。切到纳米标签看到"完场"而贝泰标签显示"推迟"，是真实存在的数据形态，不是 bug。

#### （C）比分映射关系（《数据模型设计》"比赛-数据库字段"表，实库逐条验证）

**纳米标签（足球）——`home_scores/away_scores` JSON 数组下标语义**（实库样本 `home_scores=[4, 1, 0, 2, 6, 0, 0]`；**⭐未开赛（status_id=1）时全场与半场比分均不显示**）：

| 展示项 | 纳米字段 | 依据 |
| --- | --- | --- |
| 主队全场 | `home_scores[0]` | 需求集成表明文（实库 3 万场验证一致） |
| 主队半场 | `home_scores[1]` | 需求集成表明文 |
| ⭐未开赛态 | 不显示比分（两项均不显示，非 0:0） | ⭐需求变更 B；实库存在 status=1 但 scores 有值的脏数据（4416273=[4,3,...]、4590190=[1,1,1,0,3,...]），规则即为此类场景的前端屏蔽 |
| （其余下标 [2]–[6]） | 语义文档未定义 | 不做取值断言 |

**贝泰标签（足球）→ s_match 开奖用字段的原始来源**（《数据模型设计》集成表）：

| s_match 字段 | 贝泰原始字段 | 纳米优先规则 |
| --- | --- | --- |
| home_score_half | beitai periods[number=1].homescore | **优先纳米** home_scores[1]（文档备注列） |
| home_score | 贝泰 periods 1+2 合计 | **优先纳米** home_scores[0]（文档备注列） |

> **实库观察（供参考，不作为断言）**：实库存在 11 场 s_match 全场/半场跟随贝泰而非纳米的例外（含 1 场贝泰 status=abandoned 场），提示"优先纳米"融合可能存在条件分支 → 已列入待确认问题⑦。

**非足球项目（纳米单源）**：

| 运动 | 全场比分来源 | 半场比分 | 依据 |
| --- | --- | --- | --- |

### 2.3 更新点 ③：审核信息回显含数据源标签（需求包条目 2）

**规则原文**：若当前用户已审核过赛果（无论是否已确认），主客队切换图标、**数据源标签**、核实结果、核实渠道显示审核时填入的信息；**历史数据的数据源标签显示默认值**。

**深度解读**：
1. 回显四要素中"数据源标签"是本次新增——意味着**提交审核时必须持久化所选数据源**；
2. **数据落点（★库表变更）**：`event_match_check` 新增**独立字段 `data_source_type`**（初版设计为 change_info JSON 内的 dataSource 键，后拆出为独立列），枚举 NAMI(1)/BEITAI(3)；实库 6.3 万条存量记录该字段均为空——这正是"历史数据显示默认值"规则的数据基础：**存量数据无数据源记录，无法回显非默认标签**；
3. 测试分层：新审核记录（data_source_type 有值，回显所选项）vs 历史记录（字段为空，回显默认值=足球贝泰）；
4. **⭐变更连带**：非足球不展示数据源标签 → 非足球比赛（含历史与新记录）回显时**无标签项可回显**，"历史非足球显示默认值（纳米）"的规则随之失效；
5. 回显时主客队切换状态 = `bd_matchup_home_team_id` 与当前展示主队的比较（实库 9 条主客互换审核样本：check.bd_matchup_home_team_id=127 ≠ s_match.home_team_id=1198 → 回显时互换图标应高亮）。

### 2.4 更新点 ④："当前标签"状态约束赛果正确（需求包条目 4.1）

**规则原文**：**当前标签**的比赛状态非"完场"时，不可选择"赛果正确"。

**深度解读**：
1. 旧版判断的是比赛（整体）状态；新版判断**当前所见数据源的状态**——两源状态不一致时（如贝泰=推迟、纳米=完场），切标签会实时改变"赛果正确"可选性：**贝泰标签下不可选、纳米标签下可选**。这是规则 2.2(B) 双源状态不一致场景的直接联动，必测；
2. "完场"判定口径：贝泰标签 → s_match.status_id 12xx；纳米标签 → nami status_id=8；
3. 非完场时选"赛果错误"是唯一路径 → 选状态（完场/推迟/中断/取消）→ 非完场状态比分固定 -1:-1（实库验证：`{"statusId": 1300, "homeScore": -1, "awayScore": -1, "homeScoreHalf": -1, "awayScoreHalf": -1}`，1300 推迟/1400 中断均有真实样本）。

### 2.5 更新点 ⑤：提交时携带数据源（需求包条目 8.2）

**规则原文**：校验通过后，根据选择的**数据源**及核实结果更新当前用户对应比赛的赛果、主客队顺序，并更新赛果状态为已审核。

**深度解读**：
1. 提交主客队顺序校验（条目 8.1）不变：核实结果主客顺序 ≠ 赛程顺序 → 提示"当前比赛的主客队顺序与赛程不一致，请修改后再提交"（赛程顺序 = bd_batch_matchup 的 team_reverse+home_team_id，同比赛多批次多编号时取一致顺序）；
2. 更新落点：`event_match_check` 新记录（check_type=2，uk 无——实库同用户同比赛无重复记录，推测 upsert 语义或前端防重）；
3. "数据源"影响的是**审核依据的记录**（回显与确认时比对口径），不改变 change_info 的比分语义（仍是 statusId+四比分）；赛果确认的 ≥2 人一致比对按 PRD"不比较用户审核时选择的数据源"（赛果确认条目 3），数据源仅作审核过程参考。

### 4.4 提交接口语义（OpenAPI）

- POST `/data-backend/event-match-check`：单条提交（body 含批次/比赛/数据源/核实结果/渠道/比分）；
- POST `/data-backend/event-match-check/batch`：**批次维度批量创建/修改**审核信息（较 PRD 单场提交流程更强的批量入口，测试需覆盖）；
- GET `/check-source-id`：按比赛回显当前用户审核（回显数据源的读取来源）；
- 错误码规范：0 成功 / 2 业务校验 / 31 服务异常。

### 5.1 本次迭代的九个核心测试面（⭐含两处需求变更）

1. **标签页展示矩阵（⭐变更 A 更新）**：足球双源（默认贝泰可切换）/足球仅贝泰（纳米灰）/**非足球不展示任何标签**（含篮球/冰球/橄榄球/网球等全部非足球运动）；
