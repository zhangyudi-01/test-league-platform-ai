## 二、Oracle 与比较边界

[api-query-oracle.sql](./api-query-oracle.sql) 提供 6 条可独立参数化的 MySQL 只读查询：竞彩与标准比赛/贝泰球队事实、纳米原始 `incidents`、允许类型贝泰事件、全部正式赛程、当前用户审核、贝泰事件原始快照。执行参数分别为 `[P]`、`[S]`、`[H,H,H,H,S]`、`[S]`、`[S,当前账号]`、`[贝泰来源比赛ID]`；P 为请求官方 ID，S 从首条查询读取并对照本次 fixture 返回的 ID，H 由用例按 3.2 的球队关系单独验证得到。测试账号来自现有认证配置，不写入工作簿或文档。

1. **球队身份先行**：每场按 3.2 登记抽象球队 A/B：竞彩、标准化与贝泰的球队关系由关联表回读核验；本次合成纳米 JSON 的 1/2 对应 A/B 是显式构造约定，helper 不创建纳米比赛或球队档案。确保两队不同且 H 恰等于贝泰两队之一。不能仅凭 `if_change`、审核方向、被测返回值或跨来源不同 ID 的数字相等推导身份。纳米预期按原始数组逐项解码、按已构造身份决定是否交换 1/2 和两侧比分；中立 0 不变、缺失 position 保持 null。贝泰 SQL 用 H 直接计算 position 和分数，原始字段与响应逐项对应。SQL 对 team 为 null/未知的 position 不指定预期，测试点 30 仅核对 team。
2. **读取事实而不复刻服务**：SQL 不根据审核或确认选择一个“优先记录”；场景 42～46 通过查询确认准备的状态，再独立核对最终竞彩方向。正式赛程必须恰好一条、当前账号赛果审核最多一条；不满足则按数据前置失败，不采用 `LIMIT 1` 或“最新记录”弥补。输出相同不能证明内部执行顺序。
3. **列表和顺序**：纳米使用原 JSON 数组次序；不存在 live 行、SQL NULL、空数组均期望 `[]`。贝泰比较完整符合九类的事件集合，`orderId` 不同的升序；相同 `orderId` 的事件按 ID 逐一对应并断言各出现一次，不约定同组顺序，也不增加 ID 排序为接口要求。用例数据须隔离，使返回范围不仅限于本次记录 ID 的查询也不会混入其他事件。
4. **元素和时间**：按 OpenAPI 字段名映射，不用默认 `0`、空字符串或空数组替换 null；查询 `team=null` 时不猜测 position。日期时间保留数据库原值，并在确认测试环境、接口时区/序列化后作等价时间比较，不强加字符串格式或未经确认的时区。涉及 null 字段显式检查键存在且值为 null。
5. **只读性**：测试点 47 在调用前后按主键快照语句 1 和原始贝泰事件查询的关联、`if_change`、来源 ID、team/比分，不用已换向的语句 3 代替原值。测试时禁止并发采集/修改该独立数据；失败不能简单归因于本接口。
6. **包装/错误**：成功核对 HTTP 200、`code=0`、`message=OK` 和目标数据；错误 1～7 只核对 `code=2`，不限定错误 HTTP 状态、message、data。现有 `API.request` 的 `expect_http_code or 200` 无法关闭状态码检查；须先确认真实传输行为，必要时以经审核的最小范围方式使错误用例可只断言业务码，不修改测试点预期。此问题是工程门禁，非已验证缺陷。

### 2.1 client 与 generator 的断言分工

- `DataBff.test` 继承 `API.test → request → verify_response`：client 首次 `next(generator)` 后登录、发请求；`request` 的 `finally` 先 `send(actual_result)` 执行 generator 后置，再检查 HTTP 和预期。入口不手动推进 generator。
- HTTP 默认断言 200，`expect_http_code or 200` 不能关闭。非空 `预期` 且状态非 500 时才调用 `json_tools.diff` 作完整响应比较；状态 500 跳过比较。空 `预期` 时默认成功字段不一致只打印，不抛断言，不构成成功校验。以上是源码静态分析，不是实测。
- **现有实现，待按 2.2 修订**：本接口使用空 `预期`，避免把未约定字段、同序事件或错误响应写为完整预期。成功场景 HTTP 200 由 client 断言；generator 显式断言 `code=0`、`message=OK` 和该场景的 `data`、顺序、空值、字段或只读判据。错误场景仅显式断言 `code=2`，但 HTTP 仍受默认 200 限制；要真正不限制 HTTP 须先审核最小适配并验证，不能称为已覆盖。第 9 点第二次请求的状态、成功包装和 data 比较须单独负责。
- 请求失败时响应可能缺失或残留，登录失败会尝试再次推进 generator；后置断言不得把残留当本次结果，清理须独立且不遮蔽原异常。须用受控异常测试验证。

### 清理、失败与重跑

1. generator 在首次写入前进入 `try/finally`，记录本次创建的关系唯一键、event_id、纳米来源 ID、审核 check_id 和原字段；不得删除 fixture 的 P。按用户确认复用工程入口 `data_bff.test(case_dict, eval(case_dict['处理数据'] or 'None'))`，不额外包裹 `close()`；框架负责推进 generator，后置断言避免覆盖已有异常。已验证本轮常规请求及断言失败时清理；未对所有中断方式做故障注入。
2. 清理顺序：删除本次审核 `check_id`、贝泰 `event_id`、新增纳米 live 行和竞彩球队关系 `relation_id`；恢复 P 的关联/方向/队序，以及 S 来源 ID、正式赛程队序、确认和比分等被修改字段。尤其贝泰 ID 暂置 null 时须在批量 teardown 前恢复原 ID；纳米 helper 的删除函数不恢复 S。禁止按 `match_id+账号` 扩大删除不属于本次测试的审核记录。
3. 用例结束后先断开并恢复 P→S；赛程 fixture 确认 `draw_no`、比赛及引用全部归本次所有且无外部引用后，调用 `delete_bd_game_draw_data(draw_no, delete_matches=True)`；Workbook fixture 再按相反 Sheet 顺序删除已登记的 P 和 T。fixture 顺序以依赖关系或测试入口明确保证，不依赖 pytest 参数顺序。旧删除函数会清理事件域并删除赛程/标准比赛/复制来源比赛，文档说明审计表保留；事故或外部新增引用导致无法证明归属时停止并报告，不扩大删除。按 ID 回查并重复运行两遍；审计保留不冒称完全无痕。
4. 若初始化赛程池被多个用例共享，每个用例只持有当前 S，恢复其状态后才交回池；单独运行任一 Excel 行时同一 fixture 仍创建所需基础链，不依赖其他用例。写库串行、禁并行采集或其他测试对同一 ID 写入。

### 4.1 Excel 到 generator 的具体差异

本节保留重构前的设计和映射以供追溯；当前实现以 2026-11-05 结构重构记录及代码为准。

`处理数据` 直接指定业务函数，优先传 `case_dict`；必要且无法从真实请求推导的场景差异才以具名业务数据参数承载，不新增控制列，不从标题、编号或场景码再分发。具体 ID 来源和唯一性如下，示例是设计而非已创建数据：

- 参数 Sheet 保留真实字段 `sportId|int`、`sportteryMatchId|json`、`matchId|int`。合法 P 的 `sportteryMatchId` 单元格写 JSON 对象，如 `{"match_no":"LIVE002A"}`；P3 用 `{"match_no":"LIVE002C"}`。`Excel.get_asdict` 的 `|json` 转换后由 `api_test_data` 合并入 `case_dict['参数']`；generator 在首次 `yield` 前以 `SELECT match_id FROM sporttery_football_match WHERE match_no = %s` 参数化查询，严格要求恰好一行，将对象替换为所得整数。`match_no` 不是数据库唯一键，需装库前全局查空、运行期隔离并逐次检查唯一性；不得直接发送对象。本次闭包修订已获审核，后续实质变更仍须复审。
- 直接 ID 保持在 `sportteryMatchId` 同一列：第 4 点用文本单元格写 JSON 数字字符串 `0`，第 5 点同样用文本写受控不存在的整数，发送前确认不存在；第 2 点删除该键。不可写 Excel 数值 0：现有 `|json` 转换按真假值分支，数值 0 会变成 `{}`，非零数值也不能直接交给 `json.loads`；文本 `0` 才解析成整数 0。空单元格同样会成为 `{}`，缺参须在 generator 中明确删除键，并通过项目读取链验证。缺参和非法场景不额外构造定位列或复制 ID；最终请求只含契约参数。
- `sporttery_live_base_data` 仅为测试入口 fixture，不作为处理函数参数；`sporttery_live_matches` 返回的动态 S 仅传给确需绑定、核对或第二场数据的业务 generator，最终消费者直接使用其 `match_ids` / 正式赛程 ID，无法从尚未绑定的 P 推导。其他函数不透传此上下文。第 10 点第二个 P 的 `match_no` 作为该行的第二场业务数据，由该 generator 参数化唯一查询；它不是额外请求参数。事件、比分和状态由业务函数消费，不能重复传请求已有 ID。
