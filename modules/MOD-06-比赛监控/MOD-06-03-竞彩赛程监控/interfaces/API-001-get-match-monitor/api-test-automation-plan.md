# 竞彩赛程监控列表接口自动化实施方案

> API-001：`GET /sporttery/match-monitor`；经 BFF 调用 `GET /data-backend/sporttery/match-monitor`。  
> 方案状态：已审核并部分实施；实际执行结果和未完成项见第七节。  
> SQL 已在授权测试环境进行语法检查，并用于已实施用例的独立预期；各测试点的覆盖和失败情况以第七节为准。

## 一、范围和依据

输入为已审核的 [100 条接口测试点](./api-test-plan.md)、[接口分析](./interface-analysis.md)、[问题确认](./clarification-questions.md)、[DC-001](../../preanalysis/data-closures/DC-001-列表聚合数据闭包.md)、[ADC-001](./data-closures/ADC-001-列表贝泰直播数据路径.md) 及 [历史复用回顾](../../reference-analysis/match-monitoring-reuse-review.md)。物理字段以项目 DDL 为静态依据，实际目标库的版本和权限实施前核实。

只实现该接口；前端刷新、展示颜色与占位符、进程详情以及其他接口不在本方案内。测试点 74、77 保留，但分别依赖隔离故障注入和可控时钟；没有安全条件时明确阻断。赛事简称为 null、多跳/断链/跨项目异常替换链不扩充预期。

## 二、独立预期

[api-query-oracle.sql](./api-query-oracle.sql) 从请求范围内的竞彩赛程独立查询两运动项目、源联赛/球队、同项目标准比赛及有效单跳替换、事件、类型 1 备注和足球贝泰 live。事件、备注先分别聚合，避免多对多放大；事件取最新 `update_time, event_id`。不查询 `sporttery_task`，不套用旧比赛监控的开售过滤。SQL 的参数是有效项目 JSON 数组和实际生效的两个业务日，由 `DB_CONN.get_asdict(sql, args)` 绑定；调用前验证目标 MySQL 版本、驱动 JSON 参数和时区。非法参数直接检查业务错误，不通过 SQL 为错误响应制造预期。

SQL 返回无序源数据，测试代码独立转换为响应预期：

- 日期默认值按 `Asia/Shanghai` 的服务时钟确定，分别应用于缺失的起止日；显式日期直接采用请求值，保留每个项目下的全部匹配结果。定位键为 `(sportId, matchId)`，`matchId` 使用完整 64 位整数，不借用标准比赛 ID。默认日期测试要避开午夜跨日或固定隔离服务时间，不能以运行测试机器日期代替服务时钟而不核实。
- 字段按 SQL 的源值映射：竞彩队名及 ID 保持来源顺序；标准排名仅 `if_change=1` 对调；有效标准比赛提供标准 ID、来源 ID 和 `matchStatus`。`sportName` 为足球/篮球；开奖状态分别断言 1、2、3 对应的结果。live 存在以 `live_match_id` 判断，不以可空字段判断，按五个原字段断言，篮球及缺 live 返回 null。
- 已开奖只取竞彩来源，足球取半场/全场字符串，篮球将官方主客分数组成全场；未开奖只取标准来源，并在 `if_change=1` 时交换各组主客分数。足球半场和全场各自允许缺失；篮球半场为 null；双方分数组不完整时该组为 null。选定来源无有效比分时 `score=null`，不从另一来源补齐；有效时 `source` 分别是 `SPORTTERY` 或 `S_MATCH`，明确断言 `periods` 缺席。仅使用测试方案已确认的有效分数和 null；不推定非法文本、单侧官方篮球分数的其他语义。
- `eventCount` 和 `remarkCount` 分别来自 SQL 聚合；最新事件标题对应 RED/YELLOW/ORANGE/GREEN，其中绿色的 `reason_title` 为“比赛方变更”（API-001 Q-011）；其他或无事件为 NONE。事件同更新时间使用字段现有字符排序规则进行 ID 决胜，测试用固定长度、同大小写、排序明确的 ID。无任务字段的存在性契约不明，不断言 `taskType` 存在或缺失。
- 排序独立检查测试点规定的偏序：非空开赛时间在空值前；同类记录按编号数字升序，无法解析的编号在可解析编号后，同号按官方 ID 升序。使用构造明确的 `周二002/周二010/周二101` 与无法解析值；对于跨项目同编号同 ID 等未指定的完全同键，不虚构额外顺序。针对 19～23 直接检查受控目标记录的相对顺序，额外检查项目过滤与范围不漏数据。无分页场景检查全部超过 100 条受控 ID。
- 成功响应用 Excel 的 `code=0`、`data=[]` 作为预期骨架，在请求前以独立 SQL 结果填充 `data`，由 `data_bff.test()` 的完整 JSON 比较覆盖数据、顺序、字段、null、空字符串和 `periods` 缺席。`matchTime` 按时间值比较；顶层附加字段及 `taskType` 尚无确认口径，不据实际值推断业务预期。错误响应的业务断言仅约束 `code`，未确认的文案和附加字段不设预期。
- 当前公共 `API.request()` 默认断言 HTTP 200，无法由用例配置关闭，因此成功和错误用例统一走 `data_bff.test()` 后均受此框架默认约束。2026-11-03 对现有五条错误参数请求实测均为 HTTP 200，但这只是环境观察，业务文档尚未明确错误时的 HTTP 状态；若开发以后改用其他 HTTP 状态，需要先确认契约并处理公共框架能力，不能据此认定业务错误码不符合需求。

共享环境下用非默认、授权隔离业务日期与本次测试拥有的 ID 验证全量集合；默认日期可能有非测试记录，此时 SQL 应覆盖同一完整范围，且至少对本次受控记录精确断言。并发采集可能导致两次读取不一致，需在隔离环境暂停相关写入或提供一致快照；不能通过仅比对测试 ID 冒充全列表过滤正确。73 额外对精确 ID 范围内的源、标准、事件、备注、live 快照作请求前后比对，并连续请求两次。

## 三、数据准备与清理

### 3.1 选择方式

主要采用 **`data/init` 基础数据 Workbook + 显式 fixture 初始化 + generator 准备场景差异**。本接口多个测试点重复需要竞彩赛程、赛事、球队和标准比赛，且需要控制足球/篮球 ID 域、主客顺序、比分等关联关系。静态搜索当前 `common/` 和 data-bff 测试代码未发现竞彩基础赛程创建函数；`common/draw.py:create_bd_batch_matchup` 创建的是北单奖期、批次和赛程，并不创建竞彩赛程，因此不作为竞彩基础数据入口。旧 `monitoring_data.py` 的异常方法写旧事件域，不替代竞彩事件准备。

参考 [球队智能推荐 fixture](../../../../../../test-league-platform/testsuites/data-bff/team/conftest.py) 的 Excel 读取、记录成功插入键及清理思路；这是静态参考，不代表其在本接口已实际运行或可直接复制。实施时遵循现行代码编写规则，以 Workbook 本身表达表名、插入顺序、字段和首列清理键，不额外构造一套表/角色/字段映射。

### 3.2 基础数据 Workbook

`tests/test-league-platform/data/init/竞彩赛程监控列表基础数据.xlsx` 与接口测试用例 Excel 分开。一个 Sheet 对应一个真实表，首行为数据库字段名和项目支持的类型表达、第二行为说明、第三行起为可直接入库的基础数据；Sheet 按以下依赖顺序排列：

| 顺序 | Sheet / 表 | 共享基础数据及用途 |
| --- | --- | --- |
| 1～2 | `sporttery_football_league`、`sporttery_basketball_league` | 分别准备可区分简称的足球、篮球赛事。 |
| 3～4 | `sporttery_football_team`、`sporttery_basketball_team` | 分别准备可区分名称的主客球队，球队全称与简称不同，以便验证来源和回退。 |
| 5～6 | `m_competition`、`m_team` | 准备与竞彩名称不同的标准赛事、主客队，用于名称来源场景。 |
| 7 | `s_match` | 准备关联足球、篮球的标准比赛，填写不同状态、来源 ID、主客排名及比分。 |
| 8～9 | `sporttery_football_match`、`sporttery_basketball_match` | 各准备可重复使用的基础赛程，关联对应赛事、球队、同项目标准比赛，记录 `business_date`、`match_no`、`sell_status`、`if_change` 和比分。 |
| 10～12 | `beitai_football_match_live`、`sporttery_match_event`、`sporttery_match_remark` | 使用不同业务日的赛程隔离直播、事件和备注的各组真实记录。 |

例如，足球赛程行中的 `league_id`、`home_team_id`、`away_team_id` 和 `s_match_id` 指向前面 Sheet 的对应主键；篮球行同理。足球和篮球可分别准备一组相同官方比赛 ID 的记录，以验证项目隔离；实际固定 ID 须在目标库确认未占用并获准使用。示例用于说明关联，最终数据数量与字段按测试点需要设计，不在方案中虚构可用于实际库的 ID。

基础 Workbook 中的事件、备注和 live 行仅关联独立业务日的赛程，不污染其他用例使用的基础比赛。对于需要的多条基础比赛，在 Workbook 中直接表达真实字段和关联，不依赖 Python 按角色名反查或重建外键。初始化 Workbook 是固定数据，不使用日期表达式或 Python 表级转换；边界日期等少量增量由 generator 临时准备并清理或恢复。

名称来源和只读场景共享独立业务日的足球赛程，初始化标准赛事、球队、标准比赛及竞彩事件、备注；未关联标准比赛计数场景使用另一个独立业务日，初始化空关联赛程、两条事件和一条类型一备注。用例通过请求业务日查库定位，固定数据由 fixture 逆序清理，不在处理函数重复插入或删除。

### 3.3 运行入口及场景数据

`testsuites/data-bff/sporttery_match_monitoring/conftest.py` 中的显式模块级 fixture `sporttery_match_monitor_data` 负责共享基础数据：通过 `Excel` 读取上述 Workbook，按 `excel.file.ws_names` 的顺序插入。测试入口显式依赖该 fixture；处理函数只接收 `case_dict`，根据请求条件或赛事名称、业务日、比赛编号等业务键从数据库查询基础记录，不再次读取初始化 Workbook。单独执行一条参数化用例时也会初始化，不依赖其他用例或已有环境数据。多条用例同次运行时共享本次 fixture 建立的基线；串行执行且每条用例恢复自身改动，不能依赖前序用例。旧的 `match_monitoring/` 目录及其 `conftest.py`、比赛监控初始化函数均不修改。

用例 generator 对 fixture 创建且受控的行只做当前测试必需的少量修改；执行前保存原值，在 `finally` 中恢复。初始化 Workbook 承载的事件、备注和直播由 fixture 清理，generator 临时创建的增量由对应 generator 记录主键并清理。球队名称回退的 `NULL` 与空串由 Workbook 分别表达，已通过项目读取器和实际接口用例验证。

特殊场景：测试点 8～10、75～77 的业务日基于核实后的上海服务时间；8～10 及 77 需要在目标日期及相邻外侧设置足够的本次测试赛程，77 仅在可控隔离时钟下执行。18 在当前用例中批量创建超过 100 条同业务日赛程并逐键清理，基础赛事/球队可复用；19～23 若基础赛程数量不够则由该用例新增少量赛程。68 仅在能安全创建并清理旧 `s_event` 的情况下准备旧域事件；不能安全隔离时阻断该点。参数错误测试仍可依赖基础 fixture，不能以环境中已有比赛代替测试点 7 所需的受控足球赛程。

### 3.4 清理、隔离与闭包

先核实目标库版本、主键/唯一约束、外键、触发器、采集任务和固定 ID 的使用范围；Workbook 的固定主键及待构造但不应存在的关联 ID 必须预先检查未占用，冲突即停止，禁止 `REPLACE`、覆盖现有数据或使用 `MAX(id)+1`。无可靠独占数据范围或无法精确清理时阻断，不在共享环境冒险写入。固定 ID 复用只允许串行且上一次数据已清理；测试不能用上次残留当作基线。

fixture 在首次写入前建立清理保护，按 Workbook 顺序逐行插入并记录**成功插入的完整主键**；失败、测试结束或请求异常时按 Sheet 逆序仅删除本 fixture 已插入的行，检查残留。generator 对自己新增的 event/remark/live 或批量赛程记录成功主键，使用 `try/finally` 在请求及断言失败时逐键清理；对基础行的临时修改恢复原值。fixture 负责基础行，generator 负责场景增量，避免双重删除。测试入口只调用 `DataBff.test`；框架在登录失败或请求结束时继续 generator，场景自身的 `try/finally` 负责清理。实现时验证准备、登录、请求和断言失败等路径，保留原始异常并报告清理失败，不能单靠假设 `yield` 后逻辑必定执行。所有写库用例串行，采集并发无法隔离时不运行。

DC-001 的赛程、赛事、球队、标准比赛、部分事件及备注由基础 Workbook 承载；ADC-001 的贝泰 live 也由 Workbook 准备。其他场景临时新增的数据由 generator 清理。根据业务日期及 `(sportId, matchId)` 将测试记录与 SQL 结果对应；事件场景核对无对应任务。实施情况见第七节。
