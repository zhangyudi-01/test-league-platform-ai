### 1. 结构与责任

对照用户指定的 `testsuites/data-bff/team/test_nami_team_get.py::assert_team_get`：公共函数读取本行 `case_dict['参数']`，解析动态 ID、从独立依据拼装该行预期；场景函数仅负责所需的差异前置、特殊副作用检查和本场景清理，再通过 `yield from` 复用公共流程。Excel 的 `处理数据` 只写英语函数名及 `(case_dict)`。不把参数再次写入函数实参，不按用例标题、固定行号或数量分流，不新增场景控制列、登录函数、response 客户端或总路由。

普通用例的 pytest 入口保持 `data_bff.test(case_dict, eval(case_dict['处理数据'] or 'None'))`。允许 `get_test_data()` 仅负责读取 Workbook；如重复请求和并发需要独立测试函数，仅按这两个明确的处理函数表达式筛选对应数据，不做通用分组或定制参数展示。入口中的 fixture 形参只触发准备和清理，不传入业务函数。

以下函数为设计名称，最终 Workbook 和 Python 名称必须一致，不要求为每条用例新建函数：

| 函数或入口 | 职责 | 归属 |
|---|---|---|
| `assert_save_remark(case_dict)` | 公共预期：首次 yield 前解析比赛、按输入构造成功或错误的已确认预期；请求后根据独立 DB 状态检查写入；不可预先确定的响应部分按第 3 节处理 | 公共业务 generator；供常规和特殊业务函数复用，不负责登录 |
| `assert_update_remark(case_dict)` | 准备当前账号原备注，复用公共流程并检查同一 ID 更新 | 场景 generator |

### 3. 预期拼装与响应边界

1. `sportId`、`matchId`、账号和 `remark` 来自当前行，公共函数在首次 yield 前将自然键变换成官方数字 ID，并独立构造 `code=0`、`message=OK` 及测试点规定的 `sportId/matchId/account/remark/isCurrentUser`。备注预期按已审核规范化口径从原输入计算；用户感知字符计数包含首尾空格。错误场景预期业务码为 2，不固定未约定的错误消息和 data。
2. 独立 Q2 在请求后按完整业务键查库，验证新增唯一一行或更新仍是原 ID，检查目标内容及各场景指定的对照。新增 ID 只能由本次独立 DB 结果获得，不用响应反推 DB 预期。若生成完整响应所需 ID、时间或字段在请求前无法独立确定，保留一个公共、范围明确的响应投影比较：只比较已确认字段；对更新/重复保存按数据库原 ID 验证返回 ID。该例外不是登录校验，也不是和框架重复校验，因为完整预期在此分支无法表达。
3. 目前 Workbook 的成功和失败行分别只有 `{'code': 0}`、`{'code': 2}`，不能直接交给完整 JSON diff：实际响应包含其他字段。设计采用原有框架的空预期分支时，必须明确由上述公共函数执行一次有失败效果的业务码及已确认字段比较；这是一项框架缺口，不应伪称框架完成了该比较。错误场景也只比较 `code=2`，不固定错误消息。
4. **待决工程取舍**：若要求全部响应字段必须由 `DataBff.test` 的完整 JSON 比较，现有约束不能同时保证“不改公共框架、不凭响应造预期、不增加未确认时间/错误消息判据”。需另行确认允许的完整响应契约或部分匹配能力；在此之前不能承诺所有场景均由框架完成完整响应断言。当前设计优先保留已审核判据及用户不修改基础 API 的要求；第 2、3 项局部比较须随本方案审核。

### 4. 数据闭包与 26 项映射

沿用 [DC-004](../../preanalysis/data-closures/DC-004-备注读写数据闭包.md)、[只读 Q1/Q2/Q3](./api-query-oracle.sql)。`data/init/保存竞彩赛程备注基础数据.xlsx` 已有足球、篮球各自 league/team/match 六个 Sheet，按名称建立赛事与主客队关系；fixture 需在测试入口真实触发、动态分配非固定 ID、建立一对跨项目同数值比赛及另一篮球比赛。已有 `save_match_remark_data` 可作为对照，但其大量按表分支、映射和防御代码不是新设计的默认要求；实施时先检查项目已有初始化/清理能力，重新比较工作簿、fixture、处理函数和清理的总复杂度。若无法同时满足名称关系、动态 ID 和按归属清理，不得以覆盖共享记录或固定 ID 代替，应暂停并修订方案。

接口 Workbook 保持 `接口路径`、`保存竞彩赛程备注`、`保存竞彩赛程备注-参数`；参数 Sheet 分列 `sportId`、`matchId`、`remark`，按现有读取规则关联主行。`matchId` 的名称定位结构为赛事名、主队、客队；按运动项目连接对应 league/team/match，参数化查询必须唯一，首次请求前替换为数字。跨项目或对照比赛使用当前参数中已有的定位信息；不存在的 ID 在确认隔离及两项目和备注表均未占用后生成，禁止固定 ID。主表保留 `是否登录、用户名、密码` 相邻顺序及用户指定账号来源；描述写清测试内容和方法。

现有初始化数据只读核对：每个运动项目各一条 league、三条 team、两条 match；league 的名称字段为 `league_name`，team 为 `team_name`，match 的三项关联字段为 `league_id/home_team_id/away_team_id`。现有文件以名称表达关联而不是可直接入库的数字外键，因此无法宣称通用“逐 Sheet 原样插入”已支持；必须在审核设计时明确名称解析及同号 ID 的实现，避免把表映射重复散落到 fixture。若找不到可直接复用的初始化能力，保留最小必要的名称到 ID 映射、成功创建主键和逆序清理，并明确其与通用 Workbook 规则的差异；不得通过固定 ID 或删除所有匹配名称的数据规避。

Workbook 的处理函数映射：1、2、10～13、15、17、18、20 使用 `assert_save_remark(case_dict)`；3 使用 `assert_update_remark(case_dict)`；4 使用 `assert_repeat_remark(case_dict)`；5、6 分别使用 `assert_other_user_remark(case_dict)`、`assert_update_with_other_user(case_dict)`；7～9 分别使用 `assert_other_sport_remark(case_dict)`、`assert_other_match_remark(case_dict)`、`assert_other_type_remark(case_dict)`；14、16、19、21、22 使用 `assert_invalid_remark(case_dict)`；23、24 使用 `assert_invalid_match(case_dict)`；25 使用 `assert_unauthenticated_remark(case_dict)`；26 使用 `assert_remark_conflict(case_dict)`。第二账号从本次 Workbook 的已授权账号列取得，不在 Python 硬编码；需确保取得的账号与当前账号不同，且仅用于本次自有对照行。

- 目前框架会将完整 `case_dict` 和账号字段传入 Allure 参数；Workbook 凭据可能进入报告。为避免此次擅改公共封装，本版不设计新的认证或报告包装；实际执行及分发报告前须由使用方控制报告访问，是否另行修复属于独立决策。

## 3. 数据闭包与所有权

### 3.1 造数决策

**选择专用 `data/init` 初始化 Workbook 建立共享官方比赛基线，generator 直接准备少量场景备注。** 本接口的比赛闭包并非列表接口的赛事、球队和标准比赛多表链：它仅要求各项目官方比赛存在；多数用例共用比赛，且序号 7、8、24 需要可复用的同值跨项目、同项目不同值和另一项目独有 ID 关系。静态 DDL 中两张比赛表均以 `match_id` 为主键，其余列可空或有默认值，但实际部署结构、约束和采集隔离仍需确认。用两张表各少量固定行直观表达这些稳定关系，并由通用 fixture 初始化；不为此创建标准比赛、奖期、赛事或球队。

已评估其他方式：旧北单创建/删除函数不构建竞彩比赛，旧备注初始化操作 `m_match_remark`，均不能安全充当本接口的创建和清理链。每条用例直接重复创建比赛虽涉及行数少，却会重复搭建相同的共享项目/ID 关系；仅为这几行新增专用业务 builder 也无已验证的复用收益。因此选择初始化 Workbook；若运行库要求建立更多依赖或需大量字段转换、角色路由，应暂停并重新评估，而非继续扩大 fixture。

### 3.2 基础 Workbook 与入口

计划创建 `data/init/保存竞彩赛程备注基础数据.xlsx`，与接口用例 Workbook 分开：按 `sporttery_football_match`、`sporttery_basketball_match` 的 Sheet 顺序插入，逆序清理；各 Sheet 首列为 `match_id`，第一行为数据库字段名及项目支持的类型，第二行为说明，第三行开始为可直接入库的真实值。两表在本闭包中无已确认的先后依赖，顺序仅用于确定性清理，不推断外键。最终字段及类型以运行库核验为准；无需备注、账号、角色、场景控制、日期或其他业务表 Sheet。

计划基线示意（`X`、`Y`、`Z` 为此处解释关系的符号，不是实际单元格值）：足球 Sheet 两行 `X、Y`，篮球 Sheet 两行 `X、Z`。固定值须事先获准并在两表检查未占用，`X、Y、Z` 互不相同且属于可独占的安全域；Workbook 实际填写准确可入库的数字 ID，不写符号或表达式。普通足球/篮球用例分别使用本次基线足球/篮球 X；7 比较两表 X；8 比较足球 X/Y；24 请求足球 Z，并核验仅篮球 Z 存在；23 的请求参数提供额外预留的 W，确保 W 与 X/Y/Z 不同且两表均不存在，generator 在请求前核验，不将 W 写入基础 Workbook。没有可靠预留和采集隔离时不得执行对应场景；持续独占无法保证时所有依赖该基线的写入场景阻塞。固定 ID 的数值范围、Excel 整数精度、驱动类型、数据库约束及跨运行互斥必须实施前确认，禁止覆盖、`REPLACE`、取最大 ID 或把残留数据当作基线。

拟在现有 `testsuites/data-bff/sporttery_match_monitoring/conftest.py` 增加一个显式模块级 fixture `save_match_remark_data`：通用读取 Workbook 的 Sheet 顺序及行，通过现有 `Excel`、`DB_CONN` 能力插入；以实际成功插入的表及完整主键登记所有权，返回按表分组的实际记录。除第 8 点的对照比赛 ID 外，测试处理函数只使用真实请求参数，不传 fixture 返回值、不重新读初始化 Workbook。各 pytest 入口显式依赖该 fixture；单独选择任一用例时均会触发初始化；多用例执行共享本次基线但串行，场景差异不留给下一用例。该入口及调用链仅为设计，尚未实现或验证。不得增加 Workbook 已表达的表名顺序/主键映射、按 Sheet 或测试场景的分支、逐字段转换和私有路由。

初始化前验证固定 ID 在两张项目表及必要关联表无冲突，且使用获准的互斥/采集隔离；查询与插入之间仍可能竞争，唯一键冲突须安全停止，不认领或删除他人行。fixture 在首次插入前建立 `try/finally` 保护，仅登记成功插入的键；部分初始化失败、断言失败及正常退出均按 Sheet 逆序逐键精确删除自己的基础比赛并核验残留，保留原始错误并报告清理失败。不能证明所有权、隔离或清理安全时停止，不回退为共享比赛或扩大删除范围。

### 3.3 场景数据与清理

每次测试的 generator 拥有自己直接准备的 type=1/其他类型备注行及需要恢复的快照；账号 A 从认证配置获取，不持久化凭证；B 只需用于区分的本次测试专属、非 A 账号标识，若运行库约束要求真实用户则先核实并取得授权，不创建未批准账户。API 成功创建的记录由调用场景按专属比赛和当前账号完整键认领，确认其此前不存在、运行过程中无并发用户写入，记录真实 `remark_id`；不能仅因查询到同键就删除非本次记录。测试结束先核对并按自身创建的备注精确清理，再按实际依赖逆序移除自己创建的比赛；共享数据如不可避免，须有完整快照、可安全恢复的隔离和权限，否则不运行。

当前源码实体 `@Audited`，DDL 有 `audit_sporttery_match_remark` 和共享修订号，操作日志可能另有记录。先核实数据库及日志保留政策、用例归属与是否允许保留测试审计；禁止清理共享 `revinfo`、历史审计或以比赛 ID 大范围删日志。若政策要求清除而又无法证明仅属于本次测试并获准清理，写入实施受阻。generator 在首次场景写入前设置 `try/finally`；正常及异常时序和最小清理例外见 5.1，需覆盖请求、登录、断言失败与 setup 部分成功。若接口超时但可能已提交，先确认请求结束及写后状态，再按归属处置，不能立即假定未写入。

### 5.1 客户端时序与断言边界

静态追踪当前 `DataBff` 继承的 `API.test`、`API.request` 和 `verify_response`：`test` 先 `next(generator)`，再登录、请求；`request` 得到结果后在 `finally` 中 `send(actual_result)`，随后检查 HTTP 和预期。`expect_http_code or 200` 意味着即使传空值也默认断 HTTP 200；非空 `expect_result` 在非 500 状态调用 `json_tools.diff` 完整比较，500 时跳过 JSON 比较；空预期时 `success_response` 不匹配仅打印、不抛断言。`test` 登录异常时会再次推进 generator；请求或生成器异常可能改变实际结果/遮蔽错误。以上是源码核查，不是运行通过。当前 `DataBff.login` 还可能修改账号双因子字段，且失败消息可能暴露敏感信息；使用前必须确认专用账号与恢复责任、日志脱敏，不能将登录当作无副作用步骤。

| 组别 | 框架负责 | 额外判据与调用方式 |
|---|---|---|
| 成功 1～13、15、17、18、20 | `DataBff.test` 首次请求默认断 HTTP 200；空预期不作业务成功断言。 | 传空预期，generator 对响应对象检查 `code=0`、`message=OK`、`data` 为对象及测试点明确字段；3、4 的 `remarkId` 以写前 ID 核对，不为其他测试点增加未要求的响应字段；按 Q2 校验数据库副作用。未规定字段和时间不进入完整 JSON 对比，不用响应回填预期。第 4 点第二次请求由该场景按已审核判据检查成功及 ID，并在每次后查唯一记录。 |
| 错误 14、16、19、21～24 | 不走会强制 HTTP 200 的 `API.request`，不能把框架的空预期打印当作断言。 | 同脚本中用明确的错误用例入口，沿用受控授权登录上下文，通过独立 session 的原始响应发送；检查 JSON 对象及 `code=2`，不推定 HTTP 状态或其他字段，并按 Q1/Q2 验证无写入/对照不变。须维持逐行独立收集、清理和请求日志脱敏。 |
| 25、26 | 不调用共享 session 的 logout；不依赖框架默认状态或完整 JSON 比较。 | 25 独立无凭据会话，仅到达业务分支时断 `code=2` 和 Q2 不变；26 仅确认真实冲突后对冲突响应断 `code=2`、Q2 不重复和 B 不变。其余情况记录未覆盖。 |

成功入口参照同目录事件测试：pytest 接收 `case_dict` 和 fixture，构造 Excel 指定的业务 generator 并调用 `data_bff.test(case_dict, generator)`；准备数据、参数及独立预期在 generator 首次 `yield` 前完成，不手动提前 `next`。单一主 Sheet 固定 R01～R26 的顺序并检查读取恰为 26 行；参数化阶段仅对前 24 行按各行 `预期|json` 的业务 `code`（成功为 0，错误为 2）分配到成功或错误入口，第 25、26 行分别交给专用入口，禁止重复收集或发送。`预期|json` 的码来自已审核测试点，不是新增路由列；成功 generator 在 `yield` 前读取确认该预期码，再将本次 `case_dict` 的预期置为空，以避免框架对未约定字段做完整 JSON 比较，并于 `yield` 后按上表明确断言成功字段。错误入口直接消费事先确定的 `code=2`，以原始响应做局部断言。必须验证 `api_test_data()` 的行顺序、预期码和四个参数集合互斥且覆盖 R01～R26；若不能可靠区分，暂停并重新审核入口设计，不以标题匹配或新增控制列绕过。

错误入口需显式执行已授权的认证、生成器准备与清理，避免与成功入口重复调用。生成器 `try/finally` 从首次造数前覆盖；若 `API.test` 在推进后但请求接管前异常而未关闭生成器，入口仅为这一缺口在 `finally` 关闭仍存活 generator，不重复常规推进、登录或发送。需以失败注入验证这一例外及保留原始异常，若无法安全实现则阻塞对应组。

### 5.2 处理函数参数与 ID 来源

- `save_current_user_remark(case_dict, initial_remark=None, repeat=False)`：除 `case_dict` 外，3、4 的 `initial_remark` 是当前用例的原备注文本，4 的 `repeat=True` 表示测试点明确要求二次提交；1、2、10～13、15、17、18、20 使用默认值。由该函数消费这两个场景实参，分别准备原行和执行重复请求；目标 `(sportId, matchId)` 直接取真实请求参数，A 从授权认证配置取得。原文不重复存放 ID。
- `assert_remark_isolation(case_dict, baseline, comparison_match_id=None)`：`baseline` 是当前场景需创建的少量备注业务状态，包含用户角色 A/B、备注类型及不同文本，不包含比赛 ID；5/6 分别传 B 或 A+B，7/8 传目标与对照 A，9 传合法非 1 类型 T 的 A。目标 ID 取请求；7 的对照项目取另一个已确认项目且使用相同 ID；仅 8 从 `save_match_remark_data` 返回的足球第二行取 Y，作为 `comparison_match_id` 被该函数实际用于新增、查验和清理对照键，表达式可为 `assert_remark_isolation(case_dict, baseline, save_match_remark_data['sporttery_football_match'][1]['match_id'])`，其中 `baseline` 在实际表达式中是场景字面值而非未定义变量。Y 无法从仅有 `match_id` 的目标请求及其无关联的比赛表唯一推导，因此是必要的 fixture 上下文；不得把 Y 再复制到 Excel 参数或 baseline。9 的 T 需先确认合法，不能猜测。
- `reject_invalid_remark(case_dict)`：错误组前置建立 A/B 备注；目标项目、比赛和非法内容均来自请求。`reject_invalid_match(case_dict)`：23 直接使用请求中的 W；24 以请求足球 Z 推导篮球同 ID 对照；不接收 fixture 上下文。两者由错误入口消费，仅检查对应业务码与 Q2，按完整键清理。
- 25/26 专用入口接收 `case_dict` 和用于 setup/teardown 的 fixture；不把 fixture 上下文透传给无消费者的 generator。A 从授权上下文、B 从获准的本次测试身份配置取得；后续新建备注的 `remark_id` 从成功插入结果/独立 Q2 获取。所有表查询参数化，Q1 按主键唯一判断；不从响应或 `MAX(id)` 推导数据，不重新读取基础 Workbook。

成功业务族复用公共 `assert_saved_remark(case_dict)` 的动态响应及 Q2 检查，通过 `yield from` 传递实际请求所需 `case_dict`；场景函数负责各自前置和清理。函数参数均为拟定设计；实际 Excel 表达式必须与函数签名、fixture 的作用域和真实消费者一致，并验证读取链、关联条件及异常清理。若无法实现上述参数映射或入口分类，保持受影响组阻塞并提交修订审核，不得声称实施就绪。

若确实需要复用的稳定竞彩比赛创建/删除能力，先确认 `common/` 已有方法与团队约定；必要时在对应业务文件新增最小动作及配套清理并重新审核，不预先强加新的 common 模块、类、Sheet 或控制列。不会修改 `settings.py`、已有 Workbook、业务服务、其他接口方案或共享认证信息。
