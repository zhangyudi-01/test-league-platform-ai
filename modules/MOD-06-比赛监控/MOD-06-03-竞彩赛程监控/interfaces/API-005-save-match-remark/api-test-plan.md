### 公共前提与判定

1. 除明确说明外，使用已登录账号 A、有效的竞彩官方比赛及 JSON 对象请求；所需记录应由本次测试独立准备，比赛 ID 不使用标准比赛 ID。足球、篮球分别为 `sportId=1`、`sportId=2`。
2. 成功的共同预期：HTTP `200`、`code=0`、`message=OK`、`data` 为单个对象；每条额外核对所列字段和记录，不把对象当成数组。失败时仅在接口有明确业务码依据的场景断言 `code=2`，不预设错误 HTTP 状态、错误 data、字段缺失、固定精确 message 或多重错误优先级。
3. 长度按原始输入的用户感知字符计数，首尾空格计入；本方案用简单字符、单个 Emoji 和 `e` 加组合重音作为可辨识示例。Q-001 确认计数，不单独改变 OpenAPI 中首尾空白规范化保存的描述。复杂 Unicode 分段版本未指定，不对不同实现可能存在分歧的序列擅自规定判据。
4. 记录应按 `sport_id + remark_type + match_id + create_account` 精确定位；对本次新增记录按完整键清理，共享记录先记录原状态再恢复，不影响其他账号。操作日志和审计记录的清理应由后续设计核实，不以删除共享历史作为默认手段。
5. 失败无写入以请求前后的目标及同场其他账号记录比较为准；每个场景只触发所描述的一种错误，避免利用未定义的校验优先级。

## 四、差异与工程适配

1. **长度及存储差异**：序号 16～20 的 API 请求与响应可观察，数据库变化也可核验；源码静态分析显示先 `strip()`，再按 Java `String.length()` 计数。2026-11-04 实测 16～18 失败、19～20 通过，详见[Q-001 记录](./clarification-questions.md)。`varchar(300)` 限制是数据库字段事实：用户感知字符由多个码点组成时，300 个字素簇可能超出该字段容量；序号 20 特意控制在 300 码点以内，字段容量不足导致的其他输入如何处理尚无明确承诺，不写成确定成功或失败。
2. **现有框架**：DataBff 的 `API.request`、`API.test`、数据库 `DB_CONN` 及 Generator 支持请求和数据核验；检索现有 common 与 data-bff 脚本未找到竞彩备注专用 helper。序号 1～24 的副作用可观察，后续自动化设计需确认官方比赛及备注的可清理准备方式、用户感知字符分段方法。旧备注 helper 写入 `m_match_remark`，不能直接当作竞彩备注构造能力。
3. **登录与冲突**：序号 25 的请求和目标数据可观察，但独立未登录会话可能先被网关拦截；需确认如何到达业务分支，网关拦截不能当作其验证通过。序号 26 的响应及唯一键结果可观察；当前未确认可稳定触发冲突的工程设施，后续评估受控并发或其他可复现方式，不假设每次并发都会冲突。
4. **状态**：本方案根据已确认业务口径编写，实际执行、未覆盖场景、环境副作用及证据边界见[自动化实施记录](./api-test-automation-plan.md)；不以方案存在、测试收集或源码推断代替执行证据。
