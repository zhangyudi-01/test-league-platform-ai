### 2.2 接口与数据边界

1. 内部路径为 `GET /sporttery/match-monitor/remarks`，管理端 BFF 路径为 `GET /data-backend/sporttery/match-monitor/remarks`。正常页面先查询竞彩监控列表，再传入所选比赛的 `sportId` 和竞彩官方 `matchId`。足球 `sportId=1`，篮球 `sportId=2`；官方 `matchId` 不等于标准比赛 ID 的概念。
2. 指定项目、官方比赛及 `remark_type=1` 决定查询范围。`account` 为备注创建账号；`isCurrentUser` 标记备注是否属于当前登录账号。当前账号备注置顶，其余按 `updateTime` 升序，同时间按 `remarkId` 升序。
3. 用户确认已登录时非法参数或比赛不存在按参数错误断言业务 `code=2`，不严格限定错误文案、HTTP 状态或错误 `data`；多个错误不限定优先级。参数是否必填或可选、缺参行为不在本轮范围。单独未登录的 operation 文档列业务 `code=2`，认证拦截可能先于服务返回，见第四节。
4. 比赛存在但无备注时返回 `data=[]`；记录内字段无值返回 `null`，不把空字符串直接等同于无值。当前 DDL 中本接口字段对应的备注列均为 `NOT NULL`，故不为制造 null 违反该约束；实际序列化情况待调试核验。

### 2.3 公共前提与判定

- 除未登录或多重错误场景外，使用有权登录的账号 A；需要验证另一登录身份时使用有权账号 B，凭据由安全配置或现有认证流程提供，不写入方案。每个场景独立准备或确认比赛及备注，明确账号归属，并确保目标查询范围不被其他数据干扰。
- 成功查询的共同预期为 HTTP `200`、`code=0`、`message=OK`，`data` 为数组；每条场景在此基础上核对所列数量、字段、顺序及不包含的记录。若正常结果未达到共同成功条件，该场景不能判为通过。
- 涉及数据库记录比较时，以独立确认的源记录作为预期，比较时间的年月日时分秒，不额外规定时区后缀；数据按 `sportId + matchId + remark_type + create_account` 等可定位键精确清理或恢复，不删除其他用户的数据。比赛身份和数据准备的具体方式留给后续设计。
- 排序场景要求所列记录为目标范围内全部备注，确保每个账号最多一条，符合 DDL 唯一键；不依赖数据库默认顺序。下表中 A、B、C 等仅为身份或数据角色，不代表固定账号值。

## 四、适配与风险

1. **序号 4、7～9：API 可观察；框架实现状态**：通用客户端支持登录，但两个可用且有权限的账号、稳定切换身份和多账号备注准备尚未验证；现有 `common/matchup_remark.py` 和 `common/draft.py` 操作旧 `m_match_remark`，不适合作为竞彩备注数据和预期来源。后续自动化设计评估新表数据准备与隔离。
2. **序号 10、17、20～21：API 可观察；框架实现状态**：同数字跨项目比赛、未关联标准比赛及不存在比赛的受控样本是否能由现有 fixture 准备尚未证实，后续设计应核验数据闭包和精确清理；不得修改或删除共享比赛来制造不存在状态。
3. **序号 20～21：已知实现差异**：用户确认比赛不存在应返回业务 `code=2`；本地 `listRemarks` 不检查比赛存在，可能成功返回空数组或残留备注。部署情况未验证，调试时须保留预期并记录真实结果，再按用户决定调整，不以本地代码直接改写预期。
4. **序号 22～23：API 可观察；框架实现状态**：通用客户端提供登录和登出，但需确认未登录请求是否被网关或认证层先拦截；只有明确进入 operation 对应业务错误分支时才核对 `code=2`，不得预设拦截层的 HTTP、code 或文案。多重错误不限定优先级。
5. **字段 null**：用户确认记录内无值返回 `null`，但本接口当前 DDL 对应字段均非空，未发现可依据现有合法源数据构造字段 `null` 的确定路径。该规则保留为契约，待后续发现合法无值来源或环境数据后核验；不通过违反表约束、把空字符串当 `null` 或伪造响应来宣称已验证。

本方案未执行真实 API 或数据库测试；具体造数、独立数据库核对、框架扩展及清理由后续自动化设计处理。
