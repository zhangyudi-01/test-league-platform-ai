> API-ID：`API-003`  
> 方案状态：序号 1～22 已审核；参数异常按 Q-001 确认的宽松错误预期处理。

### 2.2 接口和数据边界

1. OpenAPI operation 为 `GET /sporttery/match-monitor/events`；管理端 BFF 路径为 `GET /data-backend/sporttery/match-monitor/events`。测试使用项目既有登录和 DataBff 调用方式，凭据从安全配置读取。
2. 请求使用 `sportId`、`matchId`：`sportId=1` 为足球、`sportId=2` 为篮球；`matchId` 是竞彩官方比赛 ID，对应事件表 `source_id`，不是 `s_match.match_id`。
3. 从 `sporttery_match_event` 获取事件：`eventTime` 取 `create_time`，`title` 取 `event_name`，`exceptionDetail` 取 `reason_desc`。不分页，返回该比赛的全部匹配事件；按 `create_time DESC, event_id DESC` 排序。
4. 当前 DDL 将竞彩事件来源标注为 `SPORTTERY`，并将 `event_id`、`create_time`、`event_name`、`reason_desc` 定义为非空。测试数据按当前表约束准备，除明确指定的隔离记录外，不依赖环境中原有事件。
5. 当前 operation 不使用旧比赛监控的 `s_event`、开售时间窗口和历史事件计数规则；不从旧实现引入额外的事件类型、渠道或任务过滤规则。

### 2.3 公共前提与判定

- 以下每个测试点独立准备并定位所需的官方比赛及事件数据，完成后由数据创建方按本次唯一标识精确清理或恢复；不得依赖其他用例先执行。
- 成功请求的共同预期为 HTTP `200`、业务 `code=0`、`message=OK`，`data` 为数组。每个场景另按其列出的数量、内容及顺序判定；数组项的时间、标题和详情与对应事件记录比较。
- 校验时间字段时按数据库 `DATETIME` 的秒精度核对年月日时分秒，不擅自规定接口未明确的时区后缀或偏移转换规则。
- 每条正常事件的数据库 `event_id` 非空，响应项必须返回与之完全一致的字符串 `eventId`；不依赖数据库默认返回顺序。

## 三、测试内容

### 预期目标

验证足球、篮球比赛事件的查询范围、全部记录返回、响应字段映射和稳定倒序；验证合法查询无事件时的空数组语义，以及查询对事件数据的只读性。

| 序号 | 测试项 | 测试点 | 备注 |
| --- | --- | --- | --- |
| 1 | 基本查询 | 【竞彩足球单条事件】准备一场有且仅有一条目标事件的竞彩足球比赛；请求 `sportId=1` 和该官方 `matchId` → 成功返回长度为 1 的事件数组，`eventTime`、`title`、`exceptionDetail` 分别等于该事件的 `create_time`、`event_name`、`reason_desc`。 | RSU-012、Q-004、DC-003 |
| 2 | 基本查询 | 【竞彩篮球单条事件】准备一场有且仅有一条目标事件的竞彩篮球比赛；请求 `sportId=2` 和该官方 `matchId` → 成功返回长度为 1 的事件数组，时间、标题和异常详情分别等于该事件对应字段。 | RSU-012、Q-004、DC-003 |
| 3 | 运动项目隔离 | 【相同官方比赛 ID】准备足球和篮球两场官方 `matchId` 数值相同的比赛，各有内容不同的事件；分别请求 `(sportId=1, matchId=X)` 和 `(sportId=2, matchId=X)` → 两次均成功，各自只返回本运动项目的事件，不互相混入。 | OpenAPI、DC-003 |
| 4 | 比赛隔离 | 【同运动项目不同比赛】同一运动项目下准备官方比赛 A、B，各有内容不同的事件；请求比赛 A 的 `sportId`、`matchId` → 只返回 A 的事件，不返回 B 的事件。 | RSU-012、DC-003 |
| 5 | 比赛 ID 域 | 【官方 ID 与标准比赛 ID】准备同一运动项目的合法官方比赛 A、B，A 的事件 `source_id=A`、`s_match_id=B`，且 A、B 不同、B 没有事件；分别请求 A 和 B 的官方 ID → A 返回该事件，B 返回 `data=[]`，不得按事件的 `s_match_id` 错配。 | 模块 Q-003、Q-004、DC-003 |
| 6 | 比赛 ID 域 | 【未关联标准比赛】准备一条 `s_match_id=NULL` 且 `sport_id`、`source_id` 与目标官方比赛匹配的竞彩事件；请求该比赛 → 成功返回该事件，不因缺少标准比赛关联而遗漏。 | Q-004、DC-003 |
| 7 | 比赛 ID 域 | 【64 位官方比赛 ID】准备一场官方 `matchId` 大于 32 位有符号整数上限且在 `int64` 范围内的比赛及其事件；请求该官方 ID → 成功返回对应事件，不因数值截断而查错或漏查。 | OpenAPI、DC-003 |
| 8 | 返回完整性 | 【多条事件全部返回】为目标比赛准备 25 条可通过标题区分的事件，同时存在其他比赛的干扰事件；请求目标比赛 → 返回数组恰含目标比赛的 25 条事件，每条各出现一次，不遗漏、不重复、不混入其他比赛的事件。 | Q-004、DC-003 |
| 9 | 空结果 | 【目标比赛无事件】准备一场目标官方比赛，其对应运动项目下没有事件，同时其他比赛或其他运动项目有事件；请求目标比赛 → 成功返回 `data=[]`，不是 `null`，也不返回其他比赛的事件。 | 模块 Q-003、DC-003 |
| 10 | 事件时间 | 【创建时间字段来源】准备一条 `create_time` 与 `update_time` 不同的目标事件；请求该比赛 → 返回项 `eventTime` 为日期时间字符串，所表示的年月日时分秒与该记录的 `create_time` 一致，不取 `update_time`。 | RSU-012、Q-004、DC-003 |
| 11 | 事件排序 | 【不同创建时间】准备同一比赛的多条事件，使创建时间跨越不同日期，且事件 ID 或更新时间顺序与创建时间顺序不同；请求该比赛 → 所有事件按 `create_time` 从新到旧排列，不能按 ID 或 `update_time` 作为首要排序。 | RSU-012、OpenAPI、DC-003 |
| 12 | 事件排序 | 【相同创建时间】准备同一比赛的两条事件，`create_time` 相同，事件 ID 使用按当前字段排序规则可区分大小的不同字符串，标题分别为 A、B；请求该比赛 → 事件 ID 较大的那条对应的标题排在另一条之前。 | OpenAPI、SRC-DB-SCHEMA、DC-003 |
| 13 | 标题字段 | 【事件名称与原因标题不同】准备一条 `event_name` 与 `reason_title` 不同的目标事件；请求该比赛 → 返回的 `title` 与 `event_name` 完全一致，不取 `reason_title`。 | RSU-012、Q-004、DC-003 |
| 14 | 异常详情 | 【详情内容原样返回】准备一条 `reason_desc` 含中文、换行和引号等内容的目标事件；请求该比赛 → JSON 解码后的 `exceptionDetail` 与该记录 `reason_desc` 完全一致，不丢失字符或换行。 | RSU-012、Q-004、DC-003 |
| 15 | 标题字段 | 【标题存储上限】准备一条 `event_name` 为 64 个合法字符且符合表约束的目标事件；请求该比赛 → `title` 与完整的 `event_name` 一致，不截断。 | Q-004、SRC-DB-SCHEMA、DC-003 |
| 16 | 异常详情 | 【详情存储上限】准备一条 `reason_desc` 为 2048 个合法字符且符合表约束的目标事件；请求该比赛 → `exceptionDetail` 与完整的 `reason_desc` 一致，不截断。 | Q-004、SRC-DB-SCHEMA、DC-003 |
| 17 | 返回完整性 | 【相同标题和详情的不同事件】准备同一比赛的两条事件，它们的 `event_name`、`reason_desc` 相同，但事件 ID 和 `create_time` 不同；请求该比赛 → 返回两条记录，两个事件时间均存在且按创建时间倒序，不因展示内容相同而合并。 | Q-004、DC-003 |
| 18 | 事件标识 | 【事件 ID 必返且原样保留】准备事件 ID 含字母大小写及前导零的一条目标事件；请求该比赛 → 响应项必须包含字符串 `eventId`，其值与对应数据库 `event_id` 原值完全一致。 | 接口 Q-002、DC-003 |
| 19 | 重复查询 | 【相同数据重复请求】准备目标比赛事件并保持数据不变，连续两次请求同一 `sportId`、`matchId` → 两次均成功，返回的事件内容及顺序一致。 | Q-004、DC-003 |
| 20 | 只读性 | 【查询不修改事件】记录目标比赛事件集合的主键、展示字段及创建/更新时间，请求该比赛后再次读取同一比赛的全部事件 → 事件主键集合不变，原有记录的上述字段均与请求前一致。 | API-003 接口分析、DC-003 |
| 21 | 标题字段 | 【事件名称为空字符串】准备一条 `event_name=''` 且 `reason_desc` 非空的目标事件；请求该比赛 → 返回项包含 `title`，其值为 `""`，不转换成 `null` 或省略。 | 接口 Q-003、DC-003 |
| 22 | 异常详情 | 【异常详情为空字符串】准备一条 `reason_desc=''` 且 `event_name` 非空的目标事件；请求该比赛 → 返回项包含 `exceptionDetail`，其值为 `""`，不转换成 `null` 或省略。 | 接口 Q-003、DC-003 |

### 需求覆盖去向

- RSU-012 的事件时间、标题、异常详情对应序号 1、2、10、13～16、21、22；时间倒序对应序号 11、12。
- 对应比赛、运动项目隔离、完整返回和空结果对应序号 3～9、17；接口只读和重复查询对应序号 19、20。
- 点击事件、弹窗打开/关闭、页面样式及字段在页面上的显示属于功能侧。此处仅标明职责边界；接口未实际执行前，不能将对应需求认定为已覆盖，也不提前形成模块最终功能残余结论。

## 四、待确认与适配

1. **参数错误（接口 Q-001）**：用户确认调试阶段以接口报错为准，不固化 HTTP 状态、业务码或文案；连接失败不能作为接口报错。缺参、`sportId=3`、`matchId=0/-1` 的开发环境观察见问题清单；这些探测尚未形成自动化用例，其他取值和类型绑定仍未验证。
2. **事件 ID（接口 Q-002）**：数据库事件 ID 非空时响应项必须返回对应 `eventId`；序号 18 对字段存在性、类型及原值作确定性断言。
3. **空字符串（接口 Q-003）**：数据库中合法存储的空字符串原样返回；序号 21、22 分别覆盖标题和异常详情。不通过违反表约束伪造数据库 `NULL`。
4. **接口可观察性与工程适配**：序号 1～22 的响应或事件表变化可由 API/数据库观察。当前已查阅的测试工程具备 DataBff、Excel 驱动和数据库访问能力，但未在 `common` 和 data-bff 测试脚本中找到写入 `sporttery_match_event` 的专用 helper；后续自动化设计需评估可清理的数据准备方式，不能把写入旧 `s_event` 的 helper 当成当前事件造数。

问题正文和状态见 [API-003 问题清单](./clarification-questions.md)。本方案序号 1～22 的实际执行和清理结果见 [自动化实施方案](./api-test-automation-plan.md)；本地代码快照与开发环境部署版本不一定一致。
